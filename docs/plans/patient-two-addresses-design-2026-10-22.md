# 患者様の住所を 2 つ持つ（保険証の住所・実際の訪問先）設計 2026-10-22

> 状態: 仕様は PO 了承済み（§7・10-22）。実装は未着手。コード・本番は未変更。
> きっかけ: 川名さんの依頼（Slack 10-22）。P021 様は 10/20 から保険証の住所と約 3.5km 離れた場所で訪問しており、QR が毎回「場所違い」になる。

## 1. 要件（PO 10-22）
1. **保険証の住所**: レセプトに使う住所（カイポケ上はすべてこの住所）。いまらく助に登録している住所を入れる。
2. **実際の訪問先の住所**: らく助で距離を測る（QR の判定など）ための住所。違う場合だけ入力する。
3. 同じ場合は、もう一度打たずに「保険証の住所と同じ」をボタンで選べる。そのうえで、両方の欄を埋めておく。
4. 訪問先が未記入なら、とりあえず保険証の住所と同じにする（QR が困らないように）。

## 2. 調査で分かったこと（読むだけ・10-22）
- いまは `patients.address`（String 255）と `lat`/`lng`（Numeric 10,7）の **1 組だけ**（`backend/app/models/patient.py:83-85`）。
- `lat`/`lng` を読んでいるのは、QR の距離判定（`services/checkin/judge.py:103-140`）、位置のずれ（`checkin/location_drift.py`）、ペア補正・訪問モニター（`checkin/monitor.py`）、移動時間・割り当て・ならし（`scheduling/auto_allocator_v2.py`、`allocation/engine.py`、`layer2_clustering.py` ほか）、実現性チェック（`feasibility_check.py`）、同住所の判定（`api/v1/patients.py:479-600`、`patient_sync.py:852-1003`）。**どれも「実際に行く場所」の意味で読んでいる。**
- 住所の文字を読んでいるのは、Google マップのリンク（`frontend/lib/maps.ts`。行き先は住所の文字）、実現性レポート、カルテ A4（`patient_excel/karte.py:315`）、Excel 出力・取込（`patient_excel/exporter.py:313-316`・`importer.py:699-700`）、エージェントの道具（`agent/rk/ops/masters.py`）。
- カイポケ連携は住所を使っていない（患者と時刻で照合）。
- カイポケの「各種情報出力 → 出力対象選択 → 利用者情報」の CSV に、**保険証の住所**（郵便番号・都道府県・市区町村・町名以下・建物名の 5 列）がある。10-22 に 1 回出して確認（122 名）。らく助と名前で突き合わせると、住所まで一致 104 名、稼働中で違う 9 名、建物名・部屋番号だけ違う 3 名。
- 夜間に住所から座標を求め直して上書きする処理（`services/geocoding/audit.py`）はコードにあるが、**本番には登録されていない**（10-22 確認）。
- 位置のずれ合わせ（`api/v1/patient_location.py`）は `lat`/`lng` と `geocoding_cache` を打刻の位置に合わせる。10/21 に P021 で 1 回使われたが、直近 45 日の中央値が元の場所だったため効かなかった。

## 3. 方針: いまの列を「訪問先」とし、「保険証の住所」の列を足す
| 列 | 意味 | 変更 |
|---|---|---|
| `address` | **実際の訪問先の住所** | 意味の呼び名だけ変える（画面の表示は「訪問先の住所」） |
| `lat` / `lng` | 訪問先の位置 | 変えない |
| `insurance_address`（新） | **保険証の住所**（レセプト・カイポケと同じ） | String(255)・NULL 可 |
| `visit_same_as_insurance`（新） | 訪問先は保険証の住所と同じか | Boolean・NOT NULL・既定 true |

**理由**
- 距離を測る処理（QR、移動、ならし、同住所、モニター、地図）は、すべていまの `address`/`lat`/`lng` を「行く場所」として読んでいる。この列を訪問先にすれば、**それらを 1 行も変えずに**訪問先で動く。
- 逆に、訪問先の列を新しく足す案では、`lat`/`lng` を読む多くの箇所（§2 の一覧）をすべて書き換えることになる。抜けが出やすく、危ない。
- 保険証の住所は**位置（座標）を持たない**。距離を測る目的がなく、レセプトとカイポケとの照合にだけ使うため。

## 4. ふるまい
### 4-1. 保存のきまり（backend で必ず守る）
1. `visit_same_as_insurance = true` のとき: `address` に `insurance_address` を写す。住所が変わったときは位置も作り直す（いまと同じ自動変換）。
2. `visit_same_as_insurance = false` で `address` が空のとき: **要件 4 により true に戻し**、1 と同じにする。
3. `visit_same_as_insurance = false` で `address` があるとき: 訪問先は別の場所として、そのまま保存する。保険証の住所が変わっても、訪問先は動かない。
4. 保険証の住所が空で、訪問先だけがあるとき: **空のまま**にし、一覧と詳細に「保険証の住所が未記入」と知らせる。レセプト用の住所を推測で埋めない（PO 10-22）。

**訪問先の位置の網（10-22 レビューで改める）**: 「サーバーは geocode しない」をやめる。
- きまりを当てた結果、訪問先 `address` が保存済みの値（新規は空）から変わったのに、要求に新しい `lat`/`lng` が無い（来ていない、または保存済みと同じ）ときは、**サーバーで位置を求める**。求め方は `/geocode` と同じ「控え（`geocoding_cache`）優先 → 無ければ Google → 控えに保存」（共通の関数 `services/geocoding/cached.py`）。
- 求められない（見つからない・キー未設定など）ときは **422**「訪問先の住所から位置が見つかりませんでした。緯度・経度を入れてください。」。`address` が空になるときは `lat`/`lng` も空にする。
- PATCH で「同じ」のまま（保存済みも要求も true）、要求の `address` が保険証の住所と違う → **422**「訪問先が保険証の住所と同じになっています。別の場所にするときは『別の場所』を選んでください。」（古い画面が address だけ送ってきたときに黙って捨てない）。
- Excel 取込（新しい形式）: ○ の行で「訪問先の住所」が「保険証の住所」と（trim・NFKC で）違う → 行エラー「○ を外すか、訪問先の住所を保険証の住所に合わせてください」。○ が空でも 2 つが同じ文字なら「同じ」。訪問先が変わり行の緯度経度が保存済みと同じ（または空）なら同じ関数で位置を求め、求められなければ行エラー（プレビューで分かる）。古い形式の扱いは変えない。
- スマホの申請: 位置を求めるのは、きまりを当てた後の `address`。

### 4-2. 画面（患者の登録・編集 `PatientForm.tsx` の「連絡先」カード）
```
住所
  保険証の住所（レセプト・カイポケと同じ）  [ 千葉県千葉市…                ]
  実際の訪問先   (●) 保険証の住所と同じ   ( ) 別の場所
                  └ 同じとき: 写した住所と地図の位置をうすく表示（入力はできない）
```

- 患者の一覧と詳細: 訪問先が別のときだけ「訪問先は別」の札を付け、両方の住所を並べる。
- 文言: QR まわりの「登録住所」を「訪問先の住所」に変える（`settings/checkin/page.tsx`、`m/today/[visitId]/page.tsx`、`q/[token]/page.tsx`、`MonitorDetailPanel.tsx`、`MonitorMapClient.tsx`）。
- 住所は今と同じく管理者だけに見せる（保険証の住所も同じ扱い）。職員の画面には訪問先だけを出す。

## 5. カイポケとの照合（今回の範囲外・別に設計する）
PO 10-22: カイポケ側が間違っていることもあるので、カイポケを正としてらく助へ自動で反映するとは限らない。住所以外の項目（生年月日・連絡先・利用状態など）も含めて、**患者マスターとカイポケの利用者情報を見比べる仕組み**として、別に設計を検討する。

そのときの材料（10-22 に確かめた事実）:
- 取り方: 「レセプト → 訪問看護 → 各種情報出力 → 出力対象選択 → 利用者情報 → CSV出力」。条件は所属事業所だけ。RPA の予定の CSV（`lib/common.py` の `goto_export_page`）と同じ道。
- CSV は cp932、29 列。利用者名・カナ・生年月日・性別・郵便番号・都道府県・市区町村・町名以下・建物名・電話・携帯・請求方法・請求送付先・請求先の住所など・口座の列・利用者状態・備考。10-22 の時点では、口座番号などは空で、口座種別だけ全員に入っていた。必要な列だけを読み、ファイルは残さないこと。
- 住所の比べ方: 全角・半角、空白、ハイフンの種類、「丁目・番地・号」の書き方をそろえてから比べた。名前は異体字（齋・齊、髙、﨑 など）が違っても、カナと住所が同じなら同じ方の見込み（P119 の例）。

## 6. 試験
- backend: §4-1 の 4 つのきまり（同じ／別／別だが空→同じに戻る／保険証の住所だけ空）、migration の up→down→up、Excel の往復、権限（職員に保険証の住所を返さない）。
- frontend: 「同じ／別の場所」の切り替えで、位置の欄と保存の中身が正しく変わること。QR の文言。
- 本番の前に: 稼働中の全員で、migration の後も `address`・`lat`・`lng` が 1 件も変わっていないこと。

## 7. 決まったこと（PO 10-22）
- 保険証の住所が空で訪問先だけある方: 空のまま知らせる（§4-1 の 4）。
- カルテ A4 と実現性レポート: 訪問先の住所を出す。
- 一時的な訪問先（期間付き）は今回は持たない。戻ったら「保険証の住所と同じ」に戻す運用にする。
- カイポケとの照合は今回の範囲外。患者マスターと利用者情報を見比べる仕組みとして別に設計する（§5）。
