# 設計書: 自動スタッフ割当 — 不可避連続の通知化・警告適量化・拠点ハードコード除去

作成 2026-07-03 / PO 指示（同日）に基づく。対象 = Layer 3 自動スタッフ割当
（`backend/app/services/scheduling/layer3_assignment.py` / `POST /api/v1/schedule/assign-staff-only` /
`frontend/components/schedule/v2/AssignWarningDialog.tsx`）。

## 0. PO 指示（2026-07-03・原文要旨）

1. 拠点の事情や物理的に不可避な連続割当が発生するのは仕方ない。推奨方針（B+C）で進めてよい。
2. ただし管理者に「理由」を示すこと。ローテーションが機能していると思い込んだまま
   特定スタッフ×患者の連続が続くと後で問題になる。**事前に伝えて納得を得る**。
3. 警告が大げさに出すぎて縦に並び、システムの問題として不安を与えている。
   過剰に出さず、必要な情報は正しく伝わるバランスに。
4. 「都賀」拠点名ハードコードは他社事業所への展開を考えると非常にまずい。改善する。

> **注記（オーナー決定Bの上書き）**: 従来「1名拠点でも連続は必ずレビューに出す」
> （G-91 修正3・オーナー決定B、`_build_review_items` docstring 参照）が正だったが、
> 本指示 1&3 によりこれを上書きする。不可避な連続はレビュー（承認ゲート）に出さず、

## R-1. 「都賀」ハードコード除去（マルチテナント対応）

### 現状
`_build_fixed_assignments` step 2 が `if "都賀" not in (office.name or "")` で
サテライト拠点の固定割当（active role=staff の code 昇順先頭 1 名 → 当該拠点 A コース）を
発動している。拠点名の変更・他社展開で silently 機能しなくなる。

### 採用案: OfficeFeatureFlag による設定化
- `FeatureKey` Literal に **`l3_fix_primary_staff`** を追加
  （既存 `g21_new_algorithm` と同じ仕組み・スキーマ変更なし）。
- `_build_fixed_assignments` step 2 は「`l3_fix_primary_staff` が enabled な拠点」を対象にする
  （拠点名判定を全廃）。固定するスタッフの選定ロジック（active role=staff の code 昇順先頭）は不変。
- **データ移行 migration 0051**: 拠点名に「都賀」を含む office に本フラグを INSERT
  （note='2026-07 拠点名ハードコード除去の移行'）。→ 現行動作を完全保存しつつ一般化。
- 新規拠点・他社展開時は管理操作（フラグ INSERT）だけで同じ挙動を設定できる。

### 不採用案（記録）
- **構造導出**（「active staff が 1 名だけの拠点は自動で固定」）: 設定不要で魅力的だが、
  都賀に 2 名以上いる場合に現行挙動（先頭 1 名固定）と分岐し、本番挙動が黙って変わるリスク。
  フラグ方式なら挙動変更ゼロ。将来「フラグの既定動作」として再検討可。
- **固定割当ルールテーブル + 管理UI**: 最も柔軟だが今のニーズに過剰。必要になったら昇格。

## R-2. 不可避連続の判定と自動確定（B+C の実装）

### 判定（コースごと・連続 conflict 対象）
連続レビュー候補（`rotation_conflicts` の `recent_index==0`）の各コースについて
**「代替候補」の実在**を検査する:

```
代替候補 = active staff のうち、当該コースに対して
  ・ハード制約を全て満たす（勤務曜日 / 実効拠点一致 / 性別AND / StaffEvent非重複 /
    直近1週同コード除外）
  ・当該曜日の他コースに（この実行で）割当済みでない
  ・原因患者すべての直近担当者リスト（working_recent）に入っていない
  ・現候補スタッフ本人でない
```

- 代替候補 **0 名 → 不可避（unavoidable）**: レビューに出さず、クリーンなコースと同じ
  `_persist` 経路で**自動確定**し、`notices[]` として理由つきで返す。
- 代替候補 **1 名以上 → 回避可能（avoidable）**: 従来どおり 🟡 レビュー（一斉承認可）。
  ※ ハンガリアン法が全体最適の結果としてあえて連続を選んだケース。管理者の判断が意味を持つ。

### 理由文（reason_kind → 文面。表示は FE）
- `single_staff`: 「この曜日に◯◯（拠点）で勤務できるスタッフが△△さん 1 名のため、連続担当は避けられません」
- `all_recent`: 「対応可能なスタッフ全員がこの患者の直近担当者のため、どなたが担当しても連続になります」
  （代替候補 0 の内訳: 適格者そのものが 1 名なら single_staff、適格者は複数いるが全員 recent なら all_recent）

### API 契約（後方互換の追加のみ）
`POST /assign-staff-only` レスポンスに追加:
```jsonc
"auto_committed_notices": [
  {
    "course_id": "...", "course_code": "A", "weekday": 0, "office_name": "都賀",
    "staff_name": "...", "cause_patient_names": ["..."],
    "reason_kind": "single_staff" | "all_recent",
    "reason_text": "..."   // BE で組み立てた日本語文（FE はそのまま表示）
  }
]
```
`courses_assigned` は自動確定分を含む合計。既存クライアントは新フィールドを無視できる。

## R-3. レビュー UI の適量化

- **🟡 連続（回避可能のみ）**: 従来カード＋一斉承認（実装済み）。件数が構造的に減る。
- **🔵 お知らせ（不可避・確定済み）**: AssignWarningDialog 内の**折りたたみセクション**
  「体制上避けられない連続 N 件（確定済み）— 理由を見る ▼」。展開すると 1 行コンパクト表示
  （拠点/コース/曜日/スタッフ→患者/理由文）。**アクションボタンなし**（確定済みの情報提示）。
  既定は折りたたみ = 縦にずらっと並ばない。
- ダイアログを開く条件: `review_items > 0 || notices > 0`。notices のみの場合は
  タイトル・説明文を情報トーンに（「管理者の判断が必要なコースはありません。
  体制上避けられない連続 N 件は理由つきで確定済みです」）。
- toast: 警告トーンをやめ、`成功: 自動スタッフ割当が完了しました（確定 X 件・うち不可避連続 N 件）`
  ＋ レビュー必要時のみ warning を維持。
- 週次ガイド Step 3 に不可避連続の説明を 1 文追加（事前の納得形成 = PO 指示 2(c)）。

## 影響とリスク

- 不可避連続が自動確定になるため、**従来レビューで「あえて確定しない」選択をしていた運用**が
  あれば挙動変更になる（PO 指示 1(a) により許容）。確定後の手動変更（担当 dropdown）は従来どおり可能。
- 判定の保守性: 代替候補の検査はハード制約の再評価。`_cost_single_cell` と判定基準がずれると
  誤分類する — 制約判定は既存関数（`_sex_satisfies_restrictions` / `effective_office_for_weekday` 等）を
  必ず再利用し、コピーしない（正規化ルール N 系に従う）。
