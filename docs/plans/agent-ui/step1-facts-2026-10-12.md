# 第 1 部 事実

## 1. 認証（鍵）

### 1-1. 仕組み
- JWT（HS256）。クレームは `{sub, role, staff_id, type, iat, exp}`。`backend/app/core/security.py:41-58`、発行 `create_access_token` `:61-80`、検証 `decode_token` `:102-105`。
- 寿命: access 3600 秒・refresh 30 日（`backend/app/core/config.py:41-42`）。`create_access_token(ttl_seconds=…)` で任意の寿命を出せる（`security.py:66,77`）。
- `get_current_user`: Bearer を decode → `type` が access（または無し）→ `sub` の User を DB から引く（`backend/app/core/deps.py:36-89`）。**失効の仕組みは無い**（jti・token_version・拒否リストなし）。ログアウトはサーバー側で何もしない（`backend/app/api/v1/auth.py:184-186`「stateless JWT」）。
- `require_role("admin")`: **DB の `users.role`** で判定（トークンの role クレームではない）。旧 manager は admin 扱いに正規化（`deps.py:116-137`、判定 `:130`）。`get_current_active_user` が `deleted_at` を見る（`deps.py:95-110`）→ ユーザーを論理削除すればその人の鍵は効かなくなる（ただし require_role を通る経路のみ。`CurrentUser` 直の経路は deleted を見ない `deps.py:83-89`）。
- 取り消す手段は実質 2 つだけ: ① `JWT_SECRET` を変える（全員ログアウト）② ユーザーを消す。
- ログイン系だけレート制限（`auth.py:57-58`）。他は `allocate`（`allocate.py:261` 3/分）・`diff`（`diff.py:30` 5/分）程度で、一般の読み書きには制限なし。

### 1-2. 既存の「サービス用の鍵」
- cron 用 `ADMIN_TOKEN`: 管理者のアクセストークンを**10 年寿命**で手発行し、VPS の `carelink-cron` ユーザーの `~/.secrets/carelink.env` に置いて curl で叩く（`docs/plans/qr-checkin-HANDOFF.md:38,42-43`。例 `backend/app/api/v1/admin_geocoding.py:3-6`）。同 HANDOFF `:53` に「理想は scoped service account / API キー（アプリ改修）」と残課題。
- 週のならしの反映 `W_TOKEN`: サーバー内で `docker exec carelink-backend python -c "create_access_token(subject=<user id>, role='admin', staff_id=…, ttl_seconds=3600)"` で 1 時間の鍵を出す（`docs/tools/week-leveling/apply/generic/README.md:27`）。`apply.py` は環境変数で受け取る（`apply/generic/apply.py:7`）。
- **API キー／PAT（個人用の鍵）のモデル・テーブル・エンドポイントは存在しない**（`api_key` の語はリダクト一覧 `middleware/audit.py:92` と Google Maps 鍵 `config.py:45` だけ）。

### 1-3. 監査ログ
- ミドルウェア `AuditLogMiddleware`: `/api/v1` 配下の **POST/PUT/PATCH/DELETE だけ**を記録（GET は記録しない）（`backend/app/middleware/audit.py:52,305-313`）。
- 記録内容: actor_user_id・role（Bearer をその場で decode。失敗なら NULL `audit.py:216-231`）、method・path・status・latency・IP（X-Forwarded-For の先頭）・User-Agent・**リダクト済みの本文**（パスワード／token は全消し、氏名・住所・電話・メールは一部伏せ `audit.py:80-101,155-181`、8 KiB 超は `_truncated` `:106,387-388`）（組み立て `audit.py:394-407`）。
- 書き込みは応答の後に fire-and-forget（失敗しても API は止まらない）（`audit.py:250-281,411-414`）。
- テーブル `audit_logs`（`backend/app/models/audit_log.py:23-62`）。手書きの before/after 列もあり（例: unassign-all-staff が件数を after に書く `api/v1/schedule_v2.py:3180-3192`）。
- 読む API: `/api/v1/audit-logs`（admin）（`api/v1/__init__.py:192`）。
- **「誰の操作か」は分かるが「エージェント経由か」は区別できない**（区別に使えるのは User-Agent だけ）。JWT 以外の鍵を足すと `_decode_actor` が読めず actor が NULL になる。

### 2-2. お休みを書くエンドポイント
- `POST /staff/{id}/overrides`（admin）: override 1 行を作るだけ。**訪問・コースには触れない**（`api/v1/staff_overrides.py:181-209`）。PATCH `:212-262`・DELETE `:265-`（削除時に本人へ取消通知）。op_log には**記録されない**。

- **`POST /schedule/v2/staff-off-week`（「🛌 休みにする」・今週の運転席）**（`api/v1/schedule_v2.py:1818-` 、要求/応答 `schemas/v2/auto_schedule_v2.py:699-740`）:
  - 入力 `{staff_id, date, to_staff_id|null, acknowledge_constraint_warnings, op_group_id}`。
  - 1 トランザクションで: override(off) を upsert／その日その人が載っている **planned** 訪問の「本人の枠」だけを `to_staff_id` へ（primary・相方枠 VSA の両方を拾う）／その日のコース担当を `to_staff_id` へ／その日の固定イベントに取消印（docstring `schedule_v2.py:1829-1862`）。
  - **引き受け先は 1 人だけ**（または全部「担当なし」）。複数人へ振り分ける機能ではない。
  - ガード: 過去日 422（JST）・青ピンあり 422・引き受け先が新人／退職／本人／その日休みなら 422・NG/性別は `constraint_confirmation_required` 422 → acknowledge で再送（`schedule_v2.py:1856-1916`）。打刻済み等は据え置いて `skipped_visit_ids` で返す。
  - op_log に `set_staff_off`・`set_visit_staff_slot`・`set_course_staff`・`cancel_staff_event` を**同じ op_group で strict 記録** → 「戻る」1 回で休みごと戻る（`services/op_log_service.py:37-50,177-181`）。
- **`POST /schedule/v2/substitute-candidates`（急休の代替候補・read-only）**（`api/v1/substitute_candidates.py:39-67`）: 休む人×日 → コースごとの候補職員を ◎/△/× と理由・score・その日の件数付きで返す（応答 `schemas/substitute.py:102-200`、`whole_ok_staff_ids` = 1 人で全部引き受けられる人）。`/v2/assign-candidates`（`:70-`）は「担当なし」への投入候補。
- 画面側: `frontend/components/schedule/v2/cockpit/SubstitutePanel.tsx`・`lib/queries/cockpit.ts`。

### 2-3. 休みにしたとき訪問はどうなるか
- override だけ（`/overrides`・申請承認）: 訪問は**そのまま元の担当に残る**。プールには行かない。エンジン（自動割当）は off を勤務外として読む（`services/scheduling/auto_allocator_v2.py:3513-3524`）が、既存の訪問を動かすのは別操作。
- staff-off-week: 担当を 1 人へ付け替え、または担当なしへ（プールには行かない＝訪問は残り、担当が空になる）。
- 週のならしの「入らない訪問」は `DELETE /visits/{id}` で論理削除＝保留プールへ（「今週だけ取消」はプールに出ないので使わない）（`apply/generic/README.md:15`）。

## 5. ソルバーをサーバー側で動かす

- **ortools は backend の依存に入っていない**（`backend/pyproject.toml:10-29`、`requirements.txt`・`uv.lock` に無し）。今は手元で `uv run --with ortools --with openpyxl` (`docs/tools/week-leveling/README.md` 「実行」)。
- 計算: 1 日ずつ配車問題（`solver.py:19` pywrapcp、`:505-515` PARALLEL_CHEAPEST_INSERTION＋GUIDED_LOCAL_SEARCH、`time_limit = seconds`）。昼休み 45 分で解いて入らない日は 30 分で解き直し（`solver.py:25,582-589`）→ **1 日あたり seconds〜2×seconds**。既定 30 秒（`level.py:94`）、運用は 60〜120 秒・並列にすると結果が揺れる（README「試算のこつ」）。1 日だけなら `--day`。実行時間・メモリの実測値はリポジトリに無い。
- extract.py の SQL は 1 本の `json_build_object`（`extract.py:16-82`）。読み取り専用トランザクションで流している（`:96-99`）→ そのまま SQLAlchemy の `text()` に移せる形。
- 本番の backend は **uvicorn 1 プロセス**（`backend/Dockerfile:58`、`--workers` なし）。CPU を数十秒使う計算をイベントループ上で回すと API 全体が止まる。既存の重い同期処理は `run_in_executor` を使う例がある（`api/v1/allocate.py:331`）。
- VPS: 4 vCPU・8 GB・**swap 0**・OOM killer（`docs/plans/visit-voice-record-design-2026-09-17.md:26,82`、`docs/deployment/vps-state-snapshot.md:112-113`）。backend の mem_limit は未設定。TZ=UTC が前提（`backend/Dockerfile:23-29`）。
