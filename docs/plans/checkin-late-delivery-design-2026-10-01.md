# 圏外で退避した QR 打刻を、読み取った日の訪問へ遅れて届ける（2026-10-01）

PO 承認済み（2026-10-01）。マイグレーションなし。

## 1. 問題

- 圏外で読んだ QR 打刻は、スマホの退避キュー（`frontend/lib/checkin-queue.ts`・localStorage）に入る。電波が戻ったら、読んだ瞬間の `device_time`（`payload.at`）をつけて送り直す。
- サーバの判定（`judge._guard_visit`）は「受信した日（JST）の訪問だけ」を受け付けていた。夜に圏外で読み、翌朝に届いた打刻は 409 になった。
- スマホは 4xx の控えを破棄する。そのため、その訪問の記録は二度と戻らなかった。
- 予定外訪問（`adhoc-checkin`）も、`device_time` が今日でなければ 422 で同じように失われた。

## 2. 決めたこと

| 項目 | 内容 |
|---|---|
| 訪問の日付 | `device_time` が妥当なら、その JST の日付（＝読み取った日）で決める。 |
| 受付の期限 | 読み取りから **72 時間**。`actuals.LATE_DELIVERY_MAX_AGE`（モジュール定数）。 |
| 期限切れ | 409 を返す。文言は「読み取りから 3 日を過ぎたため送信できません。管理者に連絡してください」。予定外訪問は 422 で同じ文言。スマホは理由つきで破棄して知らせる（従来どおり）。 |
| 今日でも読み取った日でもない | 409「この訪問は今日の予定ではないため記録できません」。英語の文言から日本語にした。スマホはこの文をそのまま見せる。 |
| 予定外訪問 | 読み取った日に作る。`visit_date` と `start_time` は `device_time` から決める。 |
| 「遅れて届いた」の表示 | `scanned_at` と `device_time` から導く（列は足さない）。表示する場所は §4。 |

`checkin_settings` には 72 時間に当たる列がない。今回は列を足さないため、モジュール定数にした。将来は設定の候補にする（`staff_adjust_window_days` などと同じ並びに置く想定）。

## 3. 規則（ここだけが正）

### 3-1. 読取時刻 `actuals.resolve_read_time(device_time, scanned_at, visit_date)`

`device_time` を採るのは、次の 2 つをどちらも満たすときだけ。それ以外は `scanned_at` を採る。

1. **範囲**（`device_time_in_window`）: `scanned_at − 72h ≤ device_time ≤ scanned_at + 120 秒`
2. **日付**: `device_time` の JST の日付が、**受信日**か**訪問日**（`visit_date`）のどちらかと同じ

- 以前の条件は「18 時間以内」かつ「受信日と同じ」だった。
- 日付の条件を「受信日**または**訪問日」にしたので、過去の打刻の読み方は変わらない。過去の打刻は受信日＝訪問日だったため。
- 例外が 1 つある。取込で訪問日が動いた訪問では、前と同じく `scanned_at` を採る。
- `load_actuals` は打刻と訪問日を一緒に引く（JOIN）。訪問詳細・一覧・モニター・未訪問の検知・打刻履歴・Excel・A4・通知は、すべてこの関数を通る。

### 3-2. 打刻できる訪問 `judge._guard_visit(visit, now, device_time)`

次のどちらかなら受け付ける（削除済み・取消済みは従来どおり 409）。

- **受信した日の訪問**: これまでと同じ。`device_time` が無い、またはおかしい場合もここで判定する。
- **読み取った日の訪問**: `device_time` が 3-1 の範囲内にあり、その JST の日付が `visit_date` と同じ。

### 3-3. 予定外訪問 `visits._adhoc_visit_moment`

- `device_time` が 72 時間より古ければ 422。
- それ以外は `resolve_read_time(dt, now, min(dt, now) の日付)` で基準の時刻を決める。
- 進んだ時計（120 秒以内）が日付をまたいでも、受信日より先の日には訪問を作らない。
- advisory lock のキーと二重生成ガードは、**読み取った日**で組む（`read_day`）。

## 4. 「遅れて届いた」の目安と表示

`actuals.late_received_at(device_time, scanned_at, visit_date)` は、次の両方を満たす打刻について**受信時刻**を返す。

- 読取時刻に `device_time` を採った
- 受信が読み取りから **30 分を超えた**、または **JST の日付をまたいだ**

`device_time` を採らなかった打刻は「遅れていない」扱いになる。

目安を 30 分にした理由:

- 普段の打刻は、読み取りから受信まで数秒で届く。
- 地下や山間で数分つながらないくらいは、遅れとして目立たせない。
- 日付をまたいだ打刻は、時間の長さに関係なく必ず遅れとして出す。前日の訪問へ付いたことが分かるように。

フロントの `LATE_DELIVERY_MARK_AFTER_MIN = 30` は、この目安と同じ値にしている。

| 場所 | 出し方 |
|---|---|
| API | `VisitRead.actual_{arrival,departure}_late_received_at`、`MonitorVisit.{arrival,departure}_late_received_at`、`VisitHistoryItem.{arrival,departure}_late_received_at` |
| 訪問モニターの詳細 | 「到着の記録／退出の記録　遅れて届いた（9/30 8:30 受信）」。注意色にはしない。 |
| 打刻履歴の一覧 | 備考の札「遅れて届いた」（灰色）。全文は title に出す。 |
| 打刻履歴の詳細 | 到着・退出の欄の注記と、備考。 |
| 打刻履歴の Excel・A4 | 備考に「遅れて届いた（9/30 8:30 受信）」。到着と退出が別の時刻に届いたときは「到着が…」「退出が…」の 2 つ。同じ分に届いたときは「到着・退出が…」の 1 つ。「読み方」にも説明を足した。 |
| スマホの訪問詳細 | 実績の下の補足に「遅れて届いた（9/30 8:30 受信）」。 |
| スマホの再送 | 届いた控えのうち遅れたものを数え、トーストで知らせる。例「遅れて届いた記録を 1 件送信しました／9/29 18:45 に読み取った記録は、読み取った日の訪問に保存しました」。前日の訪問は今日の一覧に出ないため、どこへ入ったかを伝える。 |

文言では「直す・修正・補正」を使わない（テストで確かめている）。

## 5. 安全と、すでに動いている処理との関係

- **端末の時計が進んでいる**: 120 秒を超えて進んだ `device_time` は採らない。受信日の訪問なら受信時刻で記録する。明日の訪問には付けない。
- **端末の時計が遅れている**:
  - 1 日遅れた時計で今日の訪問を読んだ場合は、従来どおり受け付ける（受信日の訪問なので）。読取時刻は受信時刻になる。日付が訪問日とも受信日とも違うためで、記録を失わない。
  - 72 時間を超えて古い時刻は採らない。
- **位置（GPS）**:
  - 退避の控えには、読んだ時点の `lat/lng/accuracy` が入っている（`[visitId]/page.tsx` の `coordsOf(geo)`、`/q` も同じ）。
  - 再送ではそのまま送る（vitest で確かめている）。サーバは従来どおり、その座標で位置を判定する。
- **状態の移り変わり**:
  - 前日の訪問へ遅れて届いた退出も、`in_progress` を `completed` にする。
  - 予定外訪問の `end_time` は、その日の読取時刻へ合わせる（`checkin_read_at(checkin, visit.visit_date)`）。
- **同住所ペア**: モニターは読み取った日の訪問で組む。実績時刻は読み取った日の時刻なので、ペアの判定はそのまま動く。
- **通知**（場所違い・代行・予定外・NG）:
  - 遅れて届いた場合も**止めない**。管理者が後からでも知るべき事実だから。
  - 本文の時刻は「9/29 18:45（遅れて届いた）」のように、読み取った日を添える。
  - 未訪問の通知は、到着が届いたら従来どおり消す（その訪問は実際に行われていたため）。
- **時刻の調整**:
  - `_require_read_on_visit_date` は、読取時刻が訪問日に入るので通る。
  - スタッフが合わせられる期間（7 日）は `visit_date` 基準。前日の訪問はこの期間に入る。
  - 退出の「いまより後にはできない」は、今日の訪問だけに効く。
- **同じ読み取りの再送**:
  - 打刻は従来どおり追記型で、行は増える。`device_time` が同じなら同じ読み取りとして扱う（`_is_resend`）。
  - 先に入れた調整は効いたままで、実績・状態も変わらない。
  - 予定外訪問は、読み取った日の進行中の訪問へ追記する（2 本目を作らない）。
- **スマホの今日の一覧**: 前日の訪問へ付いた打刻は、今日の一覧（`visit_date` = 今日）に混ざらない（テストで確かめている）。

## 6. 端のケース

| ケース | 結果 |
|---|---|
| 23:50 に読み、0:05 に届いた（15 分） | 前日の訪問へ付く。日付をまたいだので「遅れて届いた」。 |
| ちょうど 72 時間後に届いた | 受け付ける。72 時間を 1 秒でも過ぎたら 409（予定外は 422）。 |
| `device_time` 無しで翌日に届いた | 409「この訪問は今日の予定ではないため記録できません」。 |
| 予定外訪問の到着と退出を圏外で読んだ | 退出は訪問 ID が必要。到着が届くまで退出は読めないので、この組み合わせは起こらない。 |

## 7. 残っていること（今回は扱わない）

- 72 時間を `checkin_settings` の列にする（マイグレーションが要るので見送った）。
- 予定外訪問で、到着が届き、退出まで済んだ（完了）あとに、到着の**同じ読み取り**が応答の消失で再送された場合。二重生成ガードは「進行中」だけを見るので、もう 1 本作られうる（従来から同じ）。
- 訪問詳細を開いたまま日付をまたぎ、0 時すぎに通信がつながった状態で QR を読んだ場合。前日の訪問は従来どおり 409 になり、スマホは「別の利用者の QR」の流れに入る（従来から同じ）。
