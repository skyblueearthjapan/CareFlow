# 圏外で退避した QR 打刻を、読み取った日の訪問へ遅れて届ける（2026-10-01）

PO 承認済み（2026-10-01）。マイグレーションなし。

## 1. 問題

- 圏外で読んだ QR 打刻は、スマホの退避キュー（`frontend/lib/checkin-queue.ts`・localStorage）に入る。電波が戻ったら、読んだ瞬間の `device_time`（`payload.at`）をつけて送り直す。
- サーバの判定（`judge._guard_visit`）は「受信した日（JST）の訪問だけ」を受け付けていた。夜に圏外で読み、翌朝に届いた打刻は 409 になった。
- スマホは 4xx の控えを破棄する。そのため、その訪問の記録は二度と戻らなかった。
- 予定外訪問（`adhoc-checkin`）も、`device_time` が今日でなければ 422 で同じように失われた。

## 2. 決めたこと

| 項目 | 内容 |
|---|---|
| 訪問の日付 | `device_time` が妥当なら、その JST の日付（＝読み取った日）で決める。 |
| 受付の期限 | 読み取りから **72 時間**。`actuals.LATE_DELIVERY_MAX_AGE`（モジュール定数）。 |
| 期限切れ | 409 を返す。文言は「読み取りから 3 日を過ぎたため送信できません。管理者に連絡してください」。予定外訪問は 422 で同じ文言。スマホは理由つきで破棄して知らせる（従来どおり）。 |
| 今日でも読み取った日でもない | 409。過去の訪問は「この訪問は昨日（9/29）の予定のため、今日は記録できません。管理者に連絡してください」（2 日以上前は「9/27 の予定のため…」）。今日より後の訪問は「この訪問は今日の予定ではないため記録できません」。英語の文言から日本語にした。スマホはこの文をそのまま見せる。 |
| 断るときの code | 打刻を断る 4xx は `{"detail": 文言, "code": コード}` を返す（`judge.CheckinRejected`・`main.py` の handler）。`wrong_patient`（別の利用者の QR）・`not_visit_day`・`late_expired`・`cancelled`・`deleted`。detail の文言は従来どおり。 |
| 予定外訪問 | 読み取った日に作る。`visit_date` と `start_time` は `device_time` から決める。 |
| 「遅れて届いた」の表示 | `scanned_at` と `device_time` から導く（列は足さない）。表示する場所は §4。 |

`checkin_settings` には 72 時間に当たる列がない。今回は列を足さないため、モジュール定数にした。将来は設定の候補にする（`staff_adjust_window_days` などと同じ並びに置く想定）。

## 3. 規則（ここだけが正）

### 3-1. 読取時刻 `actuals.resolve_read_time(device_time, scanned_at, visit_date)`

`device_time` を採るのは、次の 2 つをどちらも満たすときだけ。それ以外は `scanned_at` を採る。

1. **範囲**（`device_time_in_window`）: `scanned_at − 72h ≤ device_time ≤ scanned_at + 120 秒`
2. **日付**: `device_time` の JST の日付が、**受信日**か**訪問日**（`visit_date`）のどちらかと同じ

- 以前の条件は「18 時間以内」かつ「受信日と同じ」だった。
- 日付の条件を「受信日**または**訪問日」にしたので、過去の打刻の読み方は変わらない。過去の打刻は受信日＝訪問日だったため。
- 例外が 1 つある。取込で訪問日が動いた訪問では、前と同じく `scanned_at` を採る。
- 18 時間を 72 時間へ延ばしたことで読み方が変わりうるのは、「同じ日のうちに、読み取りから 18〜24 時間後に届いた打刻」だけ。本番のデータでこの打刻は **0 件** だった（2026-10-01 確認）。過去の実績時刻は変わらない。
- `load_actuals` は打刻と訪問日を一緒に引く（JOIN）。訪問詳細・一覧・モニター・未訪問の検知・打刻履歴・Excel・A4・通知は、すべてこの関数を通る。

### 3-1b. どの打刻を採るか・どの調整が効くか（`actuals._resolve_kind` / `load_actuals`）

- **kind ごとの最新**は、**読み取った瞬間**（読取時刻）が最も新しい打刻にする。受信の順ではない。圏外で退避した古い読み取りが後から届いても、その後にオンラインで読んだ新しい読み取りを上書きしない。読取時刻が同じ（同じ読み取りの再送）なら受信の新しい方。`latest_checkin`（kind を問わない生の最新）は受信順のまま。
- **調整が効くか**は、調整を作った時刻と、最新の打刻を**読んだ瞬間**を比べる（以前は打刻の `created_at` = 受信時刻と比べていた）。調整より後に読み直した打刻だけが調整を無効にする。
  - 例: 9/29 19:30 に圏外で退出を読む → 9/30 8:00 に管理者が退出を 19:20 と手で入れる → 9/30 8:30 に 19:30 の読み取りが届く。読んだのは調整より前なので、退出の実績は 19:20（調整）のまま。読取時刻 19:30 と「遅れて届いた」は残る。
  - 読取時刻は受信時刻を上限にして比べる（進んだ時計で、同じリクエストで同梱した調整を消さない）。
  - 同じ読み取りの再送（`device_time` が同じ）は、従来どおり読み直しに数えない。

### 3-2. 打刻できる訪問 `judge._guard_visit(visit, now, device_time)`

次のどちらかなら受け付ける（削除済み・取消済みは従来どおり 409）。

- **受信した日の訪問**: これまでと同じ。`device_time` が無い、またはおかしい場合もここで判定する。
- **読み取った日の訪問**: `device_time` が 3-1 の範囲内にあり、その JST の日付が `visit_date` と同じ。

### 3-3. 予定外訪問 `visits._adhoc_visit_moment`

- `device_time` が 72 時間より古ければ 422。
- それ以外は `resolve_read_time(dt, now, min(dt, now) の日付)` で基準の時刻を決める。
- 進んだ時計（120 秒以内）が日付をまたいでも、受信日より先の日には訪問を作らない。
- advisory lock のキーと二重生成ガードは、**読み取った日**で組む（`read_day`）。
- **同じ読み取りの再送**: lock の中、二重生成ガードの前で、同じスタッフ・同じ患者の予定外訪問に、同じ `device_time` の到着があるかを見る。あればその訪問の応答をそのまま返し、何も足さない。応答が消えたあとに退出で完了した訪問でも 2 本目を作らない（二重生成ガードは進行中しか見ないため）。DB の一意制約は付けない（マイグレーションが要るので見送った）。

### 3-4. スマホが 409 を受けたとき（`[visitId]/page.tsx`）

- `code == "wrong_patient"` のときだけ「別の利用者の QR」の流れ（代行／予定外の記録）へ進む。code を返さない旧 BE は、従来の英語の detail で見分ける。
- それ以外の 409（訪問日でない・期限切れ・取消・削除）は「この訪問には記録できません」とサーバの文言を出して止める。予定外の記録へは進めない。
- 訪問の画面を開いたまま日付をまたぎ、0 時すぎに通信がつながった状態で前日の訪問の QR を読んだ場合も、サーバの受け付けは広げない。「この訪問は昨日（9/29）の予定のため、今日は記録できません。管理者に連絡してください」を出す。
- 再送キューで破棄した控えにも code を添える（`DroppedPending.code`）。

## 4. 「遅れて届いた」の目安と表示

`actuals.late_received_at(device_time, scanned_at, visit_date)` は、次の両方を満たす打刻について**受信時刻**を返す。

- 読取時刻に `device_time` を採った
- 受信が読み取りから **30 分を超えた**、または **JST の日付をまたいだ**

`device_time` を採らなかった打刻は「遅れていない」扱いになる。

目安を 30 分にした理由:

- 普段の打刻は、読み取りから受信まで数秒で届く。
- 地下や山間で数分つながらないくらいは、遅れとして目立たせない。
- 日付をまたいだ打刻は、時間の長さに関係なく必ず遅れとして出す。前日の訪問へ付いたことが分かるように。

遅れたかどうかは**サーバだけが決める**。フロントは応答の `*_late_received_at` を表示するだけで、端末の時計では判定しない（スマホの再送の案内も応答で決める）。

| 場所 | 出し方 |
|---|---|
| API | `VisitRead.actual_{arrival,departure}_late_received_at`、`MonitorVisit.{arrival,departure}_late_received_at`、`VisitHistoryItem.{arrival,departure}_late_received_at` |
| 訪問モニターの詳細 | 「到着の記録／退出の記録　遅れて届いた（9/30 8:30 受信）」。注意色にはしない。 |
| 訪問モニターの要対応 | 前日以前の訪問へ遅れて届いた打刻は、位置・時間が正常でも最低「要確認」（`compute_alert(late_to_earlier_day=True)`）。要対応トレイに載り、「確認済み」で消える。**受信より前の「確認済み」は効かない**（まだ届いていない記録を確認したものではないため）。場所 要確認・位置なし・場所違いの到着が遅れて届いた場合も、同じ理由で必ずトレイに戻る。 |
| 打刻履歴の一覧 | 備考の札「遅れて届いた」（灰色）。全文は title に出す。絞り込み「遅れて届いた」（`state=late`）。Excel・A4 も同じ絞り込みで出る。 |
| 打刻履歴の詳細 | 到着・退出の欄の注記（調整してあっても「調整後（読取 13:06）・遅れて届いた（…）」と添える）と、備考。 |
| 打刻履歴の Excel・A4 | 備考に「遅れて届いた（9/30 8:30 受信）」。到着と退出が別の時刻に届いたときは「到着が…」「退出が…」の 2 つ。同じ分に届いたときは「到着・退出が…」の 1 つ。未訪問の記録が遅れて届いたときは「未訪問の記録が遅れて届いた（…）」。「読み方」にも説明を足した。 |
| スマホの訪問詳細 | 実績の下の補足に「遅れて届いた（9/30 8:30 受信）」。 |
| スマホの再送 | 届いた控えのうち、応答の `*_late_received_at` があるものを数え、トーストで知らせる。例「遅れて届いた記録を 1 件送信しました／9/29 18:45 に読み取った記録は、読み取った日の訪問に保存しました」。前日の訪問は今日の一覧に出ないため、どこへ入ったかを伝える。破棄の通知を先に出す。 |

文言では「直す・修正・補正」を使わない（テストで確かめている）。

## 5. 安全と、すでに動いている処理との関係

- **端末の時計が進んでいる**: 120 秒を超えて進んだ `device_time` は採らない。受信日の訪問なら受信時刻で記録する。明日の訪問には付けない。
- **端末の時計が遅れている**:
  - 1 日遅れた時計で今日の訪問を読んだ場合は、従来どおり受け付ける（受信日の訪問なので）。読取時刻は受信時刻になる。日付が訪問日とも受信日とも違うためで、記録を失わない。
  - 72 時間を超えて古い時刻は採らない。
- **位置（GPS）**:
  - 退避の控えには、読んだ時点の `lat/lng/accuracy` が入っている（`[visitId]/page.tsx` の `coordsOf(geo)`、`/q` も同じ）。
  - 再送ではそのまま送る（vitest で確かめている）。サーバは従来どおり、その座標で位置を判定する。
- **状態の移り変わり**:
  - 前日の訪問へ遅れて届いた退出も、`in_progress` を `completed` にする。
  - 予定外訪問の `end_time` は、その日の読取時刻へ合わせる（`checkin_read_at(checkin, visit.visit_date)`）。
- **同住所ペア**: モニターは読み取った日の訪問で組む。実績時刻は読み取った日の時刻なので、ペアの判定はそのまま動く。
- **通知**（場所違い・代行・予定外・NG）:
  - 遅れて届いた場合も**止めない**。管理者が後からでも知るべき事実だから。
  - 本文の時刻は「9/29 18:45（遅れて届いた）」のように、読み取った日を添える。
  - 未訪問の通知は、到着が届いたら従来どおり消す（その訪問は実際に行われていたため）。
  - ただし前日以前の訪問へ遅れて届いた到着では、黙って消さない。代わりに「前日以前の訪問に到着が遅れて届きました」を管理者へ残す（`notify_checkin_late_arrival`）。本文は「利用者名（看護師名）読み取り 9/29 18:45・受信 9/30 8:30」。冪等キーは `reference_type = checkin_late_arrival`（種別＋到着）と `reference_id = visit.id`。同じ日のうちに届いた打刻（30 分超でも）は出さない。
- **時刻の調整**:
  - `_require_read_on_visit_date` は、読取時刻が訪問日に入るので通る。
  - スタッフが合わせられる期間（7 日）は `visit_date` 基準。前日の訪問はこの期間に入る。
  - 退出の「いまより後にはできない」は、今日の訪問だけに効く。
- **同じ読み取りの再送**:
  - 打刻は従来どおり追記型で、行は増える。`device_time` が同じなら同じ読み取りとして扱う（`_is_resend`）。
  - 先に入れた調整は効いたままで、実績・状態も変わらない。
  - 予定外訪問は、同じ読み取りなら既にある訪問の応答を返し、何も足さない（§3-3）。
- **スマホの今日の一覧**: 前日の訪問へ付いた打刻は、今日の一覧（`visit_date` = 今日）に混ざらない（テストで確かめている）。

## 6. 端のケース

| ケース | 結果 |
|---|---|
| 23:59:59 に読み、0:00:00 に届いた（1 秒） | 前日の訪問へ付く。日付をまたいだので「遅れて届いた」。0:00:00 に読んだものは今日の訪問で、前日の訪問には付かない（409 `not_visit_day`）。 |
| 端末の時計が 120 秒進んでいる / 121 秒進んでいる | 120 秒までは読取時刻に採る。121 秒は採らず受信時刻。 |
| ちょうど 72 時間後に届いた | 受け付ける。72 時間を 1 秒でも過ぎたら 409 `late_expired`（予定外は 422 `late_expired`）。 |
| `device_time` 無しで翌日に届いた | 409 `not_visit_day`「この訪問は昨日（9/29）の予定のため、今日は記録できません。管理者に連絡してください」。 |
| 予定外訪問の到着と退出を圏外で読んだ | 退出は訪問 ID が必要。到着が届くまで退出は読めないので、この組み合わせは起こらない。 |
| 未訪問（no_show）の記録が遅れて届いた | 読み取った日の訪問へ付く（到着・退出と同じ判定）。打刻履歴の備考に「未訪問の記録が遅れて届いた（…）」。 |

## 7. 残っていること・しないこと

- **マイグレーションはしない**: 列も索引も足さない。「遅れて届いた」は `scanned_at` と `device_time` から導く。予定外の再送の一意制約（部分 UNIQUE）も、マイグレーションが要るので付けず、§3-3 のアプリ側の確認だけにした。
- 72 時間を `checkin_settings` の列にする（マイグレーションが要るので見送った・将来の設定候補）。
