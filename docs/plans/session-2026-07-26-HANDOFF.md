## 2. 気になる点（次のエージェントがハマりそうな所）★必読

1. **冪等キーは複合** `{個別業務ID}:{職員内部ID}:{日付}`。個別業務IDは週パターン由来で複数日同一（実測）。
   単独IDをキーにすると2日目が消える
2. **手動イベント(source='manual')不可侵**・取り込みが管理するのは source='kaipoke' のみ。
   staff_events の**手動編集API(PATCH)は start>=end を422拒否**→取り込んだ📝メモは画面から編集不可（仕様・編集はカイポケで）
3. **置換の実績ガード**: 打刻が1件でもある週は置換422→差分モードへ誘導。本稼働後の毎週の追いかけは差分モードが主力
4. **テンプレ単位ビューの臨時合算は理論上残存**: 臨・臨2…が同日に複数あると週リスト/日タイムラインの
   「臨時」枠に合算表示される（帰属はコード'臨'のコース担当者）。コース新設改修で実質1本/日になり顕在化しないが、
   7人以上稼働などで再発し得る。恒久対応=コース枠ビューのcourse単位表示リファクタ（バックログ）
5. **カイポケ画面DOM依存**: `btnIndividual`クラス・`showIndividualEdit`引数・`staffSchedule`のフォーム構造。
   カイポケ改修で壊れたら fail-fast する設計（0件+btnIndividual存在→エラー / day二重検証）
6. **イベント取得 ~90s は Cloudflare 100s 制限に近い**。524が出たら export と同じ async+ポーリング化（設計書§7）
7. **差分モードの月跨ぎ週**は現況CSVが月単位のため週後半（翌月分）がキャンセル候補に見える既知制限
   （置換モードは両月取得で対応済み）。月末週は置換推奨 or 大量キャンセル警告で人が止まる
8. **RPAはVPS上の別リポジトリ** `/root/PlaywrightTest1`（コンテナにbindマウント・デプロイ=ファイル編集+`docker restart kaipoke-api`）。
   本体と同期しない
9. **髙梨さんのstaff名はDB上「髙梨桂子」（空白なし）**。名寄せは正規化で吸収するが、表示で他スタッフと形式が違う
10. 稼働状況ラベル辞書（JobProgressCard.COMMAND_LABELS）に新RPAオペを足し忘れると英語名がそのまま出る
11. 置換で新設したコース行は `note='カイポケ置換取込によるコース新設'`・臨時は `template_id=臨時テンプレ`。
    週再生成(週を生成/固定枠に戻す)との相互作用は**未検証**（置換週に再生成をかける運用は想定外だが操作は可能）

## 6-b. ★次の実装テーマ（PO合意済みの方向性・セッション末尾で設計相談済み）

**「差分/置換の自動判別（日単位ハイブリッド取り込み）」** — モード選択UIを廃止し、
ボタン1つで完結させる。POの想定シナリオ: 水曜に取り込み → 月火は実稼働済み(打刻あり)、
水〜土は未稼働。

設計合意（本セッション最終相談・実装は次セッション）:
1. **判別信号 = `visit_checkins` の日別有無**（実績ガードの週判定を日単位に細分化するだけ）
   - 打刻あり日 → 差分適用（既存の `days` パラメータで日単位適用は実装済み）
   - 打刻なし日 → 置換適用（コース計画は既にセル=曜日×拠点単位。白紙化を指定日に絞る）
   - イベント → 従来どおり週全体 upsert（モード無関係）
2. **CSV取得を一本化**: export 1回の結果を差分計算と置換計画の両方に渡す（現状は別々に取得）
3. UI: ❶取得→❷統合プレビュー（日ごとに「🔒実績あり=差分」「置換」バッジ+件数）→❸実行。
   確認ダイアログの削除警告文言は置換対象日にだけ表示。モード選択トグルは撤去
4. 既存の安全装置（ゲート/実績ガード/空CSV拒否/大量キャンセル警告/冪等）は全て内包
5. 部分打刻の日は安全側=差分（日単位判定で自然にそうなる）

工数感: BE 1セッション（日単位化+統合エンドポイント+テスト）+ FE 半セッション。
技術的難所なし——一番の作業は取得一本化のリファクタ。

## 6. 次の実装相談に備えて

POは「予定のおかしな点を1つずつ相談する」モードで進めている。直近の流れ:
1枠15件→コース付替で解消 → 誤帰属→帰属修正 → 9名枠→コース新設 → （未割当）表示→select修正。
**次も同様に「スクショ+症状」が来る可能性が高い。** 調査の型:
1. まず本番DBを実測（`ssh root@72.60.211.213 'docker exec carelink-postgres psql -U carelink -d carelink -c "..."'`）
   — 表示問題かデータ問題かを最初に切り分ける
2. データ問題なら置換ロジック（replace_inbound.py）・表示問題ならテンプレ単位ビューの合算/帰属を疑う
3. 修正→テスト→デプロイ（frontendのみなら build frontend で3分・migrationなければ --no-cache 不要）
4. **置換は冪等** — データ側の修正は「再実行してもらう」だけで反映できる
