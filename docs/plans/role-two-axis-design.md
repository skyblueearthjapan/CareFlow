# ロール二軸分離の設計 — アカウント権限「管理者/一般」× 業務ロール「スタッフ/マネージャー」

PO 決定 2026-08-09。実装前設計。

## 0. 決定事項（PO の言葉）

1. **アカウント権限は「管理者」と「一般」の 2 段階に統一**。admin と manager の
   区別は廃止。編集権限の差は「今の admin と staff の差と同じでいい」
   （= 一般はほぼ編集不可・閲覧中心）。
2. **スタッフマスタ側は業務ロール「スタッフ」「マネージャー」**として呼び分ける
   （エンジン専用。アカウント権限とは無関係)。
3. 「role = システム権限」等の**紛らわしい記述はすべて調査して直す**。

## 1. 現状（調査結果の要約・2026-08-09 時点）

- ロールは既に 2 つの独立した実体:
  - `users.role` (admin/manager/staff) — API の require_role だけが読む
  - `staff.role` (staff/manager) — スケジュールエンジンだけが読む
    （manager=通常割当対象外・フリーマネージャー救済のみ・人数カウント外・
    拠点の週生成前提の在籍チェック）
- admin と manager の API 権限はほぼ同一。差分（admin 限定）は:
  患者/スタッフ/拠点の削除・全患者置換・カイポケ連携全般・監査ログ・ユーザー管理・
  ジオコーディング管理等。
- 規模: BE `require_role("admin", "manager")` 126 箇所 / `require_role("admin")` 59 箇所。
  FE の admin||manager 判定 12 ファイル+α。zod `role: z.enum(['admin','manager','staff'])`。
- 本番アカウント: admin 3 / manager 1（川名さん・s001）/ staff 6。

## 2. 新モデル

### 2.1 アカウント権限（users.role）

| 内部値 | 表示名 | できること |
|---|---|---|
| `admin` | **管理者** | すべて（現行 admin と同一 = 現行 admin∪manager の全操作） |
| `staff` | **一般** | 現行 staff と同一（閲覧中心・担当患者スコープ・チェックイン等の現場操作） |

- **`manager` は廃止**。内部値の rename はしない（`admin`/`staff` のまま、表示だけ
  管理者/一般）。列挙から `manager` を外す。
- **移行**: `UPDATE users SET role='admin' WHERE role='manager'`（migration）。
  対象は本番 1 アカウント（川名さん）。
  ⚠ 帰結: 旧 manager は admin 限定だった操作（削除系・カイポケ連携・ユーザー管理・
  全患者置換）も**できるようになる**。PO 決定「管理者=すべて」に従う。
- **旧トークン互換**: JWT の role クレームに `manager` が残った既存セッションのため、
  `require_role` 入口で `manager`→`admin` に正規化する（恒久の別名扱い。
  これにより 126 箇所の `require_role("admin", "manager")` は
  `require_role("admin")` へ機械的に単純化しても移行期間中も壊れない）。

### 2.2 業務ロール（staff.role）

- 内部値は現状維持（`staff` / `manager`）。**変更なし・移行なし**（エンジン挙動不変）。
- 表示名を「**業務ロール: スタッフ / マネージャー**」に統一し、スタッフマスタの
  編集フォーム・一覧に**説明文を添える**:
  「マネージャーは自動スタッフ割当の対象外になります（埋まらないコースの救済に
  だけ入ります）。ログイン権限とは無関係です。」

### 2.3 二軸の組み合わせ（運用イメージ）

| | 権限=管理者 | 権限=一般 |
|---|---|---|
| 業務ロール=スタッフ | 現場スタッフだが編集も任せる人 | 通常の現場スタッフ |
| 業務ロール=マネージャー | 通常のマネージャー | 閲覧のみのマネージャー |

どの組み合わせも成立する（両者は独立のため設定変更だけで実現）。

## 3. 変更内容

### Phase R-1: 権限の正規化と移行（BE 中心）

1. `app/core/deps.py` `require_role`: 判定前に `user.role == 'manager'` を
   `'admin'` として扱う正規化を追加（1 箇所・全 126+59 呼び出しに効く）。
2. migration `0069_retire_manager_role`: `users.role 'manager'→'admin'`。
   downgrade は no-op（戻す対象を特定できないため）。
3. ユーザー管理 API/schema: role の受理値から `manager` を除去
   （受信時は `manager`→`admin` へ寛容パース）。
4. seeds/開発データの manager を admin へ。

### Phase R-2: 呼び出し側の単純化（機械的置換）

5. BE: `require_role("admin", "manager")` → `require_role("admin")`（126 箇所。
   正規化があるため挙動不変の置換）。`{"admin", "manager", "staff"}` 系の
   in 判定も同様に整理。
6. FE: `role === 'admin' || role === 'manager'` → 共有ヘルパ
   `isAdminRole(role)`（`lib/auth` に新設。内部で manager も true にして旧セッション互換）
   へ置換（12 ファイル）。zod enum は `['admin','manager','staff']` のまま
   （旧トークン受理のため）→ 表示層でのみ 2 値化。
7. テスト: manager で許可を確認しているテストは「manager は admin 別名として
   引き続き通る」ことの互換テスト 1 本に集約し、残りは admin へ書き換え。

### Phase R-3: 表示名と紛らわしい記述の一掃

8. FE 表示: ユーザー管理画面（作成/編集ダイアログ）の権限セレクトを
   「管理者 / 一般」の 2 択に。一覧の role 表示も同ラベル
   （既存 manager 行は「管理者」と表示）。
9. スタッフマスタ: role フィールドの表示を「業務ロール（スタッフ/マネージャー）」
   + 上記説明文。
10. コメント・文言の一掃（調査済みの誤記）:
    - `app/models/staff.py` の「role (admin/manager/staff = システム権限)」
      → 「業務ロール (staff/manager)。エンジン専用・ログイン権限とは無関係」
    - `app/schemas/staff.py` の RoleV2 説明を業務ロールとして明記
    - grep `manager` で BE/FE の説明文・docstring を総ざらいし、
      「アカウント権限」と「業務ロール」の語で書き分ける
11. docs: 本設計書を正典に。RBAC 関連 handoff への追記。

## 4. 変えないもの（明示）

- `staff.role` の値・エンジン挙動（自動割当・救済・人数カウント）— 一切不変。
- 一般（旧 staff）権限の範囲 — 現行 staff と同一（担当患者スコープ・
  閲覧 GET 開放 3 本・チェックイン/現場ボード操作を含む）。
- 「全ロール同一表示・操作は権限どおり」の UI 原則（PO 決定 2026-07-08）。
- users.role の DB 列型・認証フロー・スタッフ×アカウント紐付け。

## 5. リスクと対処

| リスク | 対処 |
|---|---|
| 旧 manager トークンのセッションが 403 になる | require_role の正規化（別名扱い）で回避 |
| 川名さんが admin 特権（連携・削除）を得る | PO 決定どおり。リリース報告に明記 |
| manager 前提のテスト大量失敗 | 正規化により通る。R-2 で計画的に書き換え |
| 監査ログ等に残る過去の 'manager' 表記 | 履歴はそのまま（改変しない）。表示時のみ「管理者」へ寄せる |

## 6. 実装順序と規模

R-1（正規化+移行+ユーザー管理2値化）→ 半日。ここまでで運用上は完成
（表示は R-3 まで暫定）。
R-2（機械的置換+テスト）→ 半日。
R-3（表示・文言一掃）→ 半日。
デプロイは R-1 完了時点で 1 回（migration 0069 込み）、R-2/R-3 でもう 1 回。
