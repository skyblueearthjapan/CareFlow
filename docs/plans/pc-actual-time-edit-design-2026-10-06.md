# PC から実績の時刻を合わせる（訪問モニター・打刻履歴）— 設計たたき台

作成: 2026-10-06 ／ ステータス: **PO 確定（2026-10-06・モックの内容で進める）・実装中** ／ 前段: `actual-time-adjust-design-2026-09-30.md`（実績の時刻を合わせる・本番 10/1）

## 0. きっかけ
- 10/3 の熊澤さんの訪問で退出の打刻が無く、訪問モニターの滞在時間が 2,708 分になった（到着から今までを数え続けた）。10/6 に 11 件へ「到着＋35 分」をスクリプトで入れて解消。
- PC から入出・退出を合わせたい。当日はモニター、翌日以降に気づいたときはどこで、を決めたい。

## 1. 今の状態（2026-10-06）
| 場所 | 合わせられるか |
|---|---|
| PC 打刻履歴（記録 → 打刻履歴 → 行の詳細） | **できる**（管理者はすべての訪問）。到着・退出を合わせる／読取時刻に戻す／退出が無ければ手入力。**到着の読み取りがある訪問だけ** |
| PC 訪問モニター | **見るだけ**（「調整」「手入力」の印・読取時刻・誰がいつ） |
| スマホ（訪問の詳細） | 本人・7 日以内・到着の読み取りがある訪問。**先週の訪問は入口が無い**（「今週の予定」が今週だけ） |
| どこからも不可 | **到着の読み取りが無い訪問**（9/30 決定「読み取りなしは実績とみなさない」） |

## 2. PO の決定（2026-10-06）
| # | 決定 |
|---|---|
| D1 | **訪問モニターから合わせられるようにする。当日も過去の日も**（モニターの日付を切り替えれば翌日以降も使える）。管理者のみ |
| D2 | **到着の QR も読んでいない訪問（打刻なし）に、管理者だけ到着・退出を手で入れられるようにする**（紙・看護記録の時刻を入れる）。「手入力」の印で QR の実績と分ける。9/30 の「読み取りなしは実績とみなさない」を、管理者の手入力に限って改める |
| D3 | **打刻履歴に「まとめて退出を入れる」操作を足す**（「退出なし」で絞った訪問を選んで一括） |

## 3. 考え方: 部品は 1 つ、入口は 2 つ
- **訪問モニター = その日の流れの中で気づいたとき**（当日〜数日前）。詳細パネルに打刻履歴と同じ「実績の時刻を合わせる」枠を出す。**「要対応」に「退出未記録」**を出し、押すと合わせる枠が開く。
- **打刻履歴 = 期間でまとめて洗い出すとき**（請求前の月次照合など）。「退出なし」「打刻なし」で絞り、1 件ずつ、または**まとめて**入れる。
- 合わせる部品（`AdjustBox` 相当）は共通にし、どちらで合わせても API・記録・印・監査ログは同じ。

## 4. 画面（モック: `docs/mockups/pc-actual-time-edit-mock.html`）

### 4-1. 訪問モニター
- 訪問の詳細パネル（地図の右）に「実績の時刻を合わせる」枠。到着・退出を 1 行ずつ（時刻の入力＋保存・読取時刻に戻す／手入力を消す）。
- 退出の読み取りが無い訪問: 「退出を HH:MM で記録する」（記録すると完了）。候補のひと押し: **予定の終わり**／**到着＋予定の長さ**／次の訪問の到着の少し前。
- 打刻なしの訪問（D2）: 「到着・退出を手で入れる」（2 つ入れて保存で完了）。
- **過去の日**で退出が無い訪問は、滞在時間を数え続けず「**退出未記録**」と出す（今は今の時刻まで数える）。「要対応」のトレイにも出す。
- 管理者以外には枠を出さない（今のモニターの権限どおり）。

### 4-2. 打刻履歴
- 行の詳細の枠は今と同じ（部品を共通化）。打刻なしの行にも D2 の手入力を出す。
- **まとめて退出を入れる（D3）**: 「退出なし」で絞った一覧にチェックを付け →「まとめて退出を入れる」→ 決め方を選ぶ（**到着＋予定の長さ**／**到着＋○分**／**予定の終わり**）→ 確認の一覧（訪問ごとの入る時刻）→ 実行。1 件ずつ同じ API を呼び、失敗は理由つきで残す。
- 一覧に「打刻なし」の絞り込み（D2 の入口）。

## 5. API・計算（案）
- **到着の手入力（D2）**: 既存の `PUT /visits/{id}/actual-time {kind:"arrival", time}` を、**管理者で到着の読み取りが無い**ときも受ける（今は 409「到着の記録がありません」）。`visit_time_adjustments` に `base_checkin_id = NULL` の行（退出の手入力と同じ形）。到着の手入力で `planned → in_progress`、退出も入れたら `completed`。消したら元の status に戻す（`prev_visit_status` を使う）。マイグレーションは不要の見込み。
- 退出の手入力（読み取り無し）は既存のまま。
- **まとめて（D3）**: 新しい API は作らず、画面が 1 件ずつ `PUT` を呼ぶ（件数は数十件まで・既存の検証と監査がそのまま効く）。必要なら後で一括 API。
- 実績の扱い: 手入力も実績として数える（モニター・打刻履歴・ダッシュボード・予実比較）。帳票・画面では「手入力」の印で QR の実績と分ける。
- スタッフ（スマホ）の規則は変えない（本人・7 日以内・到着の読み取りがある訪問）。

## 6. 決めたいこと（細かい点）
| # | 論点 | 案 |
|---|---|---|
| Q1 | まとめて入れるときの既定 | **到着＋予定の長さ**（予定 35 分なら 35 分）。到着＋○分・予定の終わりも選べる |
| Q2 | 退出のひと押しの候補 | 予定の終わり／到着＋予定の長さ／次の訪問の到着の 10 分前 |
| Q3 | 到着だけ手入力した打刻なしの訪問 | 「実施中」。過去の日なら「退出未記録」 |
| Q4 | モニターの過去の日の「退出未記録」 | 当日は「訪問中」、前日以前は「退出未記録」（滞在時間は数えない） |
| Q5 | スマホの「先週」の入口 | 別件（今週の予定に先週も出す）。今回の範囲に入れるか |
| Q6 | 手入力・まとめて入れた時刻の印 | 「手入力」。まとめて入れたものは「手入力（まとめて）」と分けるか |
