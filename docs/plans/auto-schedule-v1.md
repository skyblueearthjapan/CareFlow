## 1. 目的とスコープ

### 1.1 目的
- 訪問看護のスケジュール作成を **人手から自動化** し、移動距離と業務負担を最小化する。
- 同時に **ローテーション要件 (担当看護師の偏り回避)** と **同住所ペアリング** などの業務ルールを厳守する。

### 1.2 スコープ (v0.1)
| 含む | 含まない |
|---|---|
| 1 拠点 × 1 週間の自動算出 | 月次/四半期の長期算出 |
| 1 名体制患者 (single-staff visit) の最適化 | 2 名体制患者 (`requires_multiple_staff=true`) の最適化 (パターン B 保留) |
| 新人 (is_trainee=true) のベテランへの同行割当 (パターン A) | 同行訓練の詳細 (教育目的のローテーション等) |
| Before/After 並列提示の UI | UI 詳細実装 (本仕様書は仕様のみ、実装は別ファイル) |
| **説明可能な提案 (KPI + AI 要約 + 個別 Justification)** | LLM API 経由の高度な自然文生成 (まずテンプレ実装) |
| マネージャー補充の **警告表示** | マネージャー自動補充の最適化 |
| 拠点間横断算出 (稲毛 + 都賀の同時最適化) | 拠点間スタッフ流通 |

## 2. 用語定義

| 用語 | 定義 |
|---|---|
| **コース** | 「曜日 × 時刻 × 患者」の枠の集合。**週通して時刻固定**。コース数は `is_trainee=false` のスタッフ数 (拠点別) で動的決定。現状: 稲毛 2 コース + 都賀 1 コース = 計 3 コース。 |
| **固定枠** | `patient_fixed_visits` テーブルの 1 行。患者 × 曜日 × 開始時刻 で確定済みのスケジュール。 |
| **モード 1 (差分追加)** | 既存固定枠を保ったまま、**差し込み対象プール**の患者を空き時間に挿入する算出モード。 |
| **モード 2 (全面最適化)** | 全 active 患者を対象に、既存固定枠を参考バッファに退避してゼロから最適化する算出モード。 |
| **差し込み対象プール** | モード 1 の入力候補集合。**自動抽出ルール: `patient.status='active' AND patient_fixed_visits に行が無い`** (= 新規契約/休止解除されたが固定枠未割当の患者)。UI で除外/追加調整は v0.4 以降で検討。 |
| **同行 (パターン A)** | 新人 (`is_trainee=true`) がベテラン (`is_trainee=false`) の visits に同行する形態。`visit_staff_assignments` に 2 行を生成。 |
| **2 名体制 (パターン B)** | 患者側都合で必ず 2 名スタッフが必要なケース (`patient.requires_multiple_staff=true`)。**v0.1 では保留**。 |
| **ローテーション** | 「同一患者に同一スタッフが連続して訪問しない」よう、曜日ごと・週ごとにスタッフを入替えるルール。 |
| **週次統一** | 同患者の訪問時刻は週通して同じ (例: 月・水・金 すべて 10:00)。 |

## 3. 入力データ

| データ | テーブル / 取得元 | 用途 |
|---|---|---|
| 患者基本情報 | `patients` (lat/lng, primary_office_id, sex_restriction, status='active') | 拠点振り分け・ハード制約判定 |
| 患者の希望条件 | `patients.weekly_pattern` (JSONB) | 希望曜日 / time_type / 希望時間帯 / サービス時間 |
| 既存固定枠 | `patient_fixed_visits` (mode='normal') | モード 1 では尊重、モード 2 では参考のみ |
| スタッフ情報 | `staff` (is_trainee, primary_office_id, role, status='active') | コース担当者の抽出、同行ペア対象の判定 |
| スタッフ実出勤枠 | `staff_shifts` + `staff_weekly_overrides` | 「その週そのスタッフが何曜日の何時から何時に稼働可能か」 |
| 受け入れカレンダー | `acceptance_calendar` | 拠点 × 曜日 × 時刻の ○/△/×。× は基本回避 |
| コーステンプレ | `course_templates` (capacity_*) | 1 コース 1 日の上限件数 (= 6 件) |

### 3.1 入力データ前処理

1. **患者を拠点別にグルーピング** (primary_office_id ベース)
2. **稼働中スタッフを抽出** (status='active', is_trainee=false → コース担当候補 / is_trainee=true → 同行候補)
3. **コース数を決定**: 拠点ごとの `is_trainee=false` のスタッフ数

## 4. 算出フェーズ (5 Phase)

### Phase 1: 固定枠集約
- 入力: `patient_fixed_visits` (mode='normal')
- 出力: 各曜日 × 時刻 × 患者の固定マップ
- 備考: モード 1 ではこの結果を「動かさない予定」として保持。モード 2 では参考用バッファに退避。

### Phase 2: 枠探索 (モード依存)

**モード 1 (差分追加)**:
- **入力**: 差し込み対象プール = `patient.status='active' AND patient_fixed_visits に行無し` の患者集合
- 各プール患者の `weekly_pattern` から希望曜日 / 時間帯を読む
- 既存固定枠と衝突しない空き時間 (= コース定員 6 件未満かつ受入カレンダー × でない) に新規枠を配置
- **既存固定枠 152 件は一切動かさない** (時刻・コース・担当いずれも保持)
- 出力: 既存 152 件 + 新規差し込み N 件

**モード 2 (全面最適化)**:
- **入力**: 全 active 患者 (現状 69 名)
- 各患者の `weekly_pattern` から候補スロットを生成
- 候補スロット = (曜日, 時刻, 患者) のタプル集合
- 既存固定枠は参考バッファに退避され、提案結果と置換候補
- 出力: 全患者の最適スケジュール (固定枠を含めて再構築)

### Phase 3: コース割当 (距離最適化) ★コア★

各 (曜日 × 時刻 × 患者) の枠を、**拠点内のコースに割り振る**。

**目的関数 (最小化)**:
```
Total Cost = Σ(distance × weight_distance)
           + Σ(staff_load_imbalance × weight_load)
           + Σ(soft_constraint_violation × weight_soft)
```

**アルゴリズム候補** (実装段階で詳細決定):
- (a) **クラスタリング (K-Means 改) + 線形割当**: 拠点内の各曜日について、患者を K (= コース数) クラスタに分割 → 各クラスタを 1 コースに割当
- (b) **VRP (車両ルーティング問題)**: より高度な最適化、ただし計算量大
- (c) **Greedy + Local Search**: 簡易だが現実的

v0.1 では **(a) クラスタリング + 線形割当** をスタート、必要に応じて精度上げる。

### Phase 4: スタッフローテーション

各 (コース × 曜日) のスロットに、**スタッフ 1 名** を割り当てる。

**制約**:
- スタッフは `is_trainee=false` から選択
- スタッフ実出勤枠内 (`staff_shifts` + 当週 override)
- **同患者 × 同スタッフ × 連続訪問** はソフトペナルティ (理想的にはハード)
- **全訪問が同スタッフ** は完全に NG (ハード制約)

**同行 (パターン A) の組込**:
- `is_trainee=true` のスタッフを、ベテランのコース × 曜日に追加割当
- 1 visit に 2 名のスタッフ (visit_staff_assignments 2 行)
- 同行先決定ルールは [要判断]: 1 週間固定 / 曜日別変動 のどちらか (運用で選択)

**マネージャー補充**:
- 「スタッフ数 < コース数 × 稼働日数」になる場合、**警告表示**
- 自動でマネージャーをコースに割り当てるロジックは v0.1 ではスコープ外

### Phase 5: コース内ルート順最適化 (TSP)
- 1 コース 1 日 (= 最大 6 件) の訪問順序を距離最小で並べる
- 上記すべての時刻が固定済みなので、実質「並べ替えのみ」(時刻は患者の希望時刻に従う)
- ただし、希望時間帯 (例: 10:00-14:00 の間でいつでも OK) の患者は、ルート順最適化の中で時刻を決定

## 5. ハード制約 (絶対遵守)

| # | 制約 | 検証 |
|---|---|---|
| H1 | 週次統一: 同患者の訪問時刻は週通して同じ | (patient_id, start_time) は週内で 1 つ |
| H2 | 同住所患者は同時刻ペアリング (最大 2 人) | 同 (lat, lng) かつ同 (weekday, start_time) は ≤ 2 |
| H3 | 同住所訪問の間に別場所を挟まない | 同住所 visit の連続性チェック |
| H4 | 全訪問が同スタッフは禁止 | 患者あたり distinct(staff_id) ≥ 2 (週訪問 2 回以上の場合) |
| H5 | 受け入れカレンダーの × 時刻には visit を入れない | acceptance_calendar.status='unavailable' と衝突しない |
| H6 | スタッフ実出勤枠を守る | staff_shifts ∪ staff_weekly_override 内に収まる |
| H7 | 性別制限を守る | patient.sex_restriction='female_only' なら staff.sex='female' のみ |
| H8 | 新人単独訪問の禁止 | is_trainee=true は必ず is_trainee=false と同 visit |

## 6. ソフト制約 (ペナルティ評価関数)

優先度の高い順:

| # | 制約 | ペナルティの目安 |
|---|---|---|
| S1 | 距離 (移動コスト) 最小化 | Haversine 距離 × weight_distance |
| S2 | スタッフ間負荷均等 | (各スタッフ訪問件数 - 平均) の二乗和 × weight_load |
| S3 | 同患者の同スタッフ連続を避ける (週内/週またぎ) | (連続発生回数) × weight_rotation |
| S4 | 午前午後別エリアは ≒ 2 時間余裕 | (午前午後跨ぎの距離) − 一定値以上なら追加ペナルティ |
| S5 | 同一コース内であちこち移動 (幕張→都賀→稲毛) 回避 | コース内エリア多様度 × weight_area |
| S6 | 連続訪問間に 60 分以上の空き (昼休憩) | 1 コース 1 日に 60+ 分空きがなければペナルティ |
| S7 | 受け入れカレンダー △ は控えめに | △ 時刻に入れた件数 × weight_consult |

## 7. UI / Before-After フロー

### 7.1 ユーザー操作フロー
```
1. 管理者が UI「自動算出」ボタンを押下
2. モード選択: モード 1 (差分追加) / モード 2 (全面最適化)
3. (モード 1 の場合) 追加対象患者を選択 (or 自動抽出)
4. 算出開始 → 数秒〜数十秒で完了
5. Before/After 並列表示で結果確認
6. 「採用」ボタンで反映 → patient_fixed_visits + visits に保存
7. または「破棄」ボタンで結果破棄
```

### 7.2 出力データ
- `visits` テーブルに `status='proposed'` で書き込み (採用前)
- 採用後: `status='proposed' → 'course_fixed' or 'staff_assigned'`
- 同時に `patient_fixed_visits` も更新 (新固定枠保存)
- `visit_staff_assignments` で スタッフ割当 (新人同行で 1 visit に 2 行)

## 9. 説明可能な提案 (Explainable Proposal)

「お客様 (= 訪問看護事業者) が **採用判断するための納得感** を得るための仕様」。
過度な情報を避けつつ、必要な深堀りはドリルダウン可能とする。

### 9.1 設計方針

- **Default は軽量** (KPI バー 5 個 + AI 要約 3-5 行のみ表示)
- **詳細はクリック展開** (折りたたみ / ポップアップで提供)
- AI 文は **テンプレートベース** (LLM 不使用、安定性重視)
- 効果は「**前回・現状 と比べていくら良くなったか**」を主軸

### 9.2 KPI ダッシュボード (Quick View, 上部固定)

5 つの集計指標を Before / After で並べる:

| KPI | 算出方法 | 表示形式 |
|---|---|---|
| 総移動距離 (km) | 全 visits の Haversine 距離合計 | `142 → 118 (-17%)` |
| スタッフ偏差 | 各スタッフ訪問件数の標準偏差 | `4.2 → 2.1 件` |
| ローテ連続発生数 | 同患者×同スタッフが連続した件数 | `3 → 0` |
| 受入× 違反数 | acceptance_calendar の × 時刻に入った visit 数 | `1 → 0` |
| 改善スコア | 評価関数 (移動・偏差・ローテ・違反の重み付き和) | `+12.4 pt` |

⭐ アイコン = 改善した指標、🔻 = 数値が減って良くなった、🟢 = 良い状態

### 9.3 AI 自然文要約 (主な変更点セクション)

#### 9.3.1 生成方式
**テンプレートベース** (決定木 → 文章合成)。生成エンジンは Python (or TypeScript) で実装、LLM API は使わない。

理由:
- 安定性 (出力ばらつき無し)
- レイテンシ (~10ms vs LLM 数秒)
- コスト (無料)
- 監査可能性 (なぜこの文が出たか追跡可)

#### 9.3.2 出力テンプレート

```
[テンプレート種別]
  ・追加: 「{患者名}様を新規追加 ({曜日} {時刻}, {コース})」
  ・時刻変更: 「{患者名}様の時間を {旧時刻} → {新時刻} に変更
              → これで {コース}{曜日}が「{エリア}集約」となり {距離変化}」
  ・担当変更: 「{患者名}様の{曜日}担当を「{旧スタッフ} → {新スタッフ}」に変更
              → {ローテ理由 or 負荷理由}」
  ・削除: 「{患者名}様の {曜日}{時刻} 訪問を削除候補
              → 理由: {状態変化 or 重複}」
```

#### 9.3.3 表示順序ルール
インパクト順:
1. 距離削減効果の大きい変更
2. 新規追加
3. ローテーション関連
4. その他

**最大 5 項目** まで。それ以上は「他 N 件の細かい変更」と集約。

### 9.4 個別 Visit Justification ポップアップ

visit セルクリック時に表示。4 観点で構造化:

| 観点 | 出力例 | 算出元 |
|---|---|---|
| **コース選択理由** | "A (移動 8km vs B 案 18km)" | Phase 3 で各候補コースのコスト比較を保持 |
| **時刻選択理由** | "13:00 (希望「午後」内、前後の visit と距離最小)" | Phase 5 で TSP 最適化時のコスト保持 |
| **担当選択理由** | "川名 (S001)。他候補: 熊澤。熊澤は同日満枠" | Phase 4 のローテ・負荷スコア保持 |
| **制約遵守** | "✅ 受入○ ✅ 性別制限なし ✅ 同住所ペアリングなし" | Phase 1-5 で参照したハード制約結果 |

### 9.5 実装観点 (実装時に詳細化)

- 各 Phase で「**決定ログ (decision log)**」を構造化 JSON で残す
  ```json
  {
    "visit_id": "...",
    "phase_3": {"chosen_course": "A", "alternatives": [{"course": "B", "cost": 18}]},
    "phase_4": {"chosen_staff": "S001", "rotation_score": 0.92, ...},
    "phase_5": {"slot_neighbors": ["10:30", "13:35"], "distance_gain": 3.2}
  }
  ```
- AI 自然文 generator は decision log + diff (Before/After) からテンプレート選択して文を組み立てる
- API レスポンスに `justification` フィールドを含める形式が望ましい

## 10. データ書込仕様

### 10.1 算出結果の保存先

| データ | 保存先 | status |
|---|---|---|
| 提案 visits | `visits` | `proposed` |
| 採用後の visits | `visits` | `course_fixed` → `staff_assigned` |
| 提案スタッフ割当 | `visit_staff_assignments` | (採用後にコミット) |
| 採用後の固定枠 | `patient_fixed_visits` | (mode='normal') |

### 10.2 採用フロー (Atomic Transaction)
```
1. user clicks 採用ボタン
2. BEGIN transaction
3. visits.status='proposed' → 'course_fixed' (採用された visit のみ)
4. visit_staff_assignments を INSERT
5. patient_fixed_visits を UPSERT (新固定枠)
6. (decision log を proposal_decisions テーブル等に永続化 - 監査用)
7. COMMIT
```

### 10.3 破棄フロー
```
1. user clicks 破棄ボタン
2. DELETE FROM visits WHERE status='proposed' AND created_at > 提案開始時刻
3. 関連 decision log もクリーンアップ
```
