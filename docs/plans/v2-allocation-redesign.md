## 1. 背景

### 1.1 v1 の失敗要因

| # | 問題 | 影響 |
|---|---|---|
| 1 | 患者マスタの条件項目が肥大化 | 入力負担増・入力漏れ多発 |
| 2 | 担当指定 / NG / 継続性希望 等の過剰条件 | 条件矛盾で割当不能ケース増加 |
| 3 | ロジックが全条件網羅を志向 | GAS 6分制限超過、Python 移植後も保守困難 |
| 4 | 監査で重大バグ 5 件 | NG/性別チェック欠落、GapPack の状態漏れ等 |

### 1.2 v2 の方針転換

- **マスタは最小条件のみ**: 希望曜日 / 週訪問回数 / 時間タイプ / 性別制限
- **時間枠決定は人手**: ドラッグ操作で時刻スロットに配置
- **自動化はスタッフ配分のみ**: 曜日ごとに距離+ローテーション+性別で自動割振
- **学習型運用**: 人が一度決めた配置を「固定ボタン」でマスタに焼き込み、
  次週以降は自動で同じ時間枠に展開される

## 2. コアコンセプト

### 2.1 用語定義

| 用語 | 説明 |
|---|---|
| 保留プール | スケジュール表下部のカード溜まり領域。新規/未固定患者がここに入る |
| 固定枠 | 時刻スロットに配置された確定済みの訪問枠 |
| 固定ボタン | その週のレイアウトを患者マスタの週間パターンに保存する操作 |
| スタッフ枠 | 1 スタッフが 1 日に持てる訪問数（基本 6 件） |
| マネージャー (M1) | スタッフ枠を持たない管理者枠。緊急時のみ訪問。割当対象外 |

### 2.2 設計哲学

> "前回の失敗の根本原因はマスタへ条件を詰め込みすぎたこと。
> v2 では **人間が直感的にスケジュールを組み、システムはそれを記憶して
> 繰り返す** という分業に切り替える。"

- マスタが知っている情報 < 管理者の頭の中の情報
- 例外運用は UI 上の手動操作で吸収する（マスタを汚さない）
- 自動化は明確に得意な領域（距離計算 / ローテーション分散）に限定

## 3. 運用フロー

### 3.1 全体像

```
[新規/既存患者]
   │  最小情報のみ：希望曜日 + 週訪問回数 + 時間タイプ
   │  + (任意) 固定希望時刻 + 性別制限
   ▼
[Step A] スケジュール表の保留プール（下部）に投入
   │
   ▼
[Step B] 管理者がカードを時間スロットにドラッグして配置
   │
   ▼
[Step C] 「固定」ボタンでその週のレイアウトを確定
   │  → 患者マスタの週間パターンに反映
   │
   ▼
[Step D] 各曜日でスタッフへ自動割り振り
       考慮: 距離・午前/午後・性別制限・ローテーション
```

### 3.2 各ステップの詳細

#### Step A: 投入

- 新規患者の登録時、または既存患者で固定パターン未設定のとき、
  カードがスケジュール表の下部「保留プール」に積まれる。
- 表示位置：希望曜日の列の最下部。曜日が複数ある場合は各曜日に重複表示。
- まだ時刻は決まっていない（時間タイプが「固定」の場合は希望時刻を持つが、
  実配置はされていない）。

#### Step B: 手動配置（ドラッグ）

- 管理者が保留プールのカードを掴み、時間スロット（**15 or 30 分単位** —
  TBD）に配置する。
- スタッフ列はまだ未指定（割振は Step D）。曜日 × 時刻のグリッドに置く。
- スタッフ枠（曜日合計 6 × N 名）に達したら、新たな配置はブロック（or 警告）。
- 2 名体制が必要な場合、配置済みカードに「+1 人」操作を加えて分身
  させる（詳細は §3.3）。

#### Step C: 固定 → マスタ反映

- 「固定」ボタンを押すと、現在の週のレイアウトが対象患者の **週間訪問
  パターン** として患者マスタに保存される。
- 次週以降の表初期化時、このパターンが自動的に時間スロットに展開される。
- 患者マスタの週間パターン更新後も、希望曜日・時間は管理者が UI 上で
  自由に編集できる。

#### Step D: スタッフ自動割り振り

- 各曜日について、その日の固定枠に並んだ患者群を稼働スタッフに分配する。
- 1 スタッフあたり最大 6 名（マネージャーは対象外）。
- 考慮要素（**詳細は §5**）:
  - 距離（メイン最適化対象）
  - 午前 / 午後の希望
  - 性別制限（ハード制約）
  - ローテーション（同一スタッフが繰り返し担当しないよう分散）
  - 拠点（**§4.3 で議論**）

### 3.3 2 名体制の取り扱い

> 決断 1 の結論: 患者マスタには `必要スタッフ数 (need_staff)` フィールドを
> 持たない。2 名体制の必要性は **スケジュール表上で曜日ごとに表現する**。



#### 仕組み

- 通常: 1 患者 → 1 時刻スロット占有 → 1 スタッフ割当
- 2 名体制化: 管理者が時刻スロット上の患者カードを「+1 人」操作で
  分身させる。同じ時刻に 2 枠占有 → 2 スタッフ割当
- **曜日別**: 月曜は 2 名・金曜は 1 名のような運用が可能（曜日ごとに
  必要人数が変わるケースを想定）

#### データモデル上の表現

- 患者マスタ: `need_staff` フィールドは削除
- 週間訪問パターン (`weekly_pattern`) の各曜日エントリに `staff_count`
  を追加（既定 1、2 で 2 名体制）
- 固定ボタン押下時、管理者が分身させた状態がそのまま `staff_count=2`
  として保存される
- 訪問インスタンス (`visits`) にも `required_staff_count`（1 or 2）を持つ
- 2 名体制を表現するため、**訪問グループ (`visit_group_id`)** を導入し、
  同じ訪問の 2 件を 1 つの論理単位としてリンク
- スタッフ割当は `visit_staff_assignments`（visit_id × staff_id 多対多）で表現し、
  Layer 3 出力は 2 名体制の場合に **2 行返す**

#### スタッフ枠への影響

- 2 名体制 1 件 = スタッフ枠 2 つ消費（その時間帯の各スタッフが 1 枠ずつ）
- 「6 人/日」の枠カウントは **枠消費（service 時間）ベース** で判定（§MVP 前提参照）

### 3.4 特別訪問週間の取り扱い

> 決断 4 の結論: **残す**。患者マスタに通常の週訪問パターンとは別に
> 「特別訪問週間用のパターン」を持ち、特別週フラグが立った週だけ
> その別パターンが適用される。

#### コンセプト

通常時は週 2〜3 回の訪問だが、状況により一時的に週 5 回などへ訪問頻度を
増やしたい期間がある。これを「特別訪問週間」と呼び、患者ごとに事前に
定義できるようにする。

| | 通常パターン | 特別訪問週間パターン |
|---|---|---|
| 想定訪問頻度 | 週 2〜3 回 | 週 5 回など |
| 設定タイミング | スケジュール表で運用しながら確立 | 患者マスタで事前定義 |
| 適用 | 標準（毎週） | 「特別週 ON」の週のみ |

#### 設定 UI

- スタッフマスタの「出勤曜日 + 時間」設定と同じスタイルのモーダル
- 曜日ごとに「何時に訪問するか」を設定（時間タイプ・希望時刻含む）
- 通常パターンと特別週パターンをそれぞれ別タブで定義可能

#### 特別週の有効化

- 患者マスタに「特別訪問週間 ON/OFF」トグル
- ON にすると、適用週（例: 来週、再来週、または期間指定）を指定
- 該当週はスケジュール表展開時に特別週パターンが使われる

#### 固定化

- 特別週の運用中も通常時と同じく、スケジュール表上で時間枠を調整可能
- 「固定」ボタンで確定すれば、その配置が特別週パターンとして患者
  マスタに保存される（学習型運用は通常時と同じ）

#### データモデル上の表現（**確定**: Option A）

- `weekly_pattern` (JSONB): 通常パターン（既存）
- `special_weekly_pattern` (JSONB): 特別週用パターン（新規）
- `special_week_active` (JSONB): **適用週リスト** `[{iso_year, iso_week}, ...]`
  - 期間指定の場合は事前に展開して個別週として保存
- 競合時の優先順位: `special_week_active` 該当週は **`special_weekly_pattern` を優先**、
  非該当週は `weekly_pattern` を使用

#### 既存 UI の整理

- 旧 `/special-weeks` 専用ページ（サイドバー「特別訪問週間」項目）は **廃止**
- v2 では特別訪問週間は **患者マスタの一機能** として組み込まれるため、独立した一覧画面は不要
- サイドバー項目は **削除済み**（2026-05-05 時点でフロントエンドの NAV から除外）。
  バックエンドの `/special-weeks` ルート・関連テーブルは v2 実装時にデプリケート予定

### 3.5 AI 入力の権限と承認フロー

> 2026-05-05 確定（Q-AI-4 (a), Q-AI-5 (b), Q-AI-6 (b), Q-AI-7 (a)）。

#### 3.5.1 基本原則

1. **モバイル入力は即時反映禁止** — どのロールでもモバイル端末から入力した内容は
   履歴に「申請」として残り、PC ブラウザでの管理者承認後に確定する
2. **権限はアカウント（ユーザー）に紐付く** — 入力者ロールが操作可能スコープを決める
3. **業務記録は「申請履歴」に蓄積** — Gemini API の解釈ログ（デバッグ用）とは別に、
   業務承認フローの記録を持つ（§4.4）

#### 3.5.2 AI が扱う対象

> **方針**: 音声・テキスト入力ができる箇所は **すべて AI 化** することを目標とする。

##### 対象内

| カテゴリ | 操作 | 例 |
|---|---|---|
| マスタ新規 | **患者新規登録** | 「新規患者で田中太郎さん、千葉市稲毛区の住所、週2回月木の午前」 |
| マスタ新規 | **スタッフ新規登録** | 「新規スタッフで山田花子さん、火曜と金曜が固定休、稲毛拠点」 |
| スタッフ予定 | その週だけの休み | 「田中さん木曜休み」 |
| スタッフ予定 | イベント新規 | 「火曜午後 管理者会議」 |
| スタッフ予定 | 新人フラグ切替 + 同行スタッフ割付 (曜日×午前/午後/終日) | 「鈴木さんを新人にする」「鈴木さんの月曜午前は田中さん」「鈴木さんを新人にして平日終日田中さん」 |
| 患者対応 | 特別訪問週間 ON/OFF | 「佐藤さん来週特別週オン」 |
| 患者対応 | 訪問キャンセル | 「田中さん明日キャンセル」 |
| 患者対応 | 日時変更 | 「鈴木さん明日10時に1時間追加」 |
| **患者マスタ状態変更** | **patients.status 更新** (active / suspended / admitted / pending / cancelled) | 「山田さんを入院中にして」「鈴木さんは解約」 |
| **スタッフマスタ状態変更** | **staff.status 更新** (active / on_leave / retired) | 「鈴木さんを休職にして」「田中さんは退職」 |

##### 不足情報補完モーダル（重要）

新規登録系（患者・スタッフ）は項目数が多く、音声・テキストでは情報が抜け
落ちることが想定される。以下の UX で対応：

1. AI が音声 / テキストを構造化 JSON に変換
2. **必須フィールドのうち未入力のものをハイライトしたモーダル** を表示
3. 管理者が不足情報を手で補完
4. 「登録」ボタンで通常の作成 API に POST

このパターンは新規登録以外の操作にも適用する：
- AI 解釈の信頼度が低い項目は編集モーダルで確認させる
- 必須情報が欠けていた場合は "ここを埋めてください" と明示

##### 対象外（明示）

CareFlow 内の業務操作は原則 AI 対象。ただし以下は **AI 経由不可**：
- 患者・スタッフの **削除**（重大操作）
- 拠点マスタの編集（地理データを含むため Web フォームから）
- 監査ログの編集
- ユーザー（ログインアカウント）の作成・権限変更
- 外部システム操作（カイポケ自動入力等）
- 給与・経費・請求関連

#### 3.5.3 ロール別の操作スコープ

| ロール | デバイス | 操作スコープ | 反映方式 | 履歴記録 |
|---|---|---|---|---|
| Admin | PC | 全操作 | **即時** | ✅ `pending_requests` に `approved` で記録 |
| Admin | モバイル | 全操作 | 履歴経由（即時禁止） | ✅ `pending` で記録 |
| Manager | PC | 全操作（admin 同等） | **即時** | ✅ `pending_requests` に `approved` で記録 |
| Manager | モバイル | 全操作 | 履歴経由（即時禁止） | ✅ `pending` で記録 |
| Staff | PC・モバイル | **自分軸のみ** | 履歴経由（申請） | ✅ `pending` で記録 |

> **監査要件**: AI 経由の全操作は反映方式に関わらず `pending_requests` に記録する。
> 即時反映の場合は `approved` 状態でレコードを作成し、業務反映と同一トランザクションで処理（冪等性確保）。

##### 「自分軸」の定義（スタッフが申請可能な範囲）

| 操作 | 可否 |
|---|---|
| 自分の休み・シフト希望 | ✅ |
| 自分の予定変更 | ✅ |
| 自分が担当する患者の今日のキャンセル | ✅ |
| 自分が担当する患者の日時変更依頼 | ✅ |
| 自分が担当する患者の特別訪問週間 ON/OFF 依頼 | ✅ |
| 他スタッフの休み・予定・同行割付 | ❌ |
| 自分が担当しない患者の操作 | ❌ |

> スタッフが現場で患者から直接キャンセルや時間変更を聞いた場合、その場で
> 音声入力で記録できる運用を想定（モバイル AI の本命ユースケース）。

#### 3.5.4 申請ステータス

3 状態で管理：

| ステータス | 意味 | スケジュール反映 |
|---|---|---|
| `pending` | 入力直後 | 未反映 |
| `approved` | 管理者承認済み | 反映済み |
| `rejected` | 却下（**却下理由必須**） | 未反映 |

承認バリエーション：
- 内容そのまま承認 → `approved`
- 管理者が編集してから承認 → `approved`（編集前後の差分を保存）
- 不適切と判断 → `rejected`（理由を記録）

#### 3.5.5 履歴 UI

##### 専用画面: `/admin/pending-requests`
- 申請一覧をフィルタ・並び替え可能
- **スタッフ予定** と **患者関連** を **明確に分けて表示**（タブ or セクション分割）
- 各申請にアクション: 承認 / 編集して承認 / 却下

##### スケジュール画面にも表示
- スケジュール表の **上端 or 下端** に「保留中の申請」リスト
- スケジュールを見ながら判断したいケースに対応
- 履歴画面 / スケジュール画面のどちらからでも、承認・却下・編集が可能

#### 3.5.6 スケジュール変更の種別選択（重要）

患者の日時変更を実行するとき、管理者は変更の **適用範囲** を選択：

| スコープ | 意味 | データへの反映 |
|---|---|---|
| **今週だけ** | 一回限りの変更 | その週のスケジュールのみ更新。患者マスタの `weekly_pattern` は触らない |
| **今後固定（定期）** | 恒久変更 | 患者マスタの `weekly_pattern` を更新。次週以降も自動展開 |

##### 設計意図
急なイレギュラー対応（風邪で振替、緊急訪問追加等）が、そのまま固定パターンに
焼き込まれてしまうのを防ぐ。

##### スタッフ予定の場合
スタッフ予定（休み・イベント等）は性質上、ほぼ「その週だけ」の臨時変更が中心。
種別選択は **不要**。恒久的な変更は既存の設定画面（出勤曜日・シフト時間）から
行う運用。

#### 3.5.8 スケジュール変更ダイアログの (a)/(b) モード（固定枠対応）

> §3.6.8「固定枠 (週間訪問パターン)」導入後、患者カードを D&D したときの
> 確認ダイアログは以下の 2 択に拡張する。

スケジュール画面で患者カードを D&D（時刻・曜日の変更）した際、確認ダイアログ
を表示し、管理者が適用範囲を選択する：

| 選択肢 | 意味 | データへの反映 | API |
|---|---|---|---|
| **(a) 今週のみ反映** | 一回限りのイレギュラー対応 | 当該週の `visits` の時刻のみ更新。`patient_fixed_visits` / `weekly_pattern` は触らない | `POST /api/v1/schedule/fix`（既存）|
| **(b) 固定枠を変更** | 翌週以降に恒久反映 | `patient_fixed_visits` を更新。次週以降の `generate-week` に即時反映 | `POST /api/v1/schedule/fix-or-pattern`（新規 §7.6.3） |

##### 特別週判定
- **(b)** を選択した週が `special_week_active` リストに含まれる場合 →
  `mode='special'` の `patient_fixed_visits` を更新
- 含まれない場合 → `mode='normal'` の `patient_fixed_visits` を更新

##### scope との関係（§3.5.6 との整合）
- 本ダイアログは **D&D 操作** に特化した実装フロー。
- AI 経由の `patient_reschedule` が scope=`permanent` の場合も、
  内部的には同じ `patient_fixed_visits` 更新パスを通る（§9.2 参照）。

#### 3.5.7 AI 範囲の明示と境界線の伝達

> **設計要件**: AI でできることとできないことを、ユーザーに **明確に伝える仕組み**
> を組み込む。「何でもできる AI」と誤解させないことが運用上の信頼に直結する。

##### UI に組み込む 4 つの仕組み

| 仕組み | 配置 | 内容 |
|---|---|---|
| 1. **「できること」一覧** | AI 入力モーダル内（恒常表示 or 開閉ヒント） | §3.5.2 の対象内表を、ユーザー目線の例文付きで表示 |
| 2. **「できないこと」表示** | AI 入力モーダル内（折りたたみ可） | 例: 「給与計算」「カイポケ操作」「契約書類の作成」など、誤解されがちな範囲外を明示 |
| 3. **範囲外検知時のフィードバック** | 解釈レスポンス | AI が範囲外と判定した場合、「申し訳ありません、これは現在 AI で対応していません。○○画面から手動で入力してください」を返す |
| 4. **ヘルプ / FAQ ページ** | サイドバーまたはユーザーメニュー | AI 機能の一覧 + 例文集 + 制約事項を一箇所にまとめる |

##### 具体的な「できる/できない」一覧（v2 時点）

###### ✅ できること
- 患者の新規登録（不足情報はモーダルで補完）
- スタッフの新規登録（同上）
- スタッフの今週だけの休み登録
- スタッフのイベント新規（会議・研修）
- スタッフの同行スタッフ割付（`staff_companion_assignments`）
- 患者の特別訪問週間 ON/OFF
- 患者の訪問キャンセル
- 患者の訪問日時変更（今週だけ / 今後固定 を選択）
- 患者の状態変更（稼働中 / 一時休止 / 入院中 / 開始前 / 解約済み）
- スタッフの状態変更（在籍 / 休職 / 退職）

###### ❌ できないこと（明示すべき範囲外）
- カイポケへの自動入力（操作）
- 給与・経費計算
- 契約書・請求書の作成
- 患者・スタッフの**削除**（重大操作のため AI 経由不可）
- 拠点マスタの編集（地理データを含むため Web フォームから）
- 監査ログの編集
- ユーザー（ログインアカウント）の作成・権限変更

##### 範囲外検知時のフィードバック例

ユーザー発話: 「田中さんの給与を 30 万円に変更」
AI 応答: 「給与の変更は AI では対応していません。給与管理は別システムで行ってください」

ユーザー発話: 「拠点を追加したい」
AI 応答: 「拠点の追加は AI では対応していません。サイドバーの『拠点』画面から登録してください」

##### 実装上の注意

- AI モーダルのヒント文言は **`AI_CAPABILITIES_GUIDE` のような定数集** から取得し、
  対象内/外が増減した時に 1 箇所で更新できる構成にする
- 範囲外判定は Gemini プロンプトに「対象外の場合は `out_of_scope` アクション
  を返す」と明示することで実装

#### 3.5.10 AI 経由の同行スタッフ割付 (Wave 11)

> Wave 11 追記（2026-05-06）。既存 `staff_mentor` request_type の payload を拡張し、
> 新人フラグ切替（mode A）と同行スタッフ割付（mode B）を AI 経由で一括処理できるよう
> にする。**新規 request_type は追加しない**。

##### 2 モードの概要

| モード | トリガー | 操作内容 |
|---|---|---|
| **mode A**: 新人フラグ切替 | `payload.is_trainee` bool あり | `staff.is_trainee` を `true` / `false` に更新する |
| **mode B**: 同行スタッフ割付 | `payload.assignments[]` あり | `staff_companion_assignments` を全削除 → INSERT（PUT 同等の冪等） |

両モードは **同時指定可**（1 リクエストで完結）。

##### mode B payload 構造

```json
{
  "staff_id": "<trainee uuid>",
  "assignments": [
    { "weekday": 0, "part": "am", "companion_staff_id": "<uuid>" },
    { "weekday": 0, "part": "pm", "companion_staff_id": "<uuid>" }
  ]
}
```

- `weekday`: 0〜6 (0 = 月曜)
- `part`: `'am'` / `'pm'` / `'full'` のいずれか
- `companion_staff_id`: 自身以外、`role IN ('manager','staff')`、`status = '在籍'`

##### バリデーション

| 検証項目 | 内容 |
|---|---|
| `weekday` 範囲 | 0〜6 のみ受け付ける |
| `part` 値 | `'am'` / `'pm'` / `'full'` のみ |
| `part` 排他 | 同一曜日内で `'full'` と `'am'`/`'pm'` は排他（`'full'` と同時に `'am'` または `'pm'` を指定した場合は 422） |
| companion 資格 | `role IN ('manager','staff')` かつ `status = '在籍'` かつ `deleted_at IS NULL` かつ trainee 本人以外 |
| 冪等性 | mode B 適用時は既存 `staff_companion_assignments` を全削除 → INSERT（PUT 同等） |

##### is_trainee の自動強制

`payload.assignments` が指定された場合（mode B）、trainee の `is_trainee` が `false` であっても
**自動的に `true` に強制** する。運用上「新人にする」+「companion 設定」を 1 リクエストで
完結させることを優先するため。

> 両モードが指定されていない場合（`is_trainee` も `assignments` も未指定）は
> 422 "either is_trainee or assignments must be provided" を返す。

##### 発話例と対応モード

| 発話例 | 適用モード | payload の概要 |
|---|---|---|
| 「鈴木さんを新人にする」 | mode A のみ | `{ "staff_id": "<鈴木>", "is_trainee": true }` |
| 「鈴木さんを新人から外す」 | mode A のみ | `{ "staff_id": "<鈴木>", "is_trainee": false }` |
| 「鈴木さんの月曜午前は田中さん、月曜午後は佐藤さん」 | mode B のみ | `{ "staff_id": "<鈴木>", "assignments": [{ "weekday": 0, "part": "am", "companion_staff_id": "<田中>" }, { "weekday": 0, "part": "pm", "companion_staff_id": "<佐藤>" }] }` |
| 「鈴木さんを新人にして、平日終日田中さんと同行」 | mode A + B | `{ "staff_id": "<鈴木>", "is_trainee": true, "assignments": [{ "weekday": 0, "part": "full", "companion_staff_id": "<田中>" }, ...(火〜金)] }` |

### 3.6 自動 / 手動 / AI の役割分担（3 レイヤー構造）

> §3.1〜3.5 までで個別の流れを定義した。本セクションではそれらを 3 レイヤー
> 構造として統合的に整理する。スケジュール作成の中核アーキテクチャ。

#### 3.6.1 全体像

| レイヤー | 役割 | 主体 | 固定対象 |
|---|---|---|---|
| **Layer 1** | 時間配置（患者を時刻スロットへ） | 人間中心 | `weekly_pattern`（患者単位） |
| **Layer 2** | コース分け（患者を A/B/C/D に組分け） | Python 半自動 + 人補正 | コース構成（曜日単位） |
| **Layer 3** | スタッフ割付（コース ↔ スタッフ） | Python 全自動 | 固定しない（毎週ローテで動く） |

#### 3.6.2 Layer 1: 時間配置

| 項目 | 内容 |
|---|---|
| 入力 | 患者マスタ（希望曜日・訪問回数・時間タイプ） |
| 自動 | 新規患者を「未割り当てプール」に流し込み。既存患者は `weekly_pattern` から自動展開 |
| 手動 | プール → 時刻スロット（15 分単位）ドラッグ配置 / 移動 / 2 名体制化（§3.3） |
| 固定 | 「固定」ボタン → 患者マスタの `weekly_pattern` に保存 |
| 翌週 | マスタから自動展開、新規患者のみ保留プール経由で投入 |

#### 3.6.3 Layer 2: コース分け

| 項目 | 内容 |
|---|---|
| 入力 | 当該曜日に時刻配置された患者群 + 各拠点座標 |
| 自動 | 距離ベースで 6 名 × 4 コース（= 稼働スタッフ数）の案を生成 |
| 手動 | 人が案を確認して微調整（患者をコース間で移動） |
| 固定 | コース構成を保存 |
| 翌週 | 同じ構成を維持。患者の出入りがあれば再計算 |

#### 3.6.4 Layer 3: スタッフ割付

| 項目 | 内容 |
|---|---|
| 入力 | 確定済みコース構成 × 当該週の稼働スタッフ |
| 自動 | ローテーション原則で「曜日 × コース → スタッフ」を全自動決定 |
| 手動 | 異常時のみ管理者が上書き |
| 固定 | しない（毎週変動するのが本質） |
| ハード制約 | 性別制限 / 勤務曜日 / 1 コース 1 スタッフ / マネージャー除外 |

#### 3.6.5 マネージャー (M1) の位置付け

- スケジュール表の **最上行に常駐**
- **6 人 × 4 コースの枠カウントには含まれない（枠外）**
- 役割：
  - コース 6 人枠から **あふれた患者** を引き受け
  - 緊急対応・新規患者の初回・複雑ケース
- Layer 3 の自動配分の対象外（手動配置のみ）

#### 3.6.6 「固定」の 3 段階

| 段階 | 何が固定されるか | 例 |
|---|---|---|
| 時間固定（Layer 1） | 患者の曜日 × 時刻 | 田中さんは月曜 9:00 |
| コース固定（Layer 2） | 患者の所属コース | 田中さんは A コース |
| スタッフ確定（Layer 3） | その日の担当者 | 今週月曜 A は S1（来週は S2） |

→ **時間とコースは「ほぼ動かない」、スタッフは「毎週動く」**

#### 3.6.7 再算出のトリガー

| 変化 | 再計算範囲 |
|---|---|
| 新規患者追加 | L1 保留へ → L2 案再生成 → L3 |
| 患者の時間変更（今週だけ / §3.5.6） | L1 のみ |
| 患者の時間変更（恒久 / §3.5.6） | L1 → L2 構成見直し → L3 |
| 患者キャンセル（今週だけ） | L1 から削除（L2/L3 への影響は確認後） |
| スタッフ休み（今週だけ） | L3 のみ（代替スタッフを当てる） |
| スタッフ追加・退職 | L3 全面再計算 |
| 拠点変更 | L2 から再計算（距離が変わるため） |

#### 3.6.x 同行スタッフの Layer 3 連携（Wave 10 新設）

> Wave 10 Phase 6a 追記（2026-05-06）。新人スタッフが訪問にアサインされた際、
> Layer 3 がスタッフ割付を完了した後に companion を自動付与する拡張。

##### 自動付与の仕組み

新人スタッフ（`is_trainee = true`）が `visit_staff_assignments` にアサインされた訪問に対して、
Layer 3 は `staff_companion_assignments` を参照し、対応する companion を **自動追加** する。

処理ステップ:

1. Layer 3 が当該曜日のコース割付を完了し、`visit_staff_assignments` に新人スタッフ行を INSERT する
2. 該当訪問の `start_time` から **午前 / 午後** を判定する（下記「時刻の判定」参照）
3. `staff_companion_assignments` から `(trainee_staff_id, weekday, part)` が一致する companion を取得する
4. companion が存在する場合、同一 `visit_id` × `companion_staff_id` の行を `visit_staff_assignments` に追加する
5. companion が存在しない場合（未設定）は処理を継続し、警告ログを記録する（割付失敗にはしない）

##### 時刻の判定

companion の当該曜日の `staff_shifts` レコードを参照し、シフト時間の中央時刻で午前 / 午後を分割する。

| 条件 | 判定 |
|---|---|
| `part = 'am'` | シフト開始時刻 ≦ 訪問開始時刻 < シフト中央時刻 |
| `part = 'pm'` | シフト中央時刻 ≦ 訪問開始時刻 < シフト終了時刻 |
| `part = 'full'` | シフト全体（訪問時刻によらず常に同行） |

例: シフト 9:00〜19:00 の場合、中央時刻は 14:00。午前 = 9:00〜14:00、午後 = 14:00〜19:00。

##### 2 名体制との関係

患者側 `required_staff_count = 2`（2 人体制患者）の同行要否と、新人側の companion 同行は **独立した仕組み** として扱う。

- 2 つが同じ訪問で両方該当する場合は、`visit_staff_assignments` 行数が **3 以上** になりうる
- これは設計上の許容範囲とし、運用側の判断で対処する（特別な制約は設けない）

#### 3.6.8 固定枠 (週間訪問パターン)

> Wave 9 Phase 5a 追記（2026-05-06）。`patient_fixed_visits` テーブルを導入し、
> Layer 1 を hybrid 化することで「人が一度決めた配置を自動で繰り返す」運用を
> システムとして永続化する。

##### コンセプト

スケジュール配置が安定した患者について、**希望 (weekly_pattern) → Pool → 配置確定**
という毎週の手動ステップを省略する。「固定化」操作を実行すると、その週の配置が
`patient_fixed_visits` テーブルに書き戻され、翌週以降は固定枠から直接 visits を
生成できるようになる（Layer 1 hybrid 化）。

##### ライフサイクル

```
[新規登録] 希望 weekly_pattern
    ↓ Layer 1 (希望 expander)
[Pool 配置] visits 仮配置
    ↓ Layer 2 (Course 自動分類) + 手動微調整
[配置確定] visits 確定
    ↓ ★「固定化」操作 (個別 or 全患者一括)
[固定枠] patient_fixed_visits (通常 / 特別週)
    ↓ 翌週以降
[自動展開] 固定枠から visits 直接生成 (Layer 1 hybrid 化)
```

##### Layer 1 hybrid 化

`generate-week`（§5.2）実行時、患者ごとに分岐する：

- `patient.has_fixed_visits(mode)` が **真** → `patient_fixed_visits` から
  時刻・duration を読み取り、そのまま visits を生成する（旧 expander 不使用）
- `patient.has_fixed_visits(mode)` が **偽** → 従来どおり `weekly_pattern` /
  `special_weekly_pattern` を expander に渡して visits を生成し、保留プールへ

`mode` の判定：
- 当該週が `special_week_active` リストに含まれる → `mode='special'`
- 含まれない → `mode='normal'`
- `mode='special'` の固定枠が未設定の場合は `mode='normal'` にフォールバック

##### 2 名体制の表現

`patient_fixed_visits` は **時刻・duration のみ** を持つ。必要スタッフ数は
`patients.required_staff_count` で引き続き表現し、固定枠テーブルには持たない。

##### 指名スタッフ

固定枠はスタッフを指名しない。Layer 3 のローテーションアルゴリズム（§5.4）が
毎週担当スタッフを決定する運用を維持する。

### 4.1b patient_fixed_visits テーブル（W9-BE1）

> Wave 9 Phase 5a 追記（2026-05-06）。§3.6.8 のライフサイクルを永続化する
> 新規テーブル。Alembic `0017_v2_patient_fixed_visits` で追加する（§本書 §8 参照、
> マイグレーション予約表 0017 番）。

#### DDL（Alembic 0017 と整合）

```sql
CREATE TABLE patient_fixed_visits (
    id           UUID         PRIMARY KEY DEFAULT gen_random_uuid(),
    patient_id   UUID         NOT NULL
                              REFERENCES patients(id) ON DELETE CASCADE,
    mode         VARCHAR(16)  NOT NULL
                              CHECK (mode IN ('normal', 'special')),
    weekday      SMALLINT     NOT NULL
                              CHECK (weekday BETWEEN 0 AND 6),  -- 0=Mon ... 6=Sun
    start_time   TIME         NOT NULL,
    duration_min INT          NOT NULL DEFAULT 30
                              CHECK (duration_min BETWEEN 1 AND 480),
    created_at   TIMESTAMPTZ  NOT NULL DEFAULT now(),
    updated_at   TIMESTAMPTZ  NOT NULL DEFAULT now(),
    UNIQUE (patient_id, mode, weekday)
);

CREATE INDEX idx_pfv_patient        ON patient_fixed_visits (patient_id);
CREATE INDEX idx_pfv_patient_mode   ON patient_fixed_visits (patient_id, mode);
```

#### 制約・設計方針

| 項目 | 内容 |
|---|---|
| 1 日複数訪問 | `UNIQUE (patient_id, mode, weekday)` により **1 患者 × 1 mode × 1 曜日 = 1 訪問のみ**（複数回/日は不可） |
| 2 名体制 | `patients.required_staff_count`（1 or 2）で表現。固定枠テーブルには持たない |
| 指名スタッフ | 持たない。Layer 3 ローテーションで毎週決定（§3.6.8 参照） |
| ON DELETE CASCADE | 患者削除時に関連する固定枠も自動削除 |
| mode='special' | `patients.special_week_active` に当該週が含まれる場合のみ適用される。未設定時は mode='normal' にフォールバック（§3.6.8 参照） |

#### patients テーブルとの関係

```
patients (1) ──── (0..7 rows × 2 modes) patient_fixed_visits
               ┌─ normal:  曜日ごとに最大 7 行（月〜日）
               └─ special: 曜日ごとに最大 7 行（月〜日）
```

`patient.has_fixed_visits(mode)` の評価は、
`SELECT COUNT(*) > 0 FROM patient_fixed_visits WHERE patient_id = ? AND mode = ?`
で判定する（Layer 1 hybrid 化 / §3.6.8）。

### 4.3 拠点 (Office)

#### 拠点の定義

- 「事務所の拠点」を表す概念。現状は **稲毛 / 都賀** の 2 拠点
- 各拠点は地理的な担当範囲（市区町村単位）を持つ
- 患者は住所から自動で拠点に紐付く（手動上書き可）
- スタッフは主拠点として 2 拠点のいずれかを選択（事業所から出発が前提、自宅起点は廃止）

#### 拠点マスタ

| 項目 | 用途 |

| 拠点 ID / コード | 一意識別 |

| 備考 | 自由記述 |

#### スタッフ → 拠点

- スタッフマスタの「主拠点」フィールドにて、拠点マスタの中から

- スタッフの自宅住所は v2 では管理しない（§4.2 削除済み）
- 距離計算の起点は **常に主拠点の住所**

#### 患者 → 拠点（自動紐付け + 手動上書き）

##### 自動紐付けの流れ

- UI 上で管理者が任意に拠点を変更可能

### 4.5 コース (Course)

#### 概念

- **対象期間**: 1 週間 × 1 曜日
- **構成**: A〜D の 4 つ（または稼働スタッフ数に応じた個数）

| `staff_assigned` | Layer 3 完了、スタッフ割当済み | （週終了でアーカイブ） |

タイムスタンプ補助カラム：
- `course_fixed_at`: 構成固定日時
- `staff_assigned_at`: スタッフ割当日時

- `courses` テーブル: 識別 + 状態 + 担当スタッフ ID

  - `course_fixed_at`, `staff_assigned_at` timestamps
- `visit_staff_assignments` テーブル: visit × staff の多対多（2 名体制対応）

  - `course_id` FK NULL（コースに属する訪問）

|---|---|---|
| Layer 1 | プール展開 + マスタ展開 | 単純展開 |
| Layer 2 | コース分け（クラスタリング + 制約） | 半自動（人補正） |
| Layer 3 | スタッフ割付（ローテーション付き割当問題） | 全自動 |

### 5.2 Layer 1 アルゴリズム: プール展開

#### 入力
- 患者マスタ（`weekly_pattern` 含む）
- 当該週の ISO 年 / 週

#### 処理
- 既存患者の `weekly_pattern` を読み、当該週の `visits` を生成
- 特別週フラグが立っている場合は `special_weekly_pattern` を使用
- 新規患者（パターン未確立）は保留プールに `patient_id` を入れる

#### 出力
- 時刻配置済み visits の集合
- 保留プール（未配置の patient_id 集合）

#### 計算量
- O(N_patient) — 既存ロジックの単純展開

### 5.3 Layer 2 アルゴリズム: コース分け

#### 入力
- 当該曜日に時刻配置された visits リスト `[(patient_id, time, lat, lng, service_min)]`
- スタッフ数 N（= コース数）
- 各拠点座標

#### アルゴリズム候補

| # | 手法 | 利点 | 欠点 |
|---|---|---|---|
| (i) | K-means クラスタリング + 制約後処理 | 実装容易、計算高速 | 6 人上限・時間衝突は後処理で吸収 |
| (ii) | 巡回セールスマン (TSP) ベースの近傍法 | 各コース内のルートが最適化 | コース間の総距離は二次最適化 |
| (iii) | CP-SAT（OR-Tools） | 全制約を同時最適化 | 実装やや重、計算時間が長くなる可能性 |

**MVP は (i)、将来的に (iii) で精度向上** を推奨。

#### ハード制約

- 1 コース 6 名以内（**Q1 確定後**: 単純カウント / 時刻スロット固定 / 枠消費 のいずれか）
- 同コース内の時間衝突なし（移動時間込みで検証）

#### ソフト最適化

- コース内の総移動距離最小化
- 時間希望充足（午前希望の患者が同じコース内で午前帯にまとまる）

#### 出力
- `[(course_code, [patient_ids], total_distance_km, validity_score)]` の案リスト

### 5.4 Layer 3 アルゴリズム: スタッフ割付

#### 入力
- 確定済みコース構成 `[(weekday, course_code, patients)]`
- 稼働スタッフリスト（性別 / 役割 / 勤務曜日 / 主拠点）
- 過去 N 週のローテーション履歴
- 各患者の性別制限

#### アルゴリズム
- **ハンガリアン法**（`scipy.optimize.linear_sum_assignment`）ベースの二部マッチング
- 各 (weekday × course) を行、各 staff を列とした コスト行列を構築

#### コスト関数

```
cost(weekday, course, staff) =
    α × distance_score(staff の主拠点 → コース重心)
  + β × rotation_penalty(staff × course の最近 N 週の担当回数)
  + γ × gender_mismatch_penalty(該当があれば INF)
  + δ × work_day_violation(勤務曜日違反は INF)
```

#### ハード制約
- 性別制限: 患者の性別制限を満たすスタッフのみ
- 勤務日: スタッフが当該曜日に勤務している
- 単一性: 1 スタッフは 1 日 1 コース
- 役割: マネージャー (M1) は対象外

#### ソフト最適化（Q3 ローテーション強度に依存）
- **強制モード**: 直近 N 回担当者は除外（候補から消す）
- **ソフトモード**: 最近担当ほど高ペナルティ
- **ハイブリッド**: 直近 1 週は強制除外、それ以前はソフト

#### 出力
- `[(weekday, course_code, staff_id)]` のマッピング表

#### 計算量
- ハンガリアン法は一般に **O(n³)**（n = max(C, S)）。1 曜日あたりの計算量は O(max(C,S)³)、
  全曜日合算で **O(W × max(C, S)³)**。実用規模（W=6, C/S=4-6）では瞬時

### 5.5 アルゴリズムの差し替えポイント

各レイヤーは独立しているため、将来的に差し替え可能：
- Layer 2 を MVP 後に CP-SAT 化
- Layer 3 にメタヒューリスティクス（焼きなまし法等）を追加して品質向上
- Layer 1 はシンプルなので変更不要

## 6. UI / UX 仕様（暫定）

### 6.1 スケジュール表

- 縦軸: 時刻（08:00 〜 20:00、**15 分刻み**: MVP 確定）
- 横軸: 曜日 × スタッフ（または曜日のみで Step B、スタッフ列は Step D で展開）
- 表下部: 保留プール（カード溜まり領域）

### 6.2 ドラッグ操作

- 保留プール → 時間スロット: その曜日のその時刻に固定
- 時間スロット間: 時刻変更
- 時間スロット → 保留プール: 配置解除
- スタッフ列間（Step D 後）: 担当変更

### 6.3 固定ボタン

- 押下時の動作: その週のレイアウトをすべての患者の週間パターンに保存
- 確認ダイアログ: 「○名の週間パターンを更新します」
