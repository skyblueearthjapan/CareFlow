# 今週のスケジュール空間(週空間)設計書 — コース貼り付け盤面とカイポケ双方向同期

作成: 2026-08-21 / ステータス: ドラフト(PO確認事項 §9 あり)
関連正典: kaipoke-event-two-way-design.md / pin-and-movability-spec.md / kaipoke-reverse-sync-design.md

## 1. 背景と目的

らく助は「最短ルートに最適化された固定コース(マスタ)」と「毎週のイレギュラー
(急な休み・キャンセル・前倒し)」の間にチグハグがあり、実運用に乗せきれていない。

本設計は次の二層を**思想として完成**させる:

| | マスタ層(理想形) | 週空間(現実・今週) |
|---|---|---|
| 実体 | patient_fixed_visits(PFV) / course_templates / staff_event_defaults | courses(週スカラー持ち) / visits / visit_staff_assignments / staff_events |
| 性質 | 恒久・最適化対象・研ぎ澄まし | 週単位・柔軟・任意に動かせる |
| 関係 | 週生成(Layer1)で週空間へ**展開** | 明示操作でのみマスタへ**昇格** |
| カイポケ | **触れない(汚さない)** | 取込も送信もここだけ |

**重要な前提(2026-08-21調査結果)**: この二層は既に実装の骨格として存在する。
カイポケ取込(訪問=inbound.py / イベント=events_inbound.py)は週層にしか書かず、
手動DnDも visit-move-week-only(source='manual_week')が既定で、マスタ反映は
ChangeScopeChoice の明示2択のみ。本設計は「新規二重DB構築」ではなく
**(A)週空間の操作性拡張 (B)マスタ漏れ道の封鎖 (C)カイポケ双方向の統合**の3本柱。

北極星(PO 2026-08-21): **カイポケとらく助が常に同期している状態**。
イベント/スケジュールを片方・両方・一部(患者単位/コース単位)で任意に送受信できる。

## 2. 現状調査サマリ(実装の事実)

- `visits` に週カラムは無い(`visit_date`範囲で週を導出)。`courses` は
  `iso_year+iso_week+weekday` を持つ = **週空間の「コース配置」の実体は courses**。
  `courses.assigned_staff_id` が週内のコース担当(Layer3が書く)。
- 職員スケジュールタブ(StaffWeekBoard)は既にスタッフ行×曜日列。
  行の決定は `courses.assigned_staff_id` の投影(visit.primary_staff_id ではない)。
  イベント=正典(staff_events CRUD)/ 訪問=read-only 投影。
- 週生成/固定枠戻しは manual_week・import・青ピン(week_pinned)を保護して壊さない。
  取込は inbound_snapshots で復元可。最適化エンジンは全て read-only 提案型。
- **マスタへの書込経路は11本**存在(§6の棚卸し表)。最危険は
  `DELETE /visits/{id}?cascade_fixed_visit=true`(週の1件削除がPFVを物理削除)。
- 訪問の外部キー: `visits.kaipoke_id` 既存。イベントは `staff_events.external_id`
  + source昇格(送信済=source='kaipoke')の型が完成済み。

## 3. コンセプト: 週空間の憲法(不変条件)

1. **週空間の操作はマスタを一切変更しない**(デフォルト週のみ)。
   マスタ反映は ChangeScopeChoice 経由の明示昇格のみ(PO確定 2026-08-21)。
2. **カイポケ送受信の相手は常に週空間**。PFV/テンプレ/イベント既定には触れない。
3. 週生成(展開)は週空間の手作業(manual_week/import/青ピン)を保護する(現行踏襲)。
4. 同じ事実を二重に持たない。週空間=courses+visits+staff_events が唯一の「今週の正典」。
5. ピン2軸は現行維持: 赤=マスタ属性(エンジン不可侵・人手は自由)/
   青=週属性(今週この位置のまま・人手もブロック)。

## 4. UI設計: 職員スケジュールタブを「今週の組み立て盤面」へ(PO確定: 別画面は作らない)

### 4-1. レイアウト(POのUI像 2026-08-21)

```
┌─ 職員スケジュール(今週) ──────────────────────────┐
│ [⇩カイポケ取込] [⇧カイポケ送信] [自動で割り当てる] [週生成]      │
├──────────┬─月─┬─火─┬─水─┬─木─┬─金─┬─土─┤
│ 川名        │(空)  │稲毛A │(空)  │…    │      │      │ ← スタッフ行
│ 熊澤        │稲毛B │(空)  │…    │      │      │      │   セル=コース帯+イベント帯
│ …在籍全員   │      │      │      │      │      │      │   (休みはグレー表示)
├──────────┴──────────────────────────┤
│ ▼ コースの表(パレット)  — この週のコース一覧                    │
│  未割当:  [稲毛A(水)] [都賀B(月)] [臨(金)] …  ← ドラッグ元        │
│  割当済:  [稲毛A(火)→川名] [稲毛B(月)→熊澤] … (グレー・掴んで付替可) │
└─────────────────────────────────────┘
```

- 上段 = 現行 StaffWeekBoard と同じ配列(在籍全員行×月〜土)。週生成直後は
  courses.assigned_staff_id が NULL のため**全セル空(未割当)から始まる**。
- 下段 = **コースパレット**(新設)。この週の courses を曜日つきカードで列挙。
  未割当カードを上のセルへドラッグ&ドロップで「ペタッと貼る」。
- 貼られたコースはセル内にコース帯として表示(配下の患者訪問を積んで表示)。
  イベント帯は現行どおりこの画面が正典。

### 4-2. 操作と意味(すべて週のみ・マスタ不変)

| 操作 | 意味 | BE |
|---|---|---|
| パレット→スタッフセルへコースをドロップ(同曜日列) | 今週のコース担当を設定 | 新API: course-assign-week(courses.assigned_staff_id + 配下visitsのVSA/primary同期) |
| 別スタッフのセルへ既割当コースをドラッグ | 今週のみ担当付け替え | 同上(reassign) |
| コース帯をパレットへ戻す | 未割当化 | 同上(assigned_staff_id=NULL+VSA解除) |
| **別曜日列**へコースをドロップ | コース丸ごと曜日スライド(今週のみ) | 新API: course-move-weekday-week-only(配下visits一括 manual_week 移動 + courses.weekday) ※Phase A2・要検証 |
| 患者訪問1件をセル間/曜日間ドラッグ | 個別の貼り替え | 既存 visit-move-week-only + 担当変更(拡張) |
| セルの＋ | イベント追加(現行) | 既存 staff_events |
| [自動で割り当てる] | Layer3で空きコースを一括貼り | 既存 assign-staff-only(このボードから起動可に) |

- **自動と手動の融合**: Layer3(自動割当)は「パレットの未割当を自動で貼るボタン」
  として同じ盤面に同居。自動で8割貼り、イレギュラーだけ手で貼り替えるのが定常運用。
- 警告(ブロックしない・親切に知らせる方針を踏襲):
  休み(staff_weekly_overrides)の日への貼付/blockingイベントとの重なり/
  患者時間帯の衝突/NG・性別(既存Layer3判定の流用)。青ピン訪問の移動のみ422。
- 昇格導線: 良い形ができたら現行トースト「毎週の型にも登録」= bulk-sync-week-to-fixed
  (患者単位)。コース担当の型化(course_template既定担当)は現状概念が無いため対象外
  (§9 PO確認)。

### 4-3. 作らないもの

- 別画面・別DB・「仮想空間」用の新スキーマ(courses+visitsが既にその実体)。
- 週空間からの自動昇格(サイレントにマスタが変わる経路は増やさない)。

## 5. データ/API設計

### 5-1. 新規テーブル: **なし**(コア機能)

コース貼り付け=courses.assigned_staff_id(週スカラー持ちで元々週限定)。
訪問移動=既存 manual_week 機構。イベント=staff_events。すべて既存実体で足りる。

### 5-2. 新規/変更API

1. `POST /schedule/v2/course-assign-week` — {course_id, staff_id|null}
   今週のコース担当設定/解除/付替。配下visits(週内・生存)の VSA+primary_staff_id を
   トランザクション内で同期。警告一覧(休み/イベント/NG)をレスポンスで返す。
   ※既存の担当変更系(reset-to-fixedコース担当同期の教訓 2026-07-11)と整合させること。
2. `POST /schedule/v2/course-move-weekday-week-only` — {course_id, to_weekday}
   配下visits一括で visit_date 移動(source='manual_week')。移動先に同code course が
   既存なら422(まず単純ケースのみ)。青ピン配下ありは422。 ※Phase A2
3. `GET /schedule/v2/week-course-palette` — {year, week} → コース一覧
   (code/template/weekday/assigned_staff/患者数/合計分/警告サマリ)。
   既存 week-visits 系レスポンスの拡張でも可(FE都合で決定)。
4. 職員スケジュール取込/送信ダイアログの対象拡張(§7)。

### 5-3. source カラムの整理(小規模・任意)

`manual_week` が「出所」と「週限定フラグ」を兼務するハックは当面現状維持
(青ピン解除時の manual_week→auto 書戻し含む)。週空間の思想では全visitsが
「週限定」なので、将来 `origin`(auto/manual/import) と保護規則を分離する余地のみ
書き残す。**今回は触らない**(週生成保護規則が壊れるリスク > 綺麗さ)。

## 7. カイポケ双方向同期の統合(北極星: 常時同期)

### 7-1. 統合ダイアログ(スケジュール画面)

「⇩カイポケ取込」「⇧カイポケ送信」を**対象選択式**に拡張:

```
対象:  [✓] イベント   [✓] スケジュール(訪問)
範囲:  (・) 今週すべて  ( ) 患者を選ぶ…  ( ) コースを選ぶ…
→ プレビュー(差分+重なり警告) → 実行(202+job_idポーリング型)
```

- 取込(inbound): イベント=完成済み。スケジュール=既存 smart-inbound
  (日単位ハイブリッド・打刻日保護・スナップショット)を職員スケジュールの
  ダイアログから起動可にする。**書込先は週空間のみ**(現行仕様のまま=憲法適合)。
- 送信(outbound):
  - イベント=完成済み(preview→start→status→external_id昇格)。
  - **訪問送信=新規**。イベント送信と同じ型(preview→202→ポーリング→昇格)で、
    差分単位は訪問1件。範囲フィルタ(患者/コース/週)はpreview段階で絞る。
  - RPA制約(現行実測): 単一スロット(取込と送信の同時不可)・イベント1件約40秒。
    訪問も同オーダーと仮定→大量送信はキュー化+進捗表示必須。

### 7-2. 訪問の同期キー設計(Phase C 実装前提の下敷き)

- 取込方向は `visits.kaipoke_id` が既存。送信方向もこれを唯一キーに統一:
  送信成功→カイポケ採番IDを `kaipoke_id` に刻む(イベントの external_id 昇格と同型)。
- 差分判定 = 週空間visits(kaipoke_id有無/内容) vs カイポケ週間スケジュール実機パース。
  三態: らく助のみ(→新規登録) / 両方で不一致(→更新 or 警告) / カイポケのみ(→取込 or 削除提案)。
- 「常時同期」はこの差分エンジンの定期実行(Phase D)。まず手動任意送信で運用を確立する。

### 7-3. 突合ビュー(差分モード)— 同期のハブ(PO要望 2026-08-21)

「取込か送信か」を先に選ばせるのではなく、**まず2つを突き合わせて差分を見せ、
差分1件ごとに方向を選ぶ**。§7-1のダイアログは入口で、実像はこの突合ビュー。

**フロー**: [🔄 カイポケと突合] → RPAで当週のカイポケ側(イベント+週間スケジュール)を
取得(202+job_idポーリング・単一スロット)→ らく助週空間と突合 → 盤面に重ね表示。

**差分の4態と盤面上の視覚表現**(職員スケジュールタブに「差分モード」トグル):

| 状態 | 意味 | 表示 |
|---|---|---|
| ✅ 一致 | 両方に同内容 | 通常表示(彩度を落として差分を目立たせる) |
| 🟡 不一致 | 両方にあるが時刻/担当/時間が違う | 帯を黄枠+「カイポケ: 10:00→」ツールチップ |
| 🔵 らく助のみ | こちらにだけある(未送信) | 帯に青ドット/「⇧未送信」バッジ |
| 🟣 カイポケのみ | カイポケにだけある | **紫破線のゴースト帯**を該当セルに描画(こちらに無いものを盤面上に見せる) |

盤面と連動する**差分リストパネル**(右側)も併設: 1行=1差分
(誰の/何曜/何時/内容/状態)。行クリックで盤面の該当帯へスクロール&ハイライト。

**差分1件ごとの方向選択**(リスト行・帯クリックの両方から):

```
🟣 熊澤 火 14:00 田中様 60分 (カイポケのみ)
   [⇩ らく助へ取り込む] [無視(今回のみ)]
🟡 川名 月 10:00 佐藤様 (らく助10:00 / カイポケ10:30)
   [⇩ カイポケに合わせる] [⇧ らく助に合わせる(送信)] [無視]
🔵 稲毛B配下 3件 (未送信)
   [⇧ まとめて送信] [無視]
```

- チェックボックスで複数選択→「選択分を実行」一括も可(取込分と送信分を
  内部で2ジョブに分けて直列実行=単一スロット制約)。
- 実行は既存機構に接続: 取込=smart-inbound/events-inbound-apply(対象を差分選択で
  絞る)・送信=events-outbound/訪問送信(Phase C2)。**新しい書込経路は作らない**。
- 突合キー: イベント=external_id、訪問=kaipoke_id、キー無しは
  (患者×日付×開始時刻)ヒューリスティックで対にし、確信が持てない対は
  「🟡不一致(要確認)」に倒す。
- **鮮度**: RPA取得はスナップショット(取得に1〜2分)。ビューに「カイポケ側:
  HH:MM時点」を常時表示し、実行前に古い(>15分等)場合は再突合を促す。
  実行後は該当差分行を即時解決表示(✅化)し、全件再取得は強要しない。
- 打刻済み日はカイポケに合わせる取込から保護(smart-inbound現行仕様の踏襲)。

この突合ビューの定期自動実行+「差分あり」通知が Phase D の常時同期の実体
(自動で方向を決めない。決めるのは人・既定方向の自動化は運用が安定してから)。

### 7-4. RPA前提(Phase C 着手前に Phase 0 プローブ必須)

カイポケ週間スケジュールへの訪問「登録/変更/削除」ポップアップの実機構造採取
(イベントで確立した手法: 遠い未来日+テスト書込→採番ID回収→即削除・ユーザー承認の上)。
訂正シートRPA(月次実績)とは別経路であることに注意。既存 individual_tasks_apply.py の
構造(showIndividualAdd→保存→再パースでID回収)が最有力の参考実装。

⇧送信方向は既存の送信ダイアログ(イベント)のみ — C2 で差分単位化。

マスタは汚れない」という思想が現場で回り始める。C1は送信RPAなしで先行可能
(取込側の既存資産だけで突合と方向選択の運用が始められる)。

## 9. PO確認事項(未確定)

1. パレットのコース単位: 現状courseは(code×曜日)行。パレットは曜日別カード
   (稲毛A(月)/稲毛A(火)…)でよいか、コード単位に束ねて見せるか。

3. 休みのスタッフに貼った場合: 警告のみ(貼れる)でよいか。
4. コース分割・合成(一部患者だけ切り出し等)はPhase A2に含めるか後回しか。
   ※個別訪問の貼り替えができれば実質可能(コース単位の名前を付けるかの問題)。
5. 訪問送信の初回スコープ: 予定01のみ・実績02は対象外(イベントと同じ整理)でよいか。
6. カイポケのみに存在する訪問を送信previewで検出した場合の既定動作
   (取込を促す/無視/削除提案)。
7. 「稲毛Bを熊澤さんの月曜に」で移動先に既に同codeコースがある場合の扱い(当面422)。
8. 突合ビュー(§7-3)の差分表示: 盤面色分け+右リスト併設の案でよいか。
   4態の色(黄=不一致/青=未送信/紫破線=カイポケのみ)の見え方は実装時にモックで確認。
9. 不一致(🟡)の既定推奨方向: 現状方針は「取込=カイポケが正」だが、週空間を
   組み立てた直後は「らく助が正」のはず。**「どちらが正か」は差分ごとに人が選ぶ**で
   よいか、時期ルール(送信前はらく助正/送信後はカイポケ正)を設けるか。

## 10. リスクと整合性

- **Layer3との整合**: course-assign-week は Layer3 の書込先(assigned_staff_id+VSA)と
  同一。相互上書きは「後勝ち」でよいが、Layer3の既割当保護仕様
  (layer3_assignment.py W25 Bug#2)と同じ議論=「手貼り済みコースを自動割当が
  動かさない」ことをテストで保証。
- **週生成との整合**: 手貼り後に週生成再実行→courses行は保持(find-or-create)だが
  assigned_staff_id の扱いを確認・保証(消えないこと)。
- **二重化根絶**: 訪問送信の昇格(kaipoke_id刻印)漏れ=次回取込で二重行。イベントで
  実証済みの「送信成功応答からID回収→同トランザクション刻印」を厳守。
- **RPA単一スロット**: 取込と送信の同時実行不可はダイアログUIで排他表示(現行踏襲)。
- 表記: 正式名称は「らく助」(「楽スケ」と書かない)。
