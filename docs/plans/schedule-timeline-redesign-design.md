## 0. PO の意図（確認済み）

スケジュール画面（本アプリの顔）を「**見えて、触れて、使いたくなる**」UIへ刷新する:
時間間隔が見える / 空き間隔が見える / 直感的に動かせる / 清潔感・さわやか /
性別が色で見える / 複数人対応が人マークで見える。
ただし**スケジュール表示は多数の画面で再利用されているため、全箇所のリサーチと
慎重な段階導入が必須**（プロダクトを破綻させない）。

**本質の読み**: プロトタイプ（ZEST型）の革新は装飾ではなく**「時間を長さで描く」**こと。
訪問カードの高さ=所要時間、カードの間=移動と余白。つまり**余白の原則が初めて目に見える**。
「余白のあるスケジュールはそもそも詰まらない」という本ソフトの中核思想を、
毎日見る画面そのものに埋め込む刷新である。

## 1. 現状調査（UI棚卸し・2026-07-07 完了）

スケジュール可視化は **4系統・約25箇所**:

- **(a) コース×曜日テーブル系**（15分刻み固定行・時間比例なし）= PC本番 `CourseDayTable`(1,509行) +
  中枢 `CourseDayTablePanel`(2,818行・全DnD/データ変換ハブ) + 週 `CourseWeekOverview` + 提案系ダイアログ群
- **(b) リスト系** = `WekdayScheduleCard`（リスト表示共有コア・3箇所）・`CourseMoveTimeline`
  （提案タイムライン共有コア・4画面）・モバイル自己予定
- **(c) 比例ガント系** = **`MonitorTimeline` のみ**（横型・`minutesToPct`/`assignVisitLanes` =
  時間比例の算法が既に本番稼働。**縦に転置すれば新コアの心臓部になる既存資産**）
- **(d) 現場ボード** = `FieldBoard`（空き枠カードは `computeFreeGaps` を共有済み）

その他: kaipoke週ビュー/差分（独立・読み取り専用）・受入マトリクス（隣接）・
レガシー未マウント群（WeekGrid ほか5件＋DiffAdd 3件 = **削除候補**）。

**含意**:
1. 「時間比例の描画」も「空き枠計算」も**ゼロから発明しない**（Monitor と freeGaps に実績あり）
2. 破綻リスクの中心は `CourseDayTable/Panel`（DnD・全ダイアログ起動のハブ）→ **最後に触る**
3. 提案系は `CourseMoveTimeline` と `WeekdayScheduleCard` の2共有コアに集約済み →
   ここを新コアに載せ替えれば**4〜5画面が一括で新意匠**になる

## 2. ビュー切替の設計（PO対話で改訂・2026-07-07）

**最終形は「統合」**（PO方針: ビューをいたずらに併存させない）。
テーブルと週ビューは**移行期の足場**であり、タイムラインが実務パリティに達したら撤去する。

```
最終形:
[期間]   日                        週
[見え方] タイムライン | リスト      週タイムライン
         （テーブル・旧週ビューは撤去済み）

移行期のみ:
[見え方] タイムライン | テーブル | リスト   （週: 週タイムライン | 旧週ビュー）
```

- **テーブル → 撤去**: テーブル固有の問い（構成・定員）はタイムラインの列ヘッダ
  （担当・件数・定員 x/6）とカード積層で吸収できる。DnD編集もタイムラインの方が本質的に優れる
  （時間軸に直接落とせる）ため、パリティ達成後に固有価値が残らない
- **旧週ビュー → 週タイムラインに置換**: 俯瞰の問いは「6日分の縦タイムラインを横に並べる」
  形（ZEST参考画像の週表示と同型）が上位互換
- **リスト → 当面残す（唯一の併存）**: 照合・請求・印刷的な「漏れなく確認」はカード面積に
  依存しない密な一覧が強い（ZEST自身が後からリストビューを追加した事実が傍証）。
  さらにリスト実装（WeekdayScheduleCard）は提案ダイアログ群が部品として使うため、
  コンポーネント自体はいずれにせよ存続する = 残すコストがほぼゼロ。
  タイムライン定着後に利用実態を見て、不要なら畳む
- **撤去の条件（パリティチェックリスト）**: プール配置DnD / 担当割当レビュー / ピン留め /
  undo・redo / 定員・警告表示 / 全ダイアログ起動 / イベント移動 — が
  タイムライン上で全て可能になり、現場が数週間タイムライン既定で運用できたこと
- 期間を切替えても選択日/週の状態は維持。見え方の選択はユーザーごとに記憶
- 他画面からの遷移・ダイアログは移行期は従来ビューを開き、撤去時に一斉に切替

## 3. アーキテクチャ方針

- **新共有コア**: `lib/scheduling/timeline.ts`（Monitor の比例算法を抽出・縦転置 +
  freeGaps 連携）+ `components/schedule/timeline/`（TimelineDayBoard / TimelineColumn /
  VisitCard / FreeSlot / EventBand / OffDutyHatch）
- **データは既存のまま**: `CourseDayTablePanel` が既に visits→表示形式の変換ハブなので、
  タイムライン用の変換を1形式追加するだけ。**ソルバ・API・集計は一切触らない（表示革命）**
- **DnD 契約は既存APIを維持**: 空き枠タップ→登録 = place-and-fix / カード移動 =
  既存の delete+place-and-fix・visit-move-week-only / イベント移動 = update-event。
  droppable の座標系だけ「15分固定行」→「連続時間軸のスナップ（15分）」に変わる
- **性別基盤（新規）**: `patients.gender` / `staff.gender`（nullable・未設定=中立色）+
  マスタ編集UI + （可能なら患者Excel取込へのマッピング追加）。カード色=**患者**性別、
  列ヘッダのアバター色=**スタッフ**性別（プロト準拠）
- **2名体制**: 人マーク×2 + ペアバッジ（既存①②/ペア情報を流用）

## 5. リスクと歯止め

1. ソルバ・集計・API不変（純粋に表示層）— 棚卸しで表示と計算の境界は確認済み
2. 既存ビュー温存+切替式 → いつでも戻れる（ロールバック=タブを切り替えるだけ）
3. DnDの座標系変更は T-2 に隔離（T-1は読むだけ）

5. 中枢2ファイル（CourseDayTable/Panel）の縮退・置換は最終段まで行わない

## 6. PO 確認事項（着手前）

1. **性別データの入力**: 患者・スタッフ両方に性別カラムを新設し、マスタ画面で入力する
   （患者は既存Excel取込に性別列を足す手もある）。**入力作業はPO側で可能か**
2. **列の単位**: プロトは「列=スタッフ」。CareFlowの日ビューは「列=コース（担当スタッフ表示）」が
   自然（コースが運用の単位のため）。**ヘッダ=担当スタッフ名を主・コース記号を従**、で良いか
3. **時間軸レンジ**: プロト 9:00〜18:00 / 現行テーブル 9:30〜18:00。9:00〜18:00 に統一で良いか
4. **T-1 の開始点**: 本丸のPC日ビュー（切替式・読み取り専用）から始めて良いか
5. 「会議・イベントを登録」ボタン（プロトにあり）: 既存の staff_events 登録動線との関係を
   どうするか（当面は表示のみ・登録は既存動線でも可）
