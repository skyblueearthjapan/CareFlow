## 0. PO の相談内容（意向・確定済み）

現行は CareFlow → カイポケ の一方向反映（月間展開 → 週差分 → 週apply）。
週分をカイポケに反映しサービス提供が始まると、キャンセル・時間変更などの単発変更は
**カイポケ上で直接編集する方が速い**ため実際そうしており、カイポケ側が最新になる。
→ カイポケの現況エクスポート(CSV)から **カイポケ → CareFlow へ取り込み**たい。

**本質 = 「週のバトンリレー」**: 未来の週は CareFlow が正（送る）。週apply がバトンタッチで、
提供中の週はカイポケが正（取り込んで追いかける）。

```
        未来の週                提供中の週               過去
  ┌──────────────────┐   ┌──────────────────┐   ┌──────────┐
  │ CareFlow が正     │ → │ カイポケが正      │ → │ 実績     │
  │ 反映: CF→カイポケ │   │ 反映: カイポケ→CF │   │          │
  │ 粒度: 週          │   │ 粒度: 日（柔軟）  │   │          │
  └──────────────────┘   └──────────────────┘   └──────────┘
        週apply が「バトンタッチ」の瞬間
```

## 0-b. PO回答ラウンド1（2026-07-06・確定事項）

1. **取り込み許可 = apply実績ゲート**: CareFlow側で差分確認→カイポケへ反映（実apply）した
   **実績のある週のみ**取り込み可。過去・未来の週は不要、**今週のみ**の対応で良い
2. **その週限りの原則で確定**: 固定枠（PFV）は変更しない。カイポケ側で消えた予定は
   「キャンセルの可能性が高い」ため**キャンセル履歴を残す表示**にする。
   ただし **CareFlow に「キャンセル」というユーザー向け概念がまだ無い**ため、
   PC版・モバイル版での見せ方を含め設計する（§4）
3. **手動ボタン実行**（自動取り込みしない）。2名体制は「2名分のスケジュール」として
   素直に処理する方針（実CSVデータで一度確認する）
4. **粒度**: 取り込み側=日単位が主目的・送る側=週単位のまま（現行①〜④は不変）。
   日単位取り込みはイレギュラー動作なのでメインボタン群と**分離配置**。
   曜日は複数選択可（月のみ／月火／…／月〜土全部まで柔軟に）

### 1-2. 新規に作る必要があるもの

1. **インバウンド・アプライヤ（心臓部・唯一の本質的新規）**: Correction → CareFlow visits 書込。
   現状カイポケCSV→visits の書込経路はゼロ。参考実装: `pending_request_applier.py`
   （`_apply_patient_cancel` = status='cancelled'、`_apply_patient_reschedule` = 時刻/担当更新、
   `_apply_visit_add_onetime` = 保護sourceでINSERT）
2. **スタッフの名寄せ**: 患者は match_name 流用可。スタッフ名→staff.id は
   `build_name_index` を staff に適用して新設
3. **取り込みUI**: 曜日チップ複数選択＋❶差分❷確認❸取り込み（§5）
4. **キャンセルの表示**: PC/モバイル/現場ボードでの見せ方（§4）

### 1-3. CareFlow 側の受け皿（確認済みの事実）

- `Visit.status` に `'cancelled'` は**データモデル上は初期から存在**（`visit.py:51`）。
  cancelled と source!='auto' の visit は**週再生成から保護される**（layer1_expander 実装済み）
- ただし表示層は現状 cancelled を**ほぼ出さない**（= PO認識「キャンセル概念が無い」は表示層で正確）:
  - 現場ボード: `Visit.status == planned` のみ表示（`board_service.py:140`）→ cancelled は消える
  - ダッシュボード集計・訪問モニター・CSV生成: cancelled 除外
  - **モバイル訪問カードだけ「取消」バッジの器が既にある**（`MobileVisitCard.tsx:23`・未使用）
- 訪問モニター・健康診断・警告は全てオンデマンド計算 → 取り込み後の再計算トリガー不要

### 1-4. 制約・弱点（設計で受け止める事実）

1. **カイポケCSVに内部IDが無い** → 突合は「利用者名×日×サービス内容×開始時刻」の合成キー
   （現行差分と同方式・実績あり）。曖昧なケース（同一患者・同日・同種複数訪問）は
   自動反映せず「要確認」行として人に判断を渡す
2. CSVの日付は「日」(1-31)のみ → 月コンテキスト必須（現行と同じ）
3. **2名体制はCSV1行⇔CareFlow2行**: カイポケCSVでは2名訪問は1行（職員名1＋職員名2・同行○）、
   CareFlow内部では visit_group_id で連結された2行。変換は csv_builder の逆写し。
   キャンセル・時刻変更はグループ丸ごと適用（片割れだけ残さない）。
   **R-0 で実CSVの2名行（577行中103行）を再確認**（PO指示）
4. export は月単位・単一スロット占有（~50秒）→ 曜日をどう選んでも取得は1回で済ませる（§5）
5. 実apply(dry_run=false)は本番未実施 → apply実績ゲートは初回実applyから自然に効き始める

## 2. バックエンド設計（新規は薄い）

- `POST /integrations/diff-inbound`（仮）: export → 対象週(月〜土)全体で CareFlow visits と突合 →

  - カイポケで消えた → `status='cancelled'`（履歴が残る。§4 の表示とセット）
  - 時刻・担当変更 → visit 更新＋`source='manual_week'`（再生成保護）＋note に出所刻印

  - dry_run 既定 true・applied 再適用409・要確認の可視化 — 現行の型を全て踏襲
- ジョブは op=`import_local` として KaipokeJob 履歴・通知基盤に載せる

## 3. 取り込みUI設計（分離配置・曜日柔軟選択）

カイポケ連携画面の**メインワークフロー（①〜④・送る側）はそのまま**。その下（または折りたたみ
セクション）に、方向が逆であることを視覚的に明示した**独立カード**を置く:

```
────────────────────────────────────────────
【送る】CareFlow → カイポケ（週の準備・週単位）
  ①展開 ②差分 ③確認 ④反映            ← 現行のまま
────────────────────────────────────────────
【取り込む】カイポケ → CareFlow（今週の追いかけ・日単位）   ← 新設・分離
  対象: 今週（7/6〜7/11）· apply実績 ✓
  曜日: [月] [火] [水] [木] [金] [土] [全部]   ← 複数選択チップ
  ❶カイポケの現況を取得して差分を見る
  ❷確認（カイポケが正・キャンセル/変更/追加）
  ❸選んだ曜日だけ取り込む（dry-run→実行）
────────────────────────────────────────────
```

- 文言案: 「カイポケでの直し込みを CareFlow に取り込みます。**今週の予定表だけ**を直します
  （定期パターンは変わりません）」
- 差分確認に方向バッジ「カイポケが正」を常時表示
- **実装方式**: 差分計算は週全体で1回（export 50秒×1）→ 曜日チップは item の絞り込み。
  これで「月のみ」「月火」「非連続（月＋水）」「月〜土全部」まで自由に対応
- apply実績が無い週はカード全体を無効化し「先に④反映（送る）を済ませてください」と案内

## 4. キャンセル表示の設計（新概念の導入・要PO確認）

前提: 取り込みで `status='cancelled'` が付いた visit が初めてユーザーの目に触れる。
「予定から黙って消える」のではなく「キャンセルされた事実が見える」ことが目的。

| 画面 | 現状 | 提案 |
|---|---|---|
| PC版スケジュール（コース表） | cancelled は概ね非表示 | グレー＋打消し線＋「キャンセル」バッジで**その場に残す**。定員・警告・重複計算からは除外（枠は空き扱い）。うるさければ「キャンセルを表示」トグル |
| モバイル 本日の訪問 | 取消バッジの器あり(未使用) | グレーカード＋「取消」バッジで残す — **担当スタッフが「行かなくていい」と気づける**ことが最重要 |
| 現場ボード(/m) | planned のみ表示 | 案A: グレーで出す（現場に周知される）/ 案B: 出さない（ボードは「行く予定」専用）→ **要PO判断** |
| 訪問モニター | cancelled 除外 | 除外を継続（実績管理の趣旨）。ただし「本日のキャンセル n件」の控えめな集計は将来候補 |
| 訪問詳細 | — | キャンセル出所を表示（「カイポケ取込により 7/6 キャンセル」= note の刻印を整形表示） |

補足: 手動キャンセル（CareFlow上でキャンセル操作する）UI は今回のスコープ外
（取り込み経由でのみ発生）。将来必要になれば同じ表示基盤に乗る。

## 8. R-3 設計（2026-07-07 PO合意・確定）

**PO とのやりとりで確定した核心（8-1 を全面改訂）**:
- スタッフ変更は「コースの変更」として扱う（PO指摘）。訪問単位の担当上書きは廃止
- 新担当がその日コースを持たない場合は**臨時コースを1本新設**して1人で対応する形に
  モデル化（PO発案）。コースは週×曜日インスタンスなので他週へ残らない
- 臨時コースの行名 = **専用コード「臨」（複数時は 臨2〜臨9）＋「臨時」テンプレート**
  （案3・PO選択）。コード CHECK 制約の拡張 migration が必要
- add の include 既定 = 患者・担当が名寄せ解決できた行のみ ON（コースは臨時新設で
  常に解決可能になったため実質2点）。着手順 R-3a→b→c

共通原則: カイポケは提供中の週の**正**なので、CareFlow側の警告（定員・重複）で
**ブロックしない**（現実に起きている予定を拒否しても意味がない）。警告は item の
comment に情報として残すだけ。適用順序は「キャンセル/変更 → 追加」
（予定が動いた場合に (patient,date,start) UNIQUE の玉突きを避ける）。

### 8-1. スタッフ変更の反映（R-3a・実装済みの確定設計）

**スタッフ変更は「コースの変更」として扱う**（PO指摘による全面改訂。当初案の
visit単位上書き＋manual_staff_override は廃止 — コース表と矛盾する表示になるため）。
3段構えで、すべてコースモデルの中で完結する:

1. **コース丸ごと交代**（事前検出）: 差分の中で「同じコース×同じ日の planned 全訪問」が
   同一の新担当への変更を示す → `Course.assigned_staff_id` を変更（週×曜日インスタンス
   なので影響はその週のその日だけ）。訪問はコースに残し、各 visit の primary も追従更新
   （揃えないと次回の送る方向差分で幽霊差分が出る）
2. **単発の担当変更**: 新担当がその週・その曜日・その拠点に持つコースへ
   `visit.course_id` を移動（コース索引 = (weekday, office, staff) 逆引き・コード昇順優先）
3. **新担当がその日コースを持たない**: **臨時コースを新設**して移す（§8-1b）

- 名寄せ: `load_staff_name_index`（患者と同一の match_name 機構・曖昧/不一致は
  その項目のみ未反映として注記）
- 担当2: 解決できたときだけ `secondary_staff_id` を反映（解除=空文字も反映）。
  `visit_staff_assignments` は担当セットで置換（重複IDは除去）
- 時刻＋担当の複合変更は1itemで両方適用。`source='manual_week'`＋note刻印は共通

### 8-1b. 臨時コース（PO発案・確定）

- コード = **臨 / 臨2〜臨9**（migration 0057 で CHECK 拡張）・テンプレート =
  各拠点の「**臨時**」（無ければ自動作成・定員0）・status=staff_assigned
- 同一スタッフ・同一日の2件目は既存の臨時コースへ相乗り（乱立防止)。臨〜臨9 が
  満杯なら failed として可視化
- 週×曜日インスタンスなので**他の週には残らない**。コース表では「臨時」テンプレ行に
  表示（FE照合に 臨2〜臨9→先頭「臨」ラベルの fallback を追加済み。複数の臨時コースを
  同日に行分けしたい場合は 臨2 等のテンプレを拠点に追加すれば exact match で分離できる）
- 色は M系（移動枠/臨時）のテラコッタへ自動フォールバック

### 8-2. add＝カイポケにのみ存在する予定の INSERT（R-3b）

- INSERT 内容: patient_id（名寄せ・未解決なら不可）/ visit_date（day→週レンジ解決）/
  start/end / type='regular' / status='planned' / **source='import'**（週再生成から保護・
  出所識別）/ note刻印「カイポケ側で追加された予定」
- **コース解決（表示の要）**: コース表は Course への join で描くため、course_id=NULL の
  visit はコース表に出ない。3段フォールバックで解決する:
  1. 職員名1 → staff 名寄せ → その週・その曜日・その拠点で当該staffが担当する
     Course（(iso_year,iso_week,weekday,office_id,assigned_staff_id) から逆引き）
  2. 同患者の同週・同曜日の他visitのコース
  3. 解決不能 → course_id=NULL のまま作成し「コース未割当」を comment に明示
     （モバイルの担当者予定には出る。コース表への反映は手動）
- スタッフ: primary_staff_id + VisitStaffAssignment を両方作成（v1/v2整合）
- include 既定: **患者・担当・コースの3点が解決できた add のみ ON**、
  それ以外は OFF＋不足要素をチップ表示（人が見て判断）
- (patient,date,start) UNIQUE 衝突（差分が古い場合）は IntegrityError を捕捉して
  failed item「既に同時刻の予定があります（差分を取り直してください）」

### 8-3. 2名体制行（R-3c・防御の完成）

本番CareFlowに2名体制visitは0件のため実質将来保険。方針は「CSV1行⇔visit1行」:
- add で職員名2あり → 1 visit に primary+secondary_staff_id・required_staff_count=2
  （csv_builder の送る方向と往復整合。visit_group 2行は作らない）
- edit の staff2 変更 → secondary_staff_id を 8-1 と同じ規則で上書き
- 職員名3（同行○/mentor）は出現実績なし → 要確認 comment のみ（自動反映しない）
- Layer1由来の visit_group 行が将来現れた場合は、既存のグループ丸ごと防御が
  キャンセル/時刻変更を面倒みる（実装済み）

### 8-4. 副次改善（R-3 と同時が効率的）

- delete+add ペアの綴じ込み: 日付も時刻も同時に変わった予定は engine が
  delete+add に分解することがある。R-3b があれば「キャンセル＋新規」で結果は
  正しいが、UI では「移動」として1行に綴じて見せる（outbound の
  companion_change と同じ発想・任意）
