### 2-1. 決まった値（画面では切り替えない）

- `CAP = 7`
- `PAD = config.visit_buffer_min + TRAVEL_GUESS_MIN`、`TRAVEL_GUESS_MIN = 12`（既定で前後 20 分）
- `LUNCH_LEN = config.lunch_duration_min`、`LUNCH_FROM = config.lunch_window_start`、`LUNCH_TO = config.lunch_window_end`
- `BIZ_START = config.business_start`、`BIZ_END = config.business_end`
- `STEP = 5`（分）
- 表に出す時間台 `HOURS = 9..17`。勤務が 8:30 始まりの人は 8:30〜8:55 の開始も計算するが、**8 時台は表に出さない**（試算どおり）。
- 見る曜日 = 拠点の営業曜日（`Office.operating_weekdays`。今は月〜土）
- 休みの種類・境目・件名の判定は **段階 0 の `app/core/leave.py`** だけを使う（§2-3）。受け入れ枠のコードに `13:00`・`12:30`・`== "off"` や件名の語を書かない（段階 0 §0-1）。

画面で選ぶもの（担い手・見る週・休みの扱い）は **サーバーには渡さない**。サーバーは職員 × 日 × 時台の「入れる」を全員ぶん一度に返し、画面がそれを集計する（M7・§4-1）。

### 2-2. 職員 × 日の材料（データの作り方は §3）

職員 `s`・日 `d` ごとに次を用意する。

- `shift` = `staff_shifts(s, d の曜日)`。行が無いか `is_on=false` なら、その日は **勤務日でない**（数えない・内訳にも出さない。決定 Q9）
- `win = [shift.start_time or BIZ_START, shift.end_time or BIZ_END]`（分）
- `src` = その日に使う記録（`actual` / `plan` / `plan_fallback`。§3-1）
- `visits` = その記録のうち、`s` が職員名１〜３のどれかに入っている行の `[開始, 終了]`。**行は拠点で絞らない**（他の拠点での訪問の時間も塞ぐ。H2・段階 0 §0-2）
- `n` = その日の件数 = **職員名１（主担当）** として入っている訪問の行数（同行＝職員名２・３は数えない）
- `events` = 予定（朝会など）の `[開始, 終了]`（§3-2 の決まりで集める。manual・fixed の予定は件名が休みでも時間を塞ぐだけ）
- `rk_off` = らく助の週だけの休み（`staff_weekly_overrides`。`override_type` が `leave.LEAVE_TYPES` のもの、または `custom_time`）
- `kp_off` = カイポケ個別業務のうち `classify_kaipoke_leave` が休みの種類（`off`・`paid_off`・`am_off`・`pm_off`）を返したもの。同じ日に 2 件以上あれば **いちばん広く休む 1 件**（終日 ＞ 半休。決定 Q10。試算のデータでは 1 日 1 件しか無い）
- `kp_unknown` = `classify_kaipoke_leave` が `"unknown"`（休みの語を含むが種類が分からない）を返したもの（§2-3）
- `not_employed` = その人が、見る範囲の材料の中で **その日より前にカイポケの行を一度も持っていない**（入職前とみなす。M10）

### 2-3. 休みの種類と境目（段階 0 の `app/core/leave.py` を使う）

段階 0 §0-1 で作られるもの（受け入れ枠は import するだけ・値を書き写さない）:

- `FULL_DAY_OFF = {"off", "paid_off"}`（有給も終日休み。M1）／`HALF_DAY_OFF = {"am_off", "pm_off"}`／`LEAVE_TYPES`（`custom_time` は休みではない）
- `leave_window(type, shift_start, shift_end) -> (work_start, work_end) | None`（終日なら None。午前休は `AM_OFF_UNTIL` から、午後休は `PM_OFF_FROM` まで）
- `classify_kaipoke_leave(subject, start=None, end=None, shift_start=None, shift_end=None) -> "off" | "am_off" | "pm_off" | "paid_off" | "unknown" | None`
  - 規則の全文と試験の正解の表は **段階 0 §0-1 だけ** にある（本書は書き写さない）。受け入れ枠は勤務の型の時刻を `shift_start`・`shift_end` に渡す。
- `is_leave_event(subject)`（`dashboard_staff_performance.py:89-100` の今の関数は、段階 0 でこれを呼ぶ薄い関数に置き換わる）

受け入れ枠での使い方:

| 材料 | 判定 | その日の窓 |
|---|---|---|
| override が `FULL_DAY_OFF` | 休み | なし（`leave_window` が None） |
| override が `HALF_DAY_OFF` | 半休 | `leave_window(type, 勤務の始まり, 勤務の終わり)` |
| override が `custom_time` | 時間変更（休みではない） | override の時刻 |

### 2-4. 移動の見込み（決定 Q1）

新しい患者さんの住所は使わないので、前後の訪問から新しいお宅までの移動は分からない。今のコードの考え方:

- 提案エンジン（propose-slots）は、前の訪問の終わりから `haversine_minutes(直線距離) + visit_buffer_min` 後を最も早い開始にする（`backend/app/services/scheduling/proposal_solver.py:203-238`、`:252-265`）。同じ建物（約 100 m 以内）は移動もゆとりも 0。
- `haversine_minutes` は `直線距離 ÷ travel_speed_kmh × 60` を丸め、最低 1 分（`backend/app/services/scheduling/auto_allocator_v2.py:671-686`）。速度の既定は 20 km/h（`constants.py:74`、`config.py:48`）。
- 職員の予定（イベント）は前後 15 分ずつ広げて塞ぐ（`proposal_solver.py:192` `EVENT_BUFFER_MINUTES = 15`、`:470-475`）。

**決定（ディレクター）**: 一律で前後 20 分（ゆとり 8＋移動 12。12 分は速度 20 km/h で約 4 km）。試算と同じ。予定の前後には足さない（決定 Q2・提案エンジンにはそろえない）。

後の段の候補（今回は作らない）:

| 案 | 中身 |
|---|---|
| B | 拠点の実際の移動から決める。見た週のカイポケの行を患者さんの座標（`patients.lat/lng`）に結び、同じ職員の続く訪問どうしの `haversine_minutes` の **中央値** を `TRAVEL_GUESS_MIN` にする |
| C | 前後の訪問先 A・B の間に入れるとき、遠回りの下限（A→新→B の移動 ≥ A→B の移動）を使う。甘め（楽観的）になる |

### 2-5. 擬似コード（サーバー: 職員 × 日 × 時台の「入れる」）

```
# 時刻はすべて「その日の 0:00 からの分」。区間は [開始, 終了)。
# 2 つの区間が重なる = a.開始 < b.終了 かつ a.終了 > b.開始（端が触れるだけは重ならない）
from app.core import leave

def lunch_ok(blocks):
    # 昼休みの窓の中に LUNCH_LEN 分の連続した空きが 1 つでも残るか
    for L in range(LUNCH_FROM, LUNCH_TO - LUNCH_LEN + 1, STEP):
        if どの blocks とも [L, L+LUNCH_LEN) が重ならない:
            return True
    return False

def day_window(s, d, use_off):
    ws, we = win                        # 勤務の型（空なら営業の時刻）
    if not use_off:
        return ("work", ws, we, "")
    why = ""
    # (1) らく助の週だけの休み
    if rk_off == "custom_time" and 時刻あり:
        ws, we = その時刻; why = "時間変更"
    elif rk_off in leave.LEAVE_TYPES:
        w = leave.leave_window(rk_off, ws, we)
        if w is None: return ("off", 種類の名前 + "（らく助）")
        ws, we = w; why = 種類の名前
    # (2) カイポケ個別業務の休み（種類は classify_kaipoke_leave が決める）
    if kp_off:                          # (種類, 件名)
        w = leave.leave_window(kp_off.種類, win.start, win.end)
        if w is None: return ("off", f"{件名}（カイポケ）")
        ws, we = max(ws, w.start), min(we, w.end); why = f"{件名}（カイポケ）"
    return ("work", ws, we, why)

def free_hours(ws, we):
    busy = [[v.開始 - PAD, v.終了 + PAD] for v in visits] + events + kp_unknown の時間
    hours = set()
    for t in range(ws, we - VISIT_MIN + 1, STEP):
        en = t + VISIT_MIN
        if [t, en) が busy のどれかと重なる: continue
        if not lunch_ok(busy + [[t - PAD, en + PAD]]): continue
        hours.add(t // 60)
    return hours                         # 8 時台も入りうるが表には出さない

for 日 d in 見る範囲（最大 8 週）の営業曜日:
    day_state[d] = "holiday"  if d が祝日（jp_holidays.holidays_between）
                   "no_data"  if d の材料がそろわない（§3-5）
                   "ok"
    for s in 拠点の担い手の候補（全員）:
        if d が s の勤務日でない: continue
        if not_employed: cell[s][d] = { state: "not_employed" }; continue
        rec = { n, src }
        for mode in (real, ignore):     # 休みの扱いの両方を一度に作る
            kind, ws, we, why = day_window(s, d, use_off = (mode == real))
            if kind == "off":   rec[mode] = { state: "off", why }
            elif n >= CAP:      rec[mode] = { state: "full" }
            else:
                h = free_hours(ws, we)
                rec[mode] = { state: "free" if h else "tight", hours: h, why }
        cell[s][d] = rec
```

（`mode == ignore` では `kp_unknown` も塞がない。休みを「無いとする」ため）

細かい点（試算どおり）:

- 開始の候補は勤務の窓の始まりから 5 分刻み。終わり（開始＋35 分）が窓の終わり以下であること。
- 既存の訪問は前後に `PAD` を足して塞ぐ。新しい訪問自身は `[t, t+35)` で重なりを見る（前後の `PAD` は既存の側に足してあるので二重には足さない）。
- 予定（朝会など）は **前後に足さずに** 塞ぐ。
- 昼休みは「既存の訪問（`PAD` 込み）・予定・新しい訪問（`PAD` 込み）」のどれとも重ならない `LUNCH_LEN` 分が窓の中に残ること。勤務の窓は見ない（午後休の人でも同じ判定）。
- 時台 = 入れる開始時刻の「時」。例: 10:00〜10:55 のどこかで始められれば「10 時台に入れる」。
- 件数の判定は件数だけ（予定の数は数えない）。7 件目を入れられるのは件数が 6 以下の日。
- 同行（職員名２・３）は時間を塞ぐが件数に数えない。

### 2-6. 擬似コード（画面: マスの判定）

```

for 曜日 wd, 時台 h (9..17):

TRIANGLE_MIN(N) = {4: 3, 6: 4, 8: 5}.get(N, ceil(N × 5 / 8))
```

## 3. データの取り方（段階 0 を使う）

### 3-1. カイポケの訪問（予定・実績）

1. **取り方・保存**: 段階 0 の `sources.fetch_month_csv(db, client, kind, month)`（`kind = plan_csv / actual_csv`）が取り、段階 0 の `kaipoke_source_snapshots` に置く（段階 0 §0-2・§0-3）。受け入れ枠は RPA を直接呼ばない。
   - 行は **拠点で絞らない**（`office_id` は常に NULL）。拠点で絞るのは担い手の候補だけ（H2）。
   - 空の CSV は `status='empty'`（該当なし。例: 月の 1 日の実績 0 件）、失敗は `failed`（前の `ok` の行は消えない）。受け入れ枠は `ok` と `empty` の行だけを材料にし、`empty` は「取れた・行が 0」として扱う。
   - `kaipoke_csv_snapshots` には触れないので、●未送信（`backend/app/api/v1/integrations.py:3292` の `get_latest`）・予実比較（`:827-870`）・送信後の `drop_snapshots`（`:605`、`:2119`）に影響しない（H1）。
2. **読み方**: `rows` は CSV の 1 行 1 オブジェクト（ヘッダ名がキー）なので、受け入れ枠は「職員名１」「職員名２」「職員名３」「日付」「利用者」「業務種別」「開始時間」「終了時間」をそのまま読む。
   - 業務種別が「医療保険」「介護保険」の行だけ（予実比較と同じ決まり。定数 `VISIT_BUSINESS_TYPES`、`backend/app/services/kaipoke/plan_actual_compare.py:186-189` を import する）。日付は「日」だけなので、月は `period_start` から付ける。
   - 名前・時刻の整え方は予実比較の `_norm_name`・`_norm_time`（`plan_actual_compare.py:192-218`）と同じにする。
   - **職員名３**: `rows` に入っているので、そのまま読める。改訂 1 で書いた「`parse_rows` に職員名３を足す」（M2）は、段階 0 で材料がヘッダ名のオブジェクトになったので **要らなくなった**（`parse_rows` は変えない・予実比較に触らない）。
   - **実績 CSV の重複行**（同じ職員名１・利用者・日・開始・終了）は 1 件にまとめる。
   - 職員名の結び付けは段階 0 §0-4（空白を除いて `staff.name` と比べる・`name_match.py` を使う）。結び付かない名前は件数と名前を API で返し、画面に「らく助に無い職員名 N 件」と出す（数えない）。
3. **日ごとの使い分け**（今日は JST で決める。VPS は UTC）:
   - 今日から先（今日を含む）→ **予定**（決定 Q5）。
   - 今日より前 → **実績**。ただし、その日の実績の件数（拠点を問わず全職員の主担当の行の合計）が予定の件数の **半分未満**（予定 1 件以上・実績 0 件を含む）なら、その日は **予定** で見て（`src = plan_fallback`）、内訳に「実績の入力待ちのため予定で見ています」と出す（H3）。
   - 「その日」は日単位で決める（職員単位にしないのは、カイポケで担当を入れ替えて記録した日に、ある人だけ実績が少なく見えるのを避けるため）。
4. 個別業務（朝会・休み）は CSV に入らない。実データ（9 月 589 行・10 月 653 行）は業務種別がすべて「医療保険」で、個別業務の行は 1 行も無かった。仮に入ってきても業務種別で落ちる。

### 3-2. 予定（朝会など）と休み — どこから読むか（M6）

週ごとに次の決まりで集める。

| 材料 | 段階 0 の表にその週の `tasks`（`status='ok'`）がある週 | 無い週（取れていない） |
|---|---|---|
| カイポケの個別業務 | 段階 0 の表から読む。`classify_kaipoke_leave` が休みの種類 → `kp_off`、`"unknown"` → `kp_unknown`、None で長さのあるもの → `events` | `staff_events` の `source='kaipoke'` の行で代える（決定 Q3）。分け方は同じ。画面に「らく助に取り込み済みの個別業務で見ています」と印 |
| `staff_events` の `source='kaipoke'` | **読まない**（二重を避ける） | 上のとおり代わりに読む |
| `staff_events` の `source in ('manual','fixed')`（`cancelled_at IS NULL`） | 時間を塞ぐだけ（件名が休みでも休みにしない） | 同じ |
| `staff_weekly_overrides` | `rk_off` | 同じ |

- 個別業務の取得は段階 0 の `sources.fetch_week_tasks(db, client, week_start)`。**らく助の `staff_events` には書き込まない**（段階 0 の表に置くだけ）。
- 読み方は `build_events_plan`（`backend/app/services/kaipoke/events_inbound.py:358-`）と同じく、日曜は除く（`:390-392`）、週の外は除く、名前は段階 0 §0-4 で結ぶ、時刻の取れない行は除く。
- 日をまたぐ予定は、その日の終わりを 24:00 とする（試算どおり）。**終わり ≤ 始まりの行（長さ 0 のメモを含む）は捨て、件数を数えて** 内訳の下に「時間の無い予定 N 件（メモなど）は見ていません」と出す。
- 月をまたぐ週で表示できなかった日（段階 0 の表の `covered_dates` に無い日。`events_inbound.py:101-104`、`:373-378` の `uncovered_days` と同じ考え）は、その日について「無い週」と同じ扱い（`staff_events` の kaipoke 行で代え、印）。
- `staff_events` の時刻は壁時計（JST）のまま保存されているので、`_wall_clock`（`backend/app/services/dashboard_staff_performance.py:322`）と同じ読み方をする（試算は psql で `-9 時間` して読んだ。同じ意味）。

### 3-3. 取り直しの範囲（受け入れ枠が決める・M5・決定 Q8）

取り直しの仕組み（ジョブ・RPA の空き確認・待ち・保存）は段階 0 §0-3。受け入れ枠が決めるのは **取る月・週の一覧** だけ。見る週の最大（8 週）をいつも取りそろえておき、4・6 週はその一部を使う（切り替えのたびに取り直さない）。範囲は **日で決める**。

**「カイポケから取り直す」（ふだん）**

| 何を | 範囲 |
|---|---|
| 実績 CSV（`actual_csv`） | 「今日から 14 日前」〜「昨日」の日を含む月（多くは 1 か月、月初は 2 か月） |
| 予定 CSV（`plan_csv`） | 今週と来週（月〜土）の日を含む月（1〜2 か月） |
| 個別業務（`tasks`） | 見る範囲（8 週）の週のうち、段階 0 の表に `ok` の行が無い週と、`fetched_at` がその週の日曜より前の週（＝その週が終わる前に取ったまま） |

**「8 週ぶんをすべて取り直す」（たまに）**: 8 週にかかる全部の月の実績・予定と、8 週ぶんの個別業務。初めて使うときと、過去の実績を大きく合わせたあと。

時間の目安（1 本: CSV ~50 秒、個別業務 60〜90 秒）:

| | 本数 | 時間 |
|---|---|---|
| ふだん | CSV 2〜4 本 ＋ 個別業務 1〜3 本 | 3〜7 分 |
| すべて | CSV 4〜6 本 ＋ 個別業務 8〜9 本 | 12〜15 分 |

休みの「カイポケと比べる」（段階 L）と同じ材料を使うので、どちらかで取り直したばかりの月・週は、もう一方でもそのまま使える（段階 0 §0-6）。

### 3-4. 保存とキャッシュ

- 材料の保存は段階 0 の `kaipoke_source_snapshots`（0098）だけ。受け入れ枠は自分の表を持たない（**migration 無し**）。
- **計算の結果のキャッシュ**（M7）: §2-5 の結果（全員 × 8 週ぶん）を、プロセス内に覚える。キーは「使った材料の `kaipoke_source_snapshots` の `id` と `fetched_at` の並び」＋「`SchedulingConfig` の値」＋「らく助側の材料の指紋（見る範囲の `staff_weekly_overrides`・`staff_events`（manual・fixed・必要なら kaipoke）・`staff_shifts`・担い手の候補の、件数と最終更新時刻）」。指紋が作れない表があれば、その分は 60 秒で捨てる。取り直しが 1 本終わるたびに材料が変わるので、次の表示で計算し直す。

### 3-5. 取れなかった週・日の扱い

- 取り直しの 1 本が失敗しても、ほかの本は続く（段階 0 §0-3）。失敗したとき段階 0 は前の `ok`／`empty` の行を書き換えない（段階 0 §0-2）。
- **材料が古くても使ってよい**（段階 0 §0-2）。`fetched_at` が今回の取り直しのジョブの開始より前の行（＝今回取れなかった・取らなかった月・週）もそのまま材料にし、画面にその `fetched_at` を出す（「古い材料を使っています（○/○ に取ったもの）」。`fetched_at` と、ジョブの `result_summary.failed[]` から）。
- 一度も取れていない月の日（予定・実績どちらも `ok`/`empty` の行が無い）は `no_data` として、その曜日の分母から外す（試算でカイポケの 8/31 が無いため 8 週の月曜を 7 週で見たのと同じ）。
- 個別業務だけ取れていない週は §3-2 のとおり `staff_events` の kaipoke 行で代え、印を出す（`no_data` にはしない）。
- 祝日（`backend/app/services/scheduling/jp_holidays.py:80` の `holidays_between`）は分母から外す。
- 見られた週が見る週の半分未満のマスは判定しない（「－」と理由。M8）。

### 3-6. 取り直しの進め方（段階 0 を使う）

段階 0 §0-3 のとおり。受け入れ枠から見た要点だけ書く:

- ジョブは `KaipokeJob`（`job_type="fetch"`・`params.op='acceptance-refresh'`・`params.scope='recent'|'all'`）。状態は `completed` / `failed` / `cancelled` だけ、一部失敗は `result_summary.failed[]`、`week_start` は範囲の最初の月曜（M3）。
- 始める前に、種類を問わず RPA を使うジョブ（`pending`/`running`）があれば 409。1 本ごとに RPA の空きを確かめ、塞がっていれば 30 秒おき・最大 10 回待って再試行し、駄目ならその本を `failed` にして次へ（M4）。
- イベント取り込みの非同期の経路（RPA の結果の置き場が 1 つ）は、段階 0 の「RPA の空き確認 → 自分の結果を受け取ってから次」の順で壊さない。
- 17〜18 時台は押せるが、押すときに「夕方は送信・取り込みと重なりやすい時間です。急がなければ他の時間に取り直してください」と確かめる。画面には常に「取り直しの間（最大 15 分）は、カイポケへの送信・取り込みが待たされます」と出す。
- 汎用の後始末 `_reconcile_latest_job`（`integrations.py:520-575`）に途中で閉じられないよう、段階 0 が除外の一覧に `acceptance-refresh` を足し、待ち時間を 120 分にし、1 本ごとにジョブを書き戻す（段階 0 §0-3・決定済み）。受け入れ枠ですることは無い。
- 受け入れ枠は `integrations.py` を触らない。API は `backend/app/api/v1/acceptance_matrix.py` に置き、取る範囲を決めて段階 0 の仕組みを呼ぶだけ（M12）。

  - **カイポケの材料**: 「カイポケから取った日時: 10/20 9:12（いちばん古いもの）」。「カイポケから取り直す」ボタン（admin だけ。押すと進み具合のバー「3 / 6 本・10 月の実績を取っています」）。その下に小さく「8 週ぶんをすべて取り直す（15 分ほどかかります）」。常に「取り直しの間（最大 15 分）は、カイポケへの送信・取り込みが待たされます」。取れなかったものがあれば「第 41 週の個別業務が取れませんでした。らく助に取り込み済みの個別業務で見ています」。
  - 時間の決まりは切り替えを出さず、文章で出す（下の文言）。
- 真ん中: 上に ○・△・× の数、その下に曜日 × 時間台（9〜17 時台）のマス。各マスに記号と「3/4 週」。祝日・データなしで週が減った曜日は見出しに「（3 週で判定）」。判定しないマスは「－」で、押すと理由。

- 右: 押したマスの内訳（週ごとに新しい順。緑 = 入れる人、桃 = 休み・半休、灰 = 満杯・隙間なし）。実績の入力待ちの日は「実績の入力待ちのため予定で見ています」、個別業務を取り込み済みのもので見た週は「らく助に取り込み済みの個別業務で見ています」、種類が分からない休みは「種類が分からない休み（件名）の時間を塞いでいます」。
- 印刷: マスと決まりの文章だけを印刷する（今の印刷ボタンを残す）。

**決まりの文章（画面に常に出す・文言案）**

> **この表の見方**
> 毎週決まって通う新しい患者さんを、何曜日の何時台なら受け入れられるかを、今週を含む直近 4 週のカイポケの記録（終わった日は実績、今日から先は予定）から出しています。

> - **△ 相談** … 4 週のうち **3 週** で入れられる人がいました。（6 週なら 4〜5 週、8 週なら 5〜7 週）
> - **× 難しい** … それより少ない週しか入れられる人がいませんでした。
> - **－** … 祝日やデータの無い日が多く、判定できませんでした。
>
> **入れられるかの決まり**: その人の勤務の時間の中で、前後の訪問との間に 20 分（ゆとり 8 分＋移動の見込み 12 分）をあけて 35 分の訪問が入ること。11:30〜13:30 の中に 60 分の昼休みが残ること。朝会などの予定と重ならないこと。その日の訪問が 7 件に達していないこと。休み・半休の日はその時間を除きます。祝日は数えません。
> 新しい患者さんのお住まいによる移動は見ていません。お住まいが遠いときは、提案（新しい患者さんの枠を探す）で確かめてください。

（数字は `rules` と選んだ週数から差し込む。週数を切り替えると「4 週」「3 週」の部分が変わる。昼休みの時刻などは画面に書き写さず `rules` から出す）

## 7. 試験の観点

### 7-1. 試算と同じ結果になること（いちばん大事）

- 試算の材料（`scratchpad\acc\acc_staff.csv`・`acc_shifts.csv`・`acc_ov.csv`・`acc_ev.csv`、`scratchpad\kp\acc_visits_kp.csv`）を `backend/tests/fixtures/acceptance_strict/` に写す。職員名は「職員A〜G」に置き換え、患者名は元から入っていない（`acc_visits_kp.csv` は日付・時刻・職員 ID・主/同行だけ）。

- **開発用の切り替え「予定だけで見る」**（全部の日をカイポケの予定で見る。実績・祝日の除外・入職前の判定を止める）を、試験と開発の画面でだけ使えるようにする。これを入れたとき、試算 Python と同じデータなら同じ結果になること:
  - 期待値: `scratchpad\acc\acc_result_kaipoke_35.json`（訪問 35 分・前後 20 分・上限 6 件・週 40〜43・職員 4 人）。54 マスの `weeks_ok` と週ごとの人数 `per_week` が一致すること。○0・△0。
  - 試算は上限 6 件で出したので、試験では `CAP` を引数で渡す（本番の既定は 7 件）。
  - 休みを「無いとする」: `acc_result_kaipoke_nooff_35.json` と一致（土曜が全時間 4/4 週）。
  - 休みの判定を段階 0 の `classify_kaipoke_leave`・`leave_window` に替えても結果が同じであること（§2-3 の表のとおり、試算の材料の休みの個別業務はすべて試算と同じ扱い）。
  - ページ版の 8 週（週 36〜43。8/31 がデータなし → 月曜は 7 週で判定）とも、材料を差し替えずにそのまま一致すること。

### 7-2. 決まりごとの小さな試験

- 端が触れるだけの訪問は重ならない（例: 既存 10:00〜10:30・PAD 20 → 10:50 開始は入る、10:45 は入らない）。
- 昼休み: 11:30〜13:30 が全部埋まっていれば、その日はどの時刻も入らない。新しい訪問が昼休みの最後の 60 分を潰す時刻は入らない。
- 件数 6 件の日は入り、7 件の日は「満杯」。同行だけの行（職員名２・３）は件数に入らないが時間は塞ぐ。
- 他の拠点の訪問の行も、その人の時間を塞ぐ（H2）。
- らく助の休み: `FULL_DAY_OFF`（`off`・`paid_off`）→ 終日休み。半休 → `leave_window` の窓。時間変更 → その時刻。
- カイポケの休み: `classify_kaipoke_leave` の種類 → `leave_window` の窓。override と両方あれば重なり。同じ日に 2 件 → 終日のほう。`"unknown"` → 休みにせず時間を塞ぐ（休みを「無いとする」では塞がない）。None（「休憩」「休日出勤」など）→ 予定として塞ぐ。
- manual・fixed の予定は件名が「休み」でも休みにならず、時間を塞ぐだけ（M6）。
- 段階 0 の表にその週の `tasks` がある週は、`staff_events` の kaipoke 行を読まない（同じ予定が二重に塞がない・休みが二重にならない）。無い週は kaipoke 行で代え、`tasks_from = staff_events`。
- 日をまたぐ予定は 24:00 まで塞ぐ。終わり ≤ 始まりの予定は捨てて `dropped_events` に数える。
- 実績 CSV の重複行は 1 件に数える。
- 過去の日で実績が予定の半分未満（予定 4・実績 1 → 予定で見る、予定 4・実績 2 → 実績で見る、予定 1・実績 0 → 予定で見る）。
- 段階 0 の表の `status='empty'` の月は「取れた・行が 0」、`failed` だけで `ok` の無い月は `no_data`。
- 勤務の型が休みの曜日は数えない（内訳にも出さない）。入職前の日は数えない。
- 祝日は分母から外す。見られた週が半分未満 →「－」。
- 時台: 10:55 開始だけ入る人は「10 時台」に入る。8:30 開始が入っても 8 時台は表に出ない。
- ○△× の境目: 4 週で 4→○、3→△、2→×。6 週で 6→○、5・4→△、3→×。8 週で 8→○、7〜5→△、4→×。7 週で 7→○、5→△、4→×。8 週中 3 週しか見られない →「－」。
- 今日より前は実績、今日から先は予定（JST の 0 時で切り替わる。UTC の 15 時台に試す）。
- 年またぎ・ISO 53 週（2026 年は第 53 週がある: 2026-12-28〜2027-01-03）をまたいで直近 8 週を作れること。月またぎの週で月の CSV を 2 つ使えること。
- 職員の権限の応答では理由が「休み」「半休」だけ（M9）。admin はそのまま。
- 受け入れ枠のコードに `13:00`・`12:30`・`== "off"` が無いこと（段階 0 §0-1。grep の試験）。
- **速さ**: 8 週・15 人・1 日 7 件の材料で、`compute_strict` が 1 秒以内（M7）。キャッシュが当たれば API はそれより十分速い。

### 7-3. データの取り方

- 受け入れ枠の取り直しの前後で、`kaipoke_csv_snapshots` の行が 1 行も変わらないこと（H1）。業務データ（`visits`・`staff_events`・マスタ）も 1 行も変わらないこと。

- 「実績の入力待ち」の判定を **日単位（全職員の合計）** にした（§3-1）。職員ごとにするかは、使ってみて合わなければ切り替える。
- 入職前の判定は「見る範囲（8 週）の材料の中で、その日より前にカイポケの行が無い」で決めるので、範囲の初めから長く休んでいた人も入職前と同じに扱われる（数えないだけで、結果が甘くなる向きではない）。

## 9. 実装の順序（段階 A）

前提: 段階 0（`app/core/leave.py`、`kaipoke_source_snapshots`（0098）、`app/services/kaipoke/sources.py`、名前の結び付け）がマージ済み。受け入れ枠は **段階 0 のマージ直後から、休み（段階 L）と並行して作れる**（休みの表・migration 0099 には頼らない）。休みが入るのを待つのは #8 だけ。受け入れ枠は migration を作らない。

1. **判定の中身（純粋な関数）と試算との一致の試験**（§2-5・2-6、§7-1・7-2）。DB も RPA も使わず、材料を渡して結果を返すだけ。休みは `app/core/leave.py` を使う。開発用の切り替え「予定だけで見る」を入れたとき、試算 Python と同じデータで 1 マスも違わないこと（週 40〜43 と、ページ版の 8 週）。8 週・15 人で 1 秒以内。
2. **材料を読む部分**（§3-1・§3-2）: 段階 0 の `kaipoke_source_snapshots`（`plan_csv`・`actual_csv`・`tasks`）と、らく助の勤務の型・週だけの休み・予定（manual・fixed）・取り込み済みの個別業務（代わりの材料）から、職員 × 日の材料を作る。祝日・入職前・実績の入力待ち・重複行・時間の無い予定。段階 0 の表が空でも `staff_events` の kaipoke 行で画面まで通せる。
3. **`GET /acceptance-matrix/strict`**（§4-1）とキャッシュ、職員の権限で理由を丸める試験。
4. **PC の画面**（§5-1）。チップ・週数・休みの切り替え・マス・内訳・決まりの文章・「カイポケから取った日時」。
5. **取り直し**（§3-3、§4-2）: 取る範囲を日で決める関数と、段階 0 の仕組みを呼ぶ API。画面にボタン・進み具合・失敗した週・夕方の注意・送信が待たされる注意を出す。
6. **毎週の上書き**（§6-1）: 優先・「手」の印・食い違いの印・1 マスの上書きと解除。
7. **スマホ**（§5-2）。
8. **休み（段階 L）が入った後**: 種類が分からない休みに管理者の選択（`kaipoke_leave_judgements`）を使う（§2-3）。1〜7 はこれを待たずに進めてよい。
9. 今の受け入れ枠（コースの箱の判定）を使う画面がなくなったことを確かめ、別の段で外す。

各段の終わりに、開発用の切り替え「予定だけで見る」で試算 Python と同じデータなら同じ結果になることを確かめる（本番の数字は試算と材料・日の使い分けが違うので、一致は求めない）。
