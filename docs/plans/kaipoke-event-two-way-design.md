# イベント双方向連携・固定イベント・イベントのみ取込（調査+設計検討）

作成: 2026-08-20。**ステータス = 調査完了・設計検討ドラフト。実装未着手（ユーザー方針:
段階的に進める）。** 要望 3 点:

1. **楽スケ→カイポケ**: 楽スケで登録したイベントをカイポケにも入れる
2. **固定イベント**: 朝会などを楽スケに固定登録し、毎日/毎週 双方向に回す
3. **イベントのみ取込**: カイポケ→楽スケ取込で「イベントだけ」を選べるようにする

---

## 1. 調査結果 A: カイポケ側の個別業務「入力」の仕組み（本番画面 HTML 解析）

RPA が保存していた職員スケジュール週間画面の完全 HTML（525KB・2026-08-17 取得）を解析。

### 1-a. 新規登録の入口は存在する（自動化可能）
- 各セル（職員×日）に **`showIndividualAdd(serviceOfferYm, enforcementDay,
  staffMemberInternalId)`** アンカーが常設（57 箇所 = 空セル分）。既存イベントは
  `showIndividualEdit(ym, 区分, 個別業務ID, 日, 職員内部ID)`（読取パーサが既に解析済み）。
- `showIndividualAdd` は hidden form `initPopupIndividualAdd`（**CSRF `tokenValue` 付き**）に
  年月/日/職員内部IDを詰めて `POST /bizhnc/staffSchedule/initIndividualPopup/` →
  登録ポップアップを動的描画する。
- **未確認 = ポップアップ内部**: 入力フィールド構成（時刻/名称/区分）と**保存ボタンの
  送信先エンドポイント**。ポップアップは動的ロードのため保存 HTML に含まれていない。
  → **Phase 0 プローブ**（§4）で取得する。
- 書き込みの技術方式は訪問 apply (`auto_apply.py`) と同じ **Playwright UI 自動操作**
  （クリック→フォーム入力→保存。3 段フォールバックの家風あり）が前例。

### 1-b. 個別業務の実データ構造（重要な発見）
- ページ埋め込み JSON `lsStaffServiceByWeekDtos` に全予定が構造化されている
  （HTML 正規表現より堅い将来のパーサ改善余地）。
- `individualOperationInternalId` は「種別マスタ」ではなく**登録ごとに採番される
  個別業務 ID**。名称 (`individualOperationName`) は自由テキスト。
- 実データの名称分布: **朝会**（複数ID = 手入力の都度登録）/ **休み** / 拠点名（都賀・稲毛）/
  申し送りメモ（「時間厳守：○○様」「新規契約：○○様(住所)」「写真撮影:○○様」）。
  → **朝会は既に現場が毎日カイポケへ手入力している** = 要望②の痛点そのもの。
- `planAchievementsDivision`: `01`=予定（161件）/ `02`=実績（17件）の区分あり。

## 2. 調査結果 B: 楽スケ側の現状（設計に効く事実）

- `staff_events`: `source`('manual'/'kaipoke') + `external_id`
  (`{個別業務ID}:{職員内部ID}:{日付}`) の部分 UNIQUE `(source, external_id)`。
  **source を増やしても索引はそのまま使える**。
- 取込 apply の delete は「当該週の `source='kaipoke'` 行で今回取得に無いもの」を
  **物理削除**（週置換の意味論）。manual 行は不可侵（テストで担保）。
- **逆方向の構造的課題**:
  1. **ラウンドトリップ二重化**: 楽スケ→カイポケ送信後に取込を回すと、同じ予定が
     manual 行 + kaipoke 行の 2 本になる（訪問側の突合 `_compare_entries` に相当する
     防御がイベントには無い）。
  2. **職員内部IDの供給源**: Staff にカイポケIDの列が無い。唯一の材料は取込済み行の
     `external_id` からの逆引き（= 一度も取込に現れない職員へは書けない）。
  3. FE/API に `source`/`external_id` が露出しておらず「カイポケ由来か」を UI が判別不能。
  4. UI の 3〜4 箇所に「**カイポケ反映外**」バッジ・文言が常設
     （TimelineDayBoard / TimelineEventAddDialog / SlotRegisterDialog）。①実装時は同時改修必須。
- **固定→週展開の家風**: `accompaniment_defaults` → `expand_accompaniment_defaults`
  （冪等・週全体・flush のみ・休職/退職ゲート付き）を、週生成系の **3 地点**
  （schedule.py:1753 / :1936 / auto_allocator_v2.py:10290）から呼ぶ型が確立済み。
- **非同期連携の最良型** = events-preview 型（CareFlow が job_id 発行→RPA にエコー→
  `/status/{job_id}` ポーリング・524 無縁）。新規のカイポケ通信はこれに揃える。
- RPA は**単一スロット**: 取得(訪問)→取得(イベント)→(将来)書き込み を直列に積むと
  ❶❸の所要が伸びる（現状表記 約2分）。

## 3. 設計方針案（要望別）

### ③ イベントのみ取込 — 【小】FE のみで実現可能・最初にやるべき
- BE は既に完全分離済み（events preview/apply は訪問系と独立・ゲートも常時開放）。
- `useInbound.ts` に取込対象モード（`both` / `events-only`）を追加し、
  `runDiff`/`runApply` の smart 系呼び出しを条件スキップするだけ。
  UI は❶ボタン脇のセグメント切替（旧「差分/置換」選択の跡地）が自然。
- 副次効果: events-only は RPA 1 オペで済むため**所要が約半分**になる。

### ② 固定イベント（楽スケ側の自動展開）— 【中】楽スケ内で完結・①なしでも価値あり
- 新テーブル `staff_event_defaults`（staff_id × weekday(0-6) × start/end × title ×
  blocking × 有効期間?）。`staff_shifts` 型の定義 + `expand_accompaniment_defaults` の
  作法で週生成 3 地点から冪等展開。
- 展開行は **新 source `'fixed'`** + `external_id='{default_id}:{YYYY-MM-DD}'`
  （既存部分 UNIQUE をそのまま冪等キーに流用）。
  - `'kaipoke'` は不可（取込 delete で毎回消される）/ `'manual'` も不可（再展開の冪等キーが無い）。
- 休職・退職スタッフは展開しない（同行既定と同じゲート）。
- UI: スタッフ詳細の「研修日/イベント」カード隣に「毎週の固定イベント」カード
  （曜日×時刻×名称。朝会 = 月〜土 09:00-09:15 のような登録を想定）。
- **これだけで「楽スケの朝会手入力」は消える**。カイポケへの反映は①ができるまで従来どおり
  現場手入力（または②+①が揃った時点で自動化）。

### ① 楽スケ→カイポケ書き込み — 【大】Phase 0 プローブの結果待ちで詳細化
- **RPA 新オペ** `individual-tasks-apply`: 職員スケジュール画面 → 対象セルの
  `showIndividualAdd` 起動 → ポップアップ入力 → 保存（auto_apply の UI 操作型・
  async:true + result ポーリング）。既存個別業務との重複スキップ判定を RPA 側で行う
  （画面上の同時刻・同名アンカー検出）。
- **CareFlow BE**: `events-outbound-preview/start` + `/status/{job_id}` +
  `events-outbound-apply`（events-preview 型に対称）。送信対象 = 当該週の
  `source IN ('manual','fixed')` 行。職員内部IDは取込済み `external_id` から逆引き
  （引けない職員は「送信不可」として preview で明示）。
- **二重化対策（最重要論点・プローブ後に確定）**: 有力案 =
  送信成功時にカイポケ側で採番された個別業務IDを取得し、当該行に
  `external_id` を刻んで **source を 'kaipoke' 系へ昇格**（以後は取込の update/delete
  管理下に入る = 1 予定 1 行を維持）。採番IDが保存応答から取れない場合は、
  直後に読取オペを 1 回走らせて title+時刻+職員で突合する案にフォールバック。
- UI: 連携ページ左カード（送る側）に「イベントを送る」を追加 +
  「カイポケ反映外」文言の全面差し替え。

### 双方向の定常運用イメージ（②+①+③が揃った後）
朝会 = 楽スケの固定イベントとして 1 回定義 → 毎週自動で盤面に展開 →
週次の「送る」でカイポケへ書き込み → 取込は昇格済み external_id で突合し二重化しない。
カイポケ側で現場が直接入れた予定は従来どおり取込で楽スケへ。

## 4. 段階ロードマップ（提案）

| Phase | 内容 | 規模 | 依存 |
|---|---|---|---|
| **0** | **プローブ**: RPA で登録ポップアップを開いて HTML/保存リクエストを採取（読み取りのみ・保存ボタンは押さない）。保存エンドポイント/必須項目/採番IDの応答有無を確定 | 極小 | なし |
| **1** | ③ イベントのみ取込（FE モード切替） | 小 | なし |
| **2** | ② 固定イベント定義+週展開（source='fixed'・mig 1本） | 中 | なし |
| **3** | ① outbound 書き込み（RPA 新オペ + BE/FE + 二重化対策 + 文言差し替え） | 大 | Phase 0 |
| **4** | 双方向定常運用の仕上げ（送信の定期化/モニタリング・実績区分の扱い） | 中 | 1-3 |

Phase 1・2 は独立して先行可能（カイポケに触れずリスクゼロ）。

## 5. PO / お客様への確認事項

1. **朝会の現運用**: 今カイポケへ毎日入れているのは誰か・全スタッフ分か・時刻は固定か
   （実データでは 09:00-09:15 が見える）。
2. **①の書き込み範囲**: メモ系（「時間厳守：○○様」等の申し送り）も楽スケから送るか、
   朝会などの定型のみか。**カイポケへの書き込みは不可逆**（削除も自動化するかは別論点）。
3. **実績 (planAchievementsDivision=02) の扱い**: 送るのは予定(01)のみで良いか。
4. **③の優先度**: 「イベントのみ取込」を先に出してよいか（最小工数・即日級）。
5. 楽スケ側でカイポケ由来イベントを編集/削除したときの扱い（現状は次回取込で
   カイポケ側が正として復元される — 双方向後もこの原則を維持するか）。

## 6. リスク・制約（横断）

- カイポケ画面の構造変更で RPA が壊れるリスクは読取と同様（書き込みは事故影響が大きい
  ため、保存前スクリーンショット + 事後読取検証を必須にする）。
- RPA 単一スロットの直列時間増（events-only モードと非同期化で緩和）。
- 職員内部IDが取込実績に依存（全職員が一度でも個別業務/訪問取込に現れれば解消。
  恒久対応は Staff への kaipoke_id 列追加 = 別途小 mig）。
- CSRF トークン・セッションは既存 RPA のログイン基盤（state.json）をそのまま利用可能。
