## 5. 気になる点・リスク

- **週42 がこのままカイポケへ送られると、重なったままの予定が現場へ出る**。最優先で PO と川名さんに確認。
- **「週を生成（固定訪問から）」は危ない**: コースの無い固定枠を稲A に寄せ、人数・時刻の重なりも見ない（layer1 は移動・昼・人数を見ない作り）。来週以降も同じことが起きる。当面は「前の週をコピー」を勧めるか、生成後に必ずならしの道具で診断する。

- 道具の計算は 1 日 30 秒（週で約 3 分）。結果は毎回少し違いうる（探索の打ち切り）。決まりの検査が 0 件なら、どの案でも決まりは守られている。
- 道具は ssh で本番に繋ぐ（`config.local.json` の server）。別の PC で使うときは鍵と設定が要る。
- 朝会の件のように、**psql の表示（Asia/Tokyo）とアプリの時刻の決まりが違う**。イベントの時刻を DB で見るときは必ず UTC で読む。

## 9. 手順メモ

- **ならしの実行**（リポジトリ直下・Bash）:
  ```bash
  PYTHONIOENCODING=utf-8 uv run -q --python 3.12 --with ortools --with openpyxl --with httpx \
    python docs/tools/week-leveling/level.py --week 2026-10-12 [--jev] [--day ...] [--off S004@2026-10-13] [--allow-over 1] [--balance]
  ```
  出力は `docs/reports/<日時>-week<NN>-leveling<印>/`。`summary.json` の `rule_errors` が 0 であることを必ず確かめる。条件だけ変えて試すときは `--from-dir <前回の出力>`。標準入力が無いと待たされることがあるので、Claude の Bash では末尾に `< /dev/null` を付けると安全。
- **PDF**: 普段使いの Chrome と別のプロフィールで動かさないと終わらない（`level.py` は対応済み）。
- **本番の読み取り**: SQL はファイルに書いて `scp` → `ssh ... docker exec -i carelink-postgres psql ... < /tmp/q.sql` の形が確実。イベントの時刻は `AT TIME ZONE 'UTC'`。
- **デプロイ**: 前回総括 §9 と同じ（push → pg_dump → pull → build →（migration）→ recreate → healthz）。デプロイ前に `kaipoke_jobs` に running が無いことを確かめる（再起動で裏の読み込みが切れるため）。
