## 1. 目的と範囲
- 管理者が**画面で行う入力作業を、エージェントが既存の API で代わりに行う**。一番の目的は「**今週のスケジュールの最適解**」。加えて、急な休み・キャンセル・特別訪問週間・人員の過不足・コース／職員スケジュールの調整、マスターの更新、カイポケとの差分、データへの質問への回答。
- **アプリ本体（backend・frontend）は変更しない**。道具とスキルは `agent/` に置く。
- Claude Code と Codex CLI の**両方**で同じスキルを使う。
- 範囲外: 職員本人の操作（打刻・サイン・本人の休み申請）の代行（実績の偽装になる）／SMS 送信（機能が未実装）／右下の小窓（frontend の変更が要るので後の段）。

## 3. 共通の道具「rk」（すべてのスキルが使う）
### 3-1. つなぎ方（アプリ変更なし）
- 本番は Cloudflare Access の後ろなので、外からは API を呼べない（R1 §1）。
- `RK_MODE=pc`: SSH で VPS に入り、**サーバーの中から** `http://127.0.0.1:18001/api/v1` を呼ぶ（ssh のポート転送）。読み取り SQL は `ssh → docker exec carelink-postgres psql`（今の `extract.py` と同じ・`begin transaction read only`）。
- `RK_MODE=vps`: VPS 上で動くとき。API は直接 127.0.0.1:18001、SQL は docker exec。
- ログイン: 既存の `POST /auth/login`（エージェント専用の管理者ユーザーを推奨・§9）。**refresh トークンを使い回し、ログインを繰り返さない**（15 分 5 回の制限・09-14 の事故）。資格情報は環境変数か `~/.rakusuke/credentials`（リポジトリに置かない）。

### 3-2. コマンド（インターフェースの正典。スキルはこれだけを使う）
| コマンド | 働き |
|---|---|
| `rk whoami` | つながるか・誰として動いているかを表示 |
| `rk get <path> [-q k=v ...]` | GET。JSON を標準出力 |
| `rk post-read <path> --json <file|->` | 読むだけの POST（unsent-summary・dry_run の提案など）。R1 で「読み取り」と印のあるものだけ通す |
| `rk sql <name> [-p k=v ...]` | `agent/sql/<name>.sql` を読み取り専用トランザクションで実行し JSON で返す。`rk sql --list` で一覧 |
| `rk plan check <plan.json>` | 案の形と各操作の API が許可リストにあるかを検査 |
| `rk plan report <plan.json> [--a3]` | 案を A4 縦（一覧）／A3 横（時間割）の HTML に（`docs/reports/agent/`） |
| `rk backup --label <名前>` | VPS で pg_dump（`/opt/carelink/backups/agent-<名前>-<UTC 時刻>.sql.gz`） |
| `rk apply <plan.json> --approved "<誰が・いつ>"` | 反映。**承認の記録と直前のバックアップが無いと動かない**。各操作の前の状態を読んで保存 → 1 件ずつ API → 最初の想定外で止まる → 実行記録と「元に戻す案」を `runs/` に保存 |
| `rk verify <plan.json>` | 反映後に読み直して案と照合 |
| `rk undo <run-id>` | 保存した「元に戻す案」を反映（同じく承認が要る） |
| `rk level week|day ...` | ならしの道具を rk のつなぎ方で動かす（extract を rk sql/ssh に・反映は rk apply 用の案を出力） |

### 3-3. 案（plan.json）の形
```json
{ "kind": "staff-absence | week-leveling | cancel | add | move | special-week | master-update | ...",
  "title": "10/22（木）田中さん お休みの振り分け", "target": {"iso_year":2026,"iso_week":43,"date":"2026-10-22"},
  "summary": ["5 件を 鈴木・高橋・佐藤 へ", "移動 142→128 分"],
  "ops": [ { "op": "assign-staff-week", "visit_id": "…", "to_staff": "S005",
             "label": "9:30 伊東様 田中→鈴木" } ],
  "checks": ["1 人の上限", "NG", "女性限定", "…"], "warnings": [] }
```
- `op` は**許可リスト**（`rk/ops.py`）で API・本文・元に戻し方に対応づける。リストに無い操作は反映できない。
- 許可リストの初版（R1・R2・step1-facts から。画面と同じ API）: 担当の付け替え（今週だけ）・今週だけ移動（日時）・今週だけ取消・今週だけ追加・保留プールへ戻す（DELETE /visits）・プールから置く・コースの担当変更（PATCH /courses）・職員の休み（overrides）・急休代替（staff-off-week）・同行の登録・特別訪問週間の登録と○の配置・患者の状態変更・固定訪問の枠の更新・希望の更新・NG の更新。
- **既定で禁止**（R2 §4-3）: 週を生成・今週全件解除・自動スタッフ割当・全面最適化・範囲最適化の適用・sync-fixed-to-week・月初展開・Excel 完全置換・置換取込・パスワード操作・職員編集の全項目保存。PO が名前を挙げて頼んだ時だけ、別の手順で。
- カイポケへの送信（`integrations/apply`）は別のスキルで、差分を見せて了承を得てから、日中に。

### 3-4. 操作の部品の形（担当どうしの約束・`agent/rk/opsbase.py`）
```python
from rk.opsbase import Op, register, Api   # Api: get(path, params=None)->Any / call(method, path, body=None)->Any

@register
class AssignStaffWeek(Op):
    name = "assign-staff-week"            # plan.json の "op"
    summary = "今週だけ担当を付け替える"
    def request(self, op: dict) -> tuple[str, str, dict | None]: ...   # (method, path, body) — 画面と同じ API
    def snapshot(self, api: Api, op: dict) -> dict: ...                # 反映前の状態を読む（元に戻すため）
    def inverse(self, op: dict, before: dict) -> list[dict] | None: ... # 元に戻す操作（None = バックアップからしか戻せない）
    def verify(self, api: Api, op: dict) -> list[str]: ...             # 反映後に読み直して食い違いを返す（空なら OK）
```
- 各分野の部品は `agent/rk/ops/<分野>.py` に置く（`visits.py`・`staff.py`・`special.py`・`masters.py`・`kaipoke.py`）。`rk/ops/__init__.py` が全部を読み込む。
- テストは偽の Api（記録するだけ）で行う。本番の API は呼ばない。

## 3-5. 足りない API（PO 2026-10-12「作っていくしかない」）
- **画面（frontend）は変えず、backend に足りない API を足す**。足すたびに テスト → 別担当のレビュー → PO 了承 → pg_dump → デプロイ。
- 候補（調査から）: まとめて読む窓口（職員の勤務・休み・予定・NG を週単位で一括／直前 4 週の担当歴／患者の状態での絞り込み・名前検索）、エージェント向けの週の文脈（ならしの道具の入力一式）、反映の一括とまとめての取り消し（操作のグループ単位）、エージェント専用の鍵（取り消せる・期限つき）。
- まず読み取り系（安全）から。書き込み系の一括・取り消しは、rk の API 逐次方式で足りない所が見えてから。

## 4. 安全の約束（AGENTS.md に書き、rk で強制する）
1. 読むのは自由。**書く前に必ず案を作り、A4/A3 と要点を見せ、選択肢で了承を取る**（日本語）。
2. 反映の前に `rk backup`。反映は案のとおり 1 件ずつ、想定外で止まる。終わったら `rk verify`。
3. 元に戻す: `rk undo`（API で戻せる操作）。戻せない操作は案の時点で「戻すにはバックアップから」と明示し、了承の時に伝える。
4. カイポケはお客様が直接直すことがある → 送る前・取り込む前に必ず差分を見る。
5. 画面の言葉は「合わせる・調整」。アプリ名は「らく助」。
6. 答えには根拠（どの API・どの SQL・いつのデータか）を添える。カイポケとの比較は保存した CSV の時刻を必ず言う。
7. 時刻の扱い（R3 §3）: 予定は日本時間・打刻は UTC→日本時間・職員の予定は UTC 表示の日本時間。
