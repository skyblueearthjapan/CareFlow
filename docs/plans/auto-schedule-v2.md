## 0. なぜ v2 を書くのか (v1 の何が間違っていたか)

### 0.1 v1 実装の問題

| # | 問題 | 影響 |
|---|---|---|
| P1 | **コースの定義が間違っていた** | v1 は「拠点 × ラベル(A-E)」を course とみなし K-Means クラスタリングしたが、本来は「**1 スタッフが 1 日担当する午前ブロック + 午後ブロック**」 |
| P2 | **午前/午後の概念がない** | 1 日を 1 つの距離クラスタとして扱い、午前/午後で異なるエリアを回るロジックが組めない |
| P3 | **K (クラスタ数) = スタッフ数** で固定 | 稲毛 2 名 / 都賀 1 名 → 月曜の全患者を 2 クラスタに押し込み → **A コースに 32 名集中** (実データで確認済) |
| P4 | **容量超過 enforcement が無効化** | K=1 のとき `_enforce_course_capacity` が機能せず、6 名上限が破られる |
| P5 | **運用主体が逆** | v1 は「自動算出が新規 course を作る」前提だが、実運用は「**患者マスタの固定枠が真実**」で自動算出は補助 |
| P6 | **全面最適化を日常機能扱い** | 本来は「年に数回の見直し用」で、日常は差分追加だけ |
| P7 | **個別マスタ編集時の Before/After 提案が無い** | 患者の希望曜日を変えた時に「移動距離どう変わる?」を提示できない |
| P8 | **「固定枠に戻す/合わせる」ボタンが無い** | 一度ばらしたスケジュールを患者マスタの設定に戻せない |

### 0.2 v1 → v2 で変える根本コンセプト

| 観点 | v1 | v2 |
|---|---|---|
| コース | 「拠点 × ラベル」 | **「1 スタッフ × 1 日 (午前 + 午後)」** |
| クラスタリング軸 | 拠点 × 曜日 | **拠点 × 曜日 × 午前 or 午後** |
| K 値 | スタッフ数 | **患者数 ÷ 2-3 (各時間帯ごと)** |
| 主機能 | 全面最適化 | **差分追加 (日常)** + **全面最適化 (見直し)** |
| データ主体 | 自動算出が visits を作る | **患者マスタの固定枠が主**、自動算出は固定枠を更新する提案 |
| UI | 1 つのモーダル | **Before/After 並列**, **個別マスタ編集時の提案**, **固定枠に戻すボタン** |

## 1. 用語定義 (v1 から変更あり)

| 用語 | v2 での定義 |
|---|---|
| **コース** | **1 スタッフが 1 日に担当する訪問の集合**。形式は「午前ブロック + 昼休憩 + 午後ブロック」。曜日ごとに別コース (=月曜の A さんコース、火曜の A さんコース、…) |
| **午前ブロック** | **9:30 〜 12:00** の訪問群 (なるべく近場で集中) |
| **昼休憩** | **12:00 〜 13:00** (訪問枠不可) |
| **午後ブロック** | **13:00 〜 18:00** の訪問群 (午前と別エリアに移動可、移動時間考慮) |
| **時間帯** | 「午前」または「午後」の 2 値 |
| **セット** | 同じ (曜日 × 時間帯) で **距離が近い 2-3 名の visit 集合**。これがコースの構成要素 |
| **コース数** | 当該拠点の **稼働可能なスタッフ数 = 「`is_trainee=false` でその曜日に勤務可能なスタッフ数」**。マネージャー補充は別途警告 |
| **固定枠** | `patient_fixed_visits` テーブル。**患者マスタが管理する真実のスケジュール**。日常運用ではこれをスケジュールに反映 |
| **プール** | 「**まだ固定枠が決まっていない患者**」(`status='active'` かつ `patient_fixed_visits` 行無し) |
| **差分追加モード** | プール患者を既存固定枠の隙間に挿入する日常モード |
| **全面最適化モード** | 全 active 患者で固定枠ごと再構築する見直しモード |

## 2. 運用フロー (v2 の中心思想)

```
[日常運用]
  ┌──────────────────────────────────┐
  │ 患者マスタ「週訪問スケジュール」(固定枠)│
  │ - この患者は 月10:00 / 水10:00 / 金10:00 │
  │ - 一度決まったら基本不変                │
  └──────────────┬───────────────────┘
                 │ そのまま反映
                 ▼
  ┌──────────────────────────────────┐
  │ 週次スケジュール (visits + courses)    │
  │ - 毎週同じ時刻・同じコース            │
  │ - スタッフのみローテーション            │
  └──────────────────────────────────┘
                 │
                 │ 新規患者 / 状態変化があれば
                 ▼
  ┌──────────────────────────────────┐
  │ 差分追加モード                     │
  │ - プール患者 (固定枠未登録) を抽出     │
  │ - 希望曜日 × 午前/午後 に仮配置        │
  │ - どのコースに入る? を Before/After 提案 │
  │ - ユーザー採用 → 患者マスタに固定枠保存 │
  └──────────────────────────────────┘

[年に数回の見直し]
  ┌──────────────────────────────────┐
  │ 全面最適化モード                    │
  │ - 全 active 患者でゼロから再構築      │

  │ - ユーザー採用 → 患者マスタ一括更新   │
  └──────────────────────────────────┘
```

## 3. 機能 A: 差分追加モード (日常用、5 段階)

### 3.1 目的
新規契約・状態変化で **固定枠未登録の患者** が出た時、既存固定枠を動かさずに最適な枠に挿入する。

### 3.2 入力
- 対象週 (例: 2026-W21)
- 対象拠点 (例: 稲毛)
- プール患者: `status='active' AND patient_fixed_visits 行無し`

### 3.3 算出 5 段階

```
[段階 1] プール作成
  プール患者を抽出して列挙

[段階 2] 仮配置 (希望曜日 × 時間帯)
  各プール患者について:
    希望曜日 (weekly_pattern.preferred_weekdays) で展開
    希望時間帯 (time_type) から 午前 / 午後 を判定
      - 固定 14:00 → 午後 (12:00 以降)
      - 時間帯 10:00-14:00 → 午前 (12:00 までに開始可能なら午前優先)
      - 午前 / 午後 / 終日 → そのまま
    (曜日 × 時間帯) バケットに仮置き

[段階 3] コース候補マッチング
  各プール患者を、既存固定枠の (曜日 × 時間帯) バケットと突き合わせ:
    候補 (a) 既存セット に追加できるか (容量 6 名以内、距離が近い)
    候補 (b) 既存セット のどこにも入らない → 新セット候補

[段階 4] 提案構築 (Before / After)
  プール患者ごとに以下を提案:
    1. どのコース・どの時間帯に入れるか (推奨案)
    2. 距離 / スタッフ偏差 / 時間ロスの変化量
    3. 編成を変えれば対応可能か (例: 既存患者 X を別曜日に動かせば入る)
  代案も 1-2 個提示

[段階 5] 採用 / 個別調整
  ユーザーが提案ごとに 採用 / 却下 / 編成変更 を選択
  採用された分が 患者マスタ固定枠 (patient_fixed_visits) に保存
```

### 3.4 v1 との差分
- v1 は K-Means で「全 visits を一気に分割」 → A コース集中の原因
- v2 は「既存セット + 候補マッチング」で**プール患者を 1 人ずつ** 個別配置

## 4. 機能 B: 全面最適化モード (見直し用、5 段階)

### 4.1 目的
**年に数回、現状の固定枠を全部見直して「移動距離 -20% 改善できますよ」と提案する**。

### 4.2 入力
- 対象週 (時間軸はマーカー)
- 対象拠点
- 全 active 患者 (固定枠あり / なし 問わず)

### 4.3 算出 5 段階 (ユーザー説明と完全一致)

```
[段階 1] 全患者プール化
  全 active 患者から weekly_pattern を抽出
  希望曜日 + 希望時間 (午前 / 午後 / 終日 / 固定 / 時間帯) を取得
  全員を「条件付きプール」に投入

[段階 2] 曜日 × 時間帯への配置
  例: 週3回希望 (月水金) の患者 → 月午前 (or 午後) / 水午前 / 金午前 に展開
  各 (曜日 × 時間帯) バケットに患者を入れる
  → 月午前 / 月午後 / 火午前 / 火午後 / ... / 土午前 / 土午後 の 12 バケット

[段階 3] 距離クラスタリング (★コア★)
  各バケット内で:
    地理的に最も近い 2-3 名を 1 セットにする
    セット = 「ある日のある時間帯のミニルート」

  例 (月午前 バケットに 9 名いる場合):
    セット 1: 患者 A, B, C (近場 1)
    セット 2: 患者 D, E (近場 2)
    セット 3: 患者 F, G, H (近場 3)
    セット 4: 患者 I (1 人だけ離れている)

  → セット数 はコース数を超えてもよい (段階 4 で調整)

[段階 4] コース数制約 (= スタッフ数) の適用
  当該曜日の稼働スタッフ数 (is_trainee=false かつ shift で出勤) = N

  段階 3 でできたセット数 が:
    ≤ N: そのまま採用
    > N: 余ったセットを別バケットへ流す or マネージャー補充警告

  例: 月午前で 4 セットできたが N=3 → 1 セットを別曜日 or マネージャー補充

[段階 5] 午前 ↔ 午後 の組み合わせ
  各スタッフの 1 日 = 「午前セット X + 午後セット Y」

  組み合わせ条件:
    1. 同エリア優先 (午前午後同じエリアなら昼休憩のみ)
    2. 別エリアの場合: 移動時間 + 昼休憩 (≒ 2 時間) を考慮、無理な組み合わせは禁止
    3. 「午前 幕張 → 午後 都賀 → 午後 稲毛」のような あちこち移動 は不可
    4. ローテーション履歴と組み合わせ (同患者に同スタッフ連続を避ける)

  → 各曜日について、午前×午後の組み合わせを最適化
  → 1 スタッフ 1 日のコースが確定
```

### 4.4 出力
- 全曜日 × 全コースの提案ビジュアル
- Before (現在の patient_fixed_visits) と After (提案) を週単位で比較
- 全体の改善指標 (移動距離 / スタッフ偏差 / 時間ロス)

### 4.5 採用フロー
- ユーザーは「採用」で **patient_fixed_visits を一括更新**
- 「採用しない」で現状維持
- 部分採用 (この曜日だけ採用) は v2.1 で検討

## 5. 機能 C: 個別マスタ編集時の Before/After 提案 (新規)

### 5.1 目的
患者の希望曜日 / 希望時間を変更しようとした時に、「変更後のスケジュールへの影響」を **その場で見せて判断材料にする**。

### 5.2 トリガー
- 患者編集画面で `weekly_pattern.preferred_weekdays` や `preferred_start` を変更
- 「プレビュー」ボタンで Before/After 計算

### 5.3 表示内容
- 現在のコース配置 (Before)
- 変更を反映した場合のコース配置 (After)
- 移動距離・時間ロスの差
- 警告: 「この変更で月曜午後 B コースが容量超過します」等
- 採用ボタン: 患者マスタ更新 + 関連スケジュール更新

---

## 6. 機能 D: 「固定枠に戻す / 合わせる」ボタン (新規)

### 6.1 目的
週次スケジュールが患者マスタ固定枠から逸脱した時 (ドラッグ&ドロップで動かした、自動算出を採用した等)、「**もう一度 患者マスタの固定枠に揃える**」操作を 1 クリックで。

### 6.2 配置
- スケジュール画面 (`/schedule`) のヘッダー
- 「📌 固定枠に合わせる」ボタン (admin/manager only)

### 6.3 動作
- 対象週の visits をすべて `patient_fixed_visits` から再生成
- 既存 visits は soft-delete、新 visits を INSERT
- スタッフ割当はローテーションで再計算

### 6.4 注意
- ユーザーが意図的に変えた変更も上書きされるため、確認ダイアログ必須
- 「変更前」を 1 回戻せるよう、操作ログを残す (v2.1 で undo 機能検討)

## 9. 実装の単純化原則 (ユーザー要望: 「シンプルに、複雑にせず」)

| 原則 | 適用 |
|---|---|
| **新規モデル / 新規テーブルを作らない** | 既存 patient_fixed_visits / courses / visits で対応 |
| **K-Means を捨てる** | v1 の K-Means は問題だった。v2 は 「**距離行列で 2-3 人ずつ greedy grouping**」 (シンプル) |
| **段階を踏む** | 段階 1 → 2 → 3 → 4 → 5 を独立関数化、各段階単体テスト可能 |
| **既存 Layer 1/2/3 を呼ばない** | v2 はゼロから書く (v1 で再利用したが整合性が悪かった) |
| **MVP は差分追加モードのみ** | 全面最適化 / 個別 Before-After / 固定枠に戻す は段階リリース |

## 12. ハード制約 / ソフト制約 (v1 から移植・整理)

### 12.1 ハード制約 (絶対遵守)
- H1: 同患者の visit 時刻は週通して同じ
- H2: 同住所患者は同 timeslot 配置、最大 2 人
- H3: 同住所 visit の連続性 (course 内ルートで連続配置)
- H4: 全訪問同スタッフ禁止 (週次ローテーション)
- H5: 受入カレンダーの × 時刻回避
- H6: スタッフ実出勤枠遵守
- H7: 性別制限遵守
- H8: 新人 (is_trainee=true) 単独訪問禁止
- **(新) H9: コース容量 6 名以内 (午前 + 午後の合計)**
- **(新) H10: 昼休憩 12:00-13:00 に visit を入れない**

### 12.2 ソフト制約 (ペナルティ最小化)
- S1: 移動距離最小化
- S2: スタッフ間負荷均等
- S3: 同患者×同スタッフの連続避け (週内 + 週またぎ)
- S4: 午前午後別エリア時の移動余裕 (≒ 2 時間)
- S5: あちこち移動禁止 (午前午後で 2 エリア程度まで)
- S6: コース内ルート順 (TSP) で総距離最短化
- S7: 受入カレンダー △ 時刻は控えめに
